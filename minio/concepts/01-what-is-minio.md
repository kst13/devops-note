# MinIO란 무엇이고 왜 필요한가

> MinIO는 **S3 호환 API를 제공하는 오브젝트 스토리지**입니다. 앱 입장에서는 AWS S3 SDK를 그대로 쓰는 사내 파일 저장소이고, 서버 입장에서는 바이트 덩어리(오브젝트)를 이름 붙여 보관하는 단순한 저장 계층입니다.

## 1. 오브젝트 스토리지와 S3 API

- **오브젝트 스토리지** = 파일을 디렉터리 트리가 아니라 "버킷 + 키(이름)"로 저장하는 방식. 파일시스템의 잠금·부분 수정 같은 복잡함을 버리는 대신, HTTP로 어디서든 넣고 꺼낼 수 있고 수평 확장이 쉽습니다.
- **S3 API** = AWS S3의 HTTP 통신 규약. 오브젝트 스토리지의 사실상 표준 인터페이스가 되어, MinIO를 포함한 대부분의 구현체가 이 규약을 따릅니다.
- 그래서 앱은 전용 클라이언트 없이 **AWS SDK를 그대로** 씁니다:

```java
S3Client s3 = S3Client.builder()
        .endpointOverride(URI.create("https://minio.internal:9000"))   // 접속처만 사내 MinIO
        .credentialsProvider(StaticCredentialsProvider.create(
                AwsBasicCredentials.create("notification-service", secretKey)))
        .region(Region.US_EAST_1)      // 형식상 필요 — MinIO 는 값 무관
        .forcePathStyle(true)
        .build();

s3.putObject(b -> b.bucket("notification-attachments").key("2026/09/report.pdf"),
        RequestBody.fromFile(path));
```

- 포트 역할: **9000 = S3 API(앱 코드가 사용)**, 9001 = 웹 콘솔(관리자 화면).
- S3 표준이라 나중에 실제 AWS S3나 다른 호환 스토리지로 옮겨도 앱 코드는 엔드포인트·키만 바뀝니다.

## 2. 왜 필요한가 — 현재 방식(서버 로컬/마운트 저장)의 문제

파일을 앱 서버에 마운트된 저장소에 직접 쓰는 방식은 인프라 관점에서 관리 사각지대를 만듭니다:

| 문제 | 결과 |
| --- | --- |
| 서버와 파일이 묶임 | 서버 교체·이전에 파일 이사가 따라붙고, 앱을 2대로 늘리면 파일 동기화 문제 발생. 인프라 작업의 발목을 잡음 |
| 백업이 서버별 제각각 | 어떤 파일이 어디 있고 무엇이 백업되는지 전체 그림 없음 |
| 접근 통제 없음 | 서버에 들어가면 다 보이는 구조. 삭제 추적 불가 |
| 용량 관리 분산 | 서버마다 여유 공간을 각자 확보 → 전사적으로 빈 공간이 흩어져 낭비 |

MinIO 도입으로 얻는 것:

- **중앙화 + 표준 API** — 앱 서버가 파일 없는(stateless) 서버가 되어 자유롭게 교체·증설 가능
- **거버넌스** — 서비스별 access key + 버킷 정책으로 자기 버킷만 접근(Kafka의 계정·ACL 모델과 동일), 버저닝으로 삭제 실수 복구, 수명주기 규칙으로 자동 정리
- **운영 통합** — Prometheus 메트릭 내장으로 기존 모니터링 스택에 그대로 편입

## 3. 저장은 멍청하게, 의미는 위층에서

MinIO는 내용물이 뭔지 모릅니다 — PDF든, DB에서 내린 Parquet 데이터 파일이든 똑같은 오브젝트입니다. 의미는 위층이 부여합니다:

| 용도 | MinIO에 저장되는 것 | 의미를 부여하는 층 |
| --- | --- | --- |
| 파일 저장소 | PDF·이미지 그 자체 | 앱이 키(경로)로 직접 넣고 꺼냄 |
| DB 콜드 데이터 | Parquet 파일 + Iceberg 메타 파일 | Iceberg가 "테이블"로 해석, Trino가 SQL로 조회 |

Kafka 브로커가 메시지를 바이트로만 나르고 의미는 스키마가 부여하는 것과 같은 구도입니다. 이 성질 덕분에 **파일 저장소로 도입한 인스턴스가 나중에 데이터 분석 기반(레이크하우스)의 저장층을 겸할 수 있습니다** — [05 레이크하우스와 DB 콜드 데이터](05-lakehouse-and-cold-data.md) 참고.

## 4. 도입 검토 항목

- **라이선스** — MinIO 커뮤니티판은 AGPLv3이며, 최근 신기능이 상용판(AIStor) 중심으로 재편되어 커뮤니티판은 보안 패치 위주로 유지되는 흐름입니다. MinIO를 수정·재배포하지 않고 API로만 쓰는 일반적 사내 사용에선 보통 문제가 없지만, 법무 정책 확인과 장기 유지보수 리스크(대안: Ceph RGW, SeaweedFS, Garage 등) 검토 항목을 도입 문서에 남겨둡니다.
- **파일 저장소 특성** — 잠깐 못 읽어도 서비스 전체가 죽지 않는 데이터(첨부·문서·리포트)에 적합. 모든 요청이 파일을 거치는 실시간 경로라면 처음부터 분산 구성(HA)을 검토해야 합니다 — [02 배포 형태](02-deployment-topology.md).
