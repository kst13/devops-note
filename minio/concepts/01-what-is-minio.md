# MinIO란 무엇이고 왜 필요한가

> MinIO는 **S3 호환 API를 제공하는 오브젝트 스토리지**입니다. 앱 입장에서는 AWS S3 SDK를 그대로 쓰는 사내 파일 저장소이고, 서버 입장에서는 바이트 덩어리(오브젝트)를 이름 붙여 보관하는 단순한 저장 계층입니다.

## 1. 오브젝트 스토리지와 S3 API

- **오브젝트 스토리지** = 파일을 디렉터리 트리가 아니라 "버킷 + 키(이름)"로 저장하는 방식. 파일시스템의 잠금·부분 수정 같은 복잡함을 버리는 대신, HTTP로 어디서든 넣고 꺼낼 수 있고 수평 확장이 쉽습니다.
- **S3 API** = AWS S3의 HTTP 통신 규약. 오브젝트 스토리지의 사실상 표준 인터페이스가 되어, MinIO를 포함한 대부분의 구현체가 이 규약을 따릅니다.
- 그래서 앱은 전용 클라이언트 없이 **AWS SDK를 그대로** 씁니다:

```java
S3Client s3 = S3Client.builder()
        .endpointOverride(URI.create("https://minio.internal:9000"))   // 접속처만 사내 MinIO
        .credentialsProvider(StaticCredentialsProvider.create(
                AwsBasicCredentials.create("notification-service", secretKey)))
        .region(Region.US_EAST_1)      // 형식상 필요 — MinIO 는 값 무관
        .forcePathStyle(true)
        .build();

s3.putObject(b -> b.bucket("notification-attachments").key("2026/09/report.pdf"),
        RequestBody.fromFile(path));
```

- 포트 역할: **9000 = S3 API(앱 코드가 사용)**, 9001 = 웹 콘솔(관리자 화면).
- S3 표준이라 나중에 실제 AWS S3나 다른 호환 스토리지로 옮겨도 앱 코드는 엔드포인트·키만 바뀝니다.

## 2. 왜 필요한가 — 현재 방식(서버 로컬/마운트 저장)의 문제

먼저 분명히 할 점이 있습니다. 파일 하나를 넣고 꺼내는 기능 자체에서는 MinIO가 로컬 디스크나 NAS보다 나을 것이 없습니다. 파일시스템이 더 단순하고 더 빠릅니다. MinIO의 이점은 **파일이 앱 서버에 묶여 있어서 생기는 문제**를 없애는 데서 나옵니다. 그 문제가 실제로 있는지가 도입 판단의 기준입니다.

### 현재 파일 서비스에서 확인된 문제

현재 파일 애플리케이션은 업로드·다운로드·삭제·조회만 하는 단순한 구조입니다. 앱 로직이 거의 없고 저장소가 전부입니다. 그런데 저장소 쪽에서 두 가지가 확인됐습니다.

| 확인된 문제 | 지금 (파일시스템) | 왜 생기나 |
| --- | --- | --- |
| **제대로 저장됐는지 확인이 어렵다** | `write()` 성공은 OS 버퍼에 들어갔다는 뜻이다. 디스크에 온전히 남았다는 보장이 아니다. 깨진 파일은 나중에 열어 봐야 안다 | 파일시스템은 저장 결과를 검증할 체크섬을 돌려주지 않는다 |
| **지워지면 복구가 어렵다** | 백업 시점으로만 되돌릴 수 있다. 백업이 없으면 끝이다. 누가 지웠는지도 모른다 | 파일시스템의 삭제는 즉시 제거이고, 감사 로그가 없다 |

MinIO는 정확히 이 두 문제를 위한 기능을 갖고 있습니다.

| 문제 | MinIO의 답 | 동작 |
| --- | --- | --- |
| 저장 확인 | **ETag(체크섬) 응답** | 업로드 응답에 저장된 객체의 해시가 온다. 보낸 파일의 해시와 비교하면 그 자리에서 검증된다. S3 SDK가 자동으로 대조한다 |
| 저장 후 무결성 | **해시 저장 + 읽기 시 대조** | 객체마다 해시를 함께 저장하고 읽을 때 대조해 비트 깨짐(bit rot)을 잡는다. 분산 구성이면 Erasure Coding으로 깨진 조각을 복원한다 |
| 존재 확인 | **`HEAD` 요청** | 크기·해시·저장 시각을 API로 묻는다. 서버에 들어가 `ls` 하는 것이 아니라 앱이 코드로 확인한다 |
| 실수 삭제 | **버저닝** | 삭제와 덮어쓰기가 "새 버전 추가"로 기록된다. 삭제된 파일은 삭제 마커만 붙고 이전 버전이 남아 한 줄로 되살린다 |
| 누가 지웠나 | **감사 로그** | 누가 언제 어떤 키를 올리고 받고 지웠는지 남는다 |
| 규정 보관 | **Object Lock** | 보관 기간 동안은 관리자도 지울 수 없다. 계약서·정산 파일용 |

```bash
mc version enable our-minio/files                 # 버킷 생성 직후, 파일을 넣기 전에 켠다
mc undo our-minio/files/2026/09/report.pdf        # 마지막 삭제·덮어쓰기 되돌리기
mc stat our-minio/files/2026/09/report.pdf        # 크기·ETag·저장 시각 확인
```

### 그 밖에 앱 서버와 파일이 묶여서 생기는 문제

| 문제 | 결과 | MinIO |
| --- | --- | --- |
| 서버와 파일이 묶임 | 서버 교체·이전에 파일 이사가 따라붙는다. 앱을 2대로 늘리면 파일 동기화 문제가 생긴다 | 앱은 주소와 키만 안다. 서버 교체·증설·컨테이너 전환이 파일과 무관해진다 |
| 백업이 서버별 제각각 | 어떤 파일이 어디 있고 무엇이 백업되는지 전체 그림이 없다 | 버킷 단위 정책 하나로 백업·복제·수명주기를 관리한다 |
| 접근 통제 없음 | 서버에 들어가면 다 보인다 | 서비스별 access key + 버킷 정책으로 자기 버킷만 접근한다. Kafka의 계정·ACL 모델과 같다 |
| 용량 관리 분산 | 서버마다 여유 공간을 각자 확보해 빈 공간이 흩어진다 | 한 곳에서 용량을 본다 |
| 대용량 전송이 앱 서버를 거침 | 다운로드가 몰리면 앱 서버 대역폭이 잡힌다 | 임시 URL(presigned URL)로 클라이언트가 MinIO와 직접 주고받는다. 앱 서버는 권한 확인만 한다 |
| 저장소 종속 | NAS 벤더·프로토콜에 묶인다 | S3 표준이라 AWS S3나 다른 호환 저장소로 옮겨도 앱은 주소와 키만 바뀐다 |

### NAS와 비교하면

이미 NAS(NFS·SMB 마운트)를 쓰고 있다면 "서버와 파일이 묶임", "백업 제각각"은 NAS도 해결합니다. 그 경우 MinIO의 차이는 저장 확인·삭제 복구·접근 통제·직접 전송·S3 표준으로 좁혀집니다. 현재 파일 서비스는 저장 확인과 삭제 복구가 안 되므로, NAS 여부와 관계없이 도입 근거가 성립합니다.

### 옮기지 않는 것이 나은 경우

- 앱 서버가 1대이고 늘릴 계획이 없으며, 저장 확인·삭제 복구가 문제된 적이 없다.
- 파일이 적고 작아 백업·용량이 문제된 적이 없다.
- 모든 요청이 파일을 거치는 실시간 경로라 지연 시간이 중요하다. 이때 MinIO를 쓰려면 처음부터 분산 구성이 필요하다.

### 도입 논리

"파일 서비스를 위해 MinIO를 도입한다"가 아니라 다음 순서로 씁니다.

1. 파일 서비스는 지금 저장 확인과 삭제 복구가 안 된다.
2. MinIO는 체크섬 검증·버저닝·감사 로그로 이 둘을 해결한다.
3. [Lakehouse](../../lakehouse/README.md) 저장층으로 MinIO를 세우므로, 파일 서비스는 `files` 버킷 하나를 추가해 같은 인스턴스를 쓴다. 저장소 종류가 하나 줄어든다.

파일 서비스가 더 급하면 먼저 옮겨도 됩니다. 어느 쪽이든 MinIO 인스턴스는 하나입니다. 이전 절차는 [04 기존 파일 애플리케이션 이전](04-file-app-migration.md)에 있습니다. 옮길 때 세 가지를 챙깁니다.

- `files` 버킷을 만들 때 **버저닝을 처음부터** 켠다. 나중에 켜면 그 전 파일은 보호되지 않는다.
- 업로드 코드에서 SDK의 체크섬 검증을 켜고, 응답 ETag를 DB의 파일 메타데이터에 함께 저장한다. 나중에 "이 파일이 그 파일이 맞나"를 대조할 근거가 된다.
- 기존 파일은 복사 후 해시 대조로 검증하고 나서 원본을 정리한다. 지금 파일이 이미 일부 깨져 있다면 이 단계에서 드러난다.

MinIO 도입으로 얻는 것을 정리하면:

- **저장 신뢰성** — 체크섬 검증, 버저닝, 감사 로그, Object Lock
- **중앙화 + 표준 API** — 앱 서버가 파일 없는(stateless) 서버가 되어 자유롭게 교체·증설 가능
- **거버넌스** — 서비스별 access key + 버킷 정책으로 자기 버킷만 접근, 수명주기 규칙으로 자동 정리
- **운영 통합** — Prometheus 메트릭 내장으로 기존 모니터링 스택에 그대로 편입

## 3. 저장은 멍청하게, 의미는 위층에서

MinIO는 내용물이 뭔지 모릅니다 — PDF든, DB에서 내린 Parquet 데이터 파일이든 똑같은 오브젝트입니다. 의미는 위층이 부여합니다:

| 용도 | MinIO에 저장되는 것 | 의미를 부여하는 층 |
| --- | --- | --- |
| 파일 저장소 | PDF·이미지 그 자체 | 앱이 키(경로)로 직접 넣고 꺼냄 |
| DB 콜드 데이터 | Parquet 파일 + Iceberg 메타 파일 | Iceberg가 "테이블"로 해석, Trino가 SQL로 조회 |

Kafka 브로커가 메시지를 바이트로만 나르고 의미는 스키마가 부여하는 것과 같은 구도입니다. 이 성질 덕분에 **파일 저장소로 도입한 인스턴스가 나중에 데이터 분석 기반(레이크하우스)의 저장층을 겸할 수 있습니다** — [05 레이크하우스와 DB 콜드 데이터](05-lakehouse-and-cold-data.md) 참고.

## 4. 도입 검토 항목

- **라이선스** — MinIO 커뮤니티판은 AGPLv3이며, 최근 신기능이 상용판(AIStor) 중심으로 재편되어 커뮤니티판은 보안 패치 위주로 유지되는 흐름입니다. MinIO를 수정·재배포하지 않고 API로만 쓰는 일반적 사내 사용에선 보통 문제가 없지만, 법무 정책 확인과 장기 유지보수 리스크(대안: Ceph RGW, SeaweedFS, Garage 등) 검토 항목을 도입 문서에 남겨둡니다.
- **파일 저장소 특성** — 잠깐 못 읽어도 서비스 전체가 죽지 않는 데이터(첨부·문서·리포트)에 적합. 모든 요청이 파일을 거치는 실시간 경로라면 처음부터 분산 구성(HA)을 검토해야 합니다 — [02 배포 형태](02-deployment-topology.md).
