# 레이크하우스와 DB 콜드 데이터

> 파일 저장소로 도입한 MinIO는 나중에 **데이터 분석 기반(레이크하우스)의 저장층**을 겸할 수 있습니다. MinIO(저장) + Iceberg(테이블 구조) + Trino(SQL 계산)의 3층 구조이며, 지금의 도입 결정에서 버려지는 투자가 없습니다.

## 1. 세 층이 맞물리는 구조

```text
                          ┌── 카탈로그 (숨은 4번째 조각) ───┐
                          │ "어떤 테이블이 어디 있나"의 장부   │
                          └──────────△────────────────────┘
                                     │ 테이블 메타 조회
┌─ Trino ────────────┐               │
│ SQL 쿼리 엔진        │──────────────┘
│ (계산만, 저장 안 함)  │──── S3 API 로 파일 읽기 ────┐
└────────────────────┘                            ▽
┌─ Iceberg — 테이블 포맷 (규약, 설치할 프로세스 없음) ────────┐
│ 스키마·파티션·스냅샷 메타데이터로 "파일 무더기 = 테이블"     │
└────────────────────────────────────────────────────────┘
┌─ MinIO — Parquet 데이터 파일 + 메타 파일 보관 (S3 API) ──┐
└────────────────────────────────────────────────────────┘
```

- 역할 분리: **MinIO는 저장, Iceberg는 구조, Trino는 계산.**
- 실제로 띄우는 프로세스는 MinIO + Trino + **카탈로그**(Iceberg REST 카탈로그 또는 PostgreSQL 기반 JDBC 카탈로그 — 컨테이너 1개면 충분, Hive Metastore 불필요).
- Kafka와의 연결: `서비스 → Kafka → (Kafka Connect Iceberg Sink) → Iceberg 테이블 → Trino`. Kafka는 보존 기간이 지나면 지우므로, 이벤트의 영구 보관·분석처가 이 층입니다.

## 2. RDB 콜드 데이터 아카이빙

운영 DB의 오래된 행을 Iceberg 테이블로 내리고 DB에서 지워서, **DB는 가볍게 유지하면서 옛 데이터는 SQL로 계속 조회**하는 패턴입니다.

**방법 ① 배치 아카이빙 (권장 시작점)** — Trino가 JDBC 커넥터로 RDB도 읽을 수 있어, 이전이 SQL 한 문장입니다:

```sql
-- 2년 지난 주문을 Iceberg 로 복사
INSERT INTO iceberg.archive.orders
SELECT * FROM mysql.commerce.orders WHERE created_at < date '2024-09-01';
-- 검증 후 RDB 에서 삭제 (파티션 테이블이면 DROP PARTITION 이 깔끔)
```

**방법 ② CDC 경유** — Debezium → Kafka → Iceberg Sink로 전체 변경 이력을 상시 복제. 구성 요소가 많으므로 ①로 시작해 발전시킵니다.

얻는 것: RDB 다이어트(쿼리·백업 부담 감소), 저렴한 보관, 옛 데이터도 표준 SQL 유지(Trino 연합 쿼리로 핫 RDB + 콜드 Iceberg를 UNION한 전 기간 조회 가능), 법정 보관 의무 충족.

**제약 — 콜드로 내린 데이터는 분석·조회용이지 운영 트랜잭션용이 아닙니다:**

- 단건 조회도 수백 ms~초 단위 — 화면 실시간 응답 부적합. "고객이 5년 전 주문을 화면에서 봐야 한다"면 그 경로는 별도 설계 필요
- 행 수정·삭제는 가끔(개인정보 파기 수준)만 — OLTP처럼 쓰지 않음
- 아카이빙 배치는 **"복사 검증 후 삭제"** 순서 강제

## 3. 버킷 분리

한 MinIO 안에서 용도를 버킷으로 나누고 접근 주체를 분리합니다:

```text
MinIO
├─ notification-attachments/   ← 파일 저장소 (해당 서비스 키만)
├─ report-files/               ← 파일 저장소
└─ lakehouse/                  ← Iceberg 전용 (Trino·적재 파이프라인 키만)
    └─ archive/orders/…parquet
```

## 4. 도입 순서와 현실 체크

권장 순서: **① MinIO 파일 저장소 구축 → ② Kafka Connect 안정화 → ③ 분석 수요가 확인되면 카탈로그 + Trino (+ Iceberg Sink) 추가.**

- **Trino가 이 스택의 대식가** — 최소 구성도 힙 8~16GB, 데이터가 커지면 워커 증설 필요. MinIO·카탈로그는 가볍습니다.
- 스트리밍 적재 시 작은 파일이 쌓여 **주기적 컴팩션** 관리가 따라옵니다.
- 분석 용도가 붙으면 용량 성장 속도가 파일 저장소와 차원이 다르므로(수백 GB~TB) 그 시점에 디스크 증설 계획을 다시 잡습니다.

관련: 온도별 데이터 배치 — 핫(운영 RDB) / 웜(Kafka, 보존 기간 내 이벤트) / 콜드(MinIO+Iceberg, 영구 보관·분석). "오래된 콜드 데이터 관리"의 담당은 이 조합이며, ScyllaDB 같은 고성능 NoSQL은 반대편(핫·실시간)의 도구입니다.
