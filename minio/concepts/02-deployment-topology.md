# 배포 형태와 서버 스펙

> 배포 형태가 서버·디스크 요구를 결정하는 첫 갈림길입니다. 핵심 질문은 두 가지 — "서버 장애 시 무중단이 필요한가", 그리고 "물리 서버인가 VM인가".

## 1. 배포 형태 3종

| 형태 | 구성 | 장애 내성 | 어울리는 용도 |
| --- | --- | --- | --- |
| SNSD (단일 노드 단일 드라이브) | 서버 1대, 디스크 1개 | 자체 보호 없음 | 개발·검증, 또는 하부 스토리지가 이중화된 VM |
| SNMD (단일 노드 다중 드라이브) | 서버 1대, 디스크 4개+ | **디스크** 장애만 견딤 (이레이저 코딩) | 물리 서버 1대의 소규모 운영 |
| MNMD (다중 노드 분산) | **서버 4대+**, 각 디스크 여러 개 | 서버 장애도 견딤 | 운영 HA |

- Kafka는 3대로 HA가 되지만 **MinIO의 운영급 HA는 4노드 이상**이 권장선입니다(이레이저 코딩 패리티 구조).
- 이레이저 코딩: 오브젝트를 조각+패리티로 나눠 디스크들에 분산. 디스크 4개(기본 EC:2)면 2개까지 고장을 견디는 대신 **사용 가능 용량 = 원시 용량의 절반**.

## 2. 물리 서버 vs VM — 디스크 독립성이 판단 기준

SNMD의 "디스크 4개"는 **물리적으로 독립된 드라이브 4개**를 전제로 합니다. 보호의 근거가 "디스크들이 서로 독립적으로 고장 난다"이기 때문입니다.

| 상황 | 판단 |
| --- | --- |
| 물리 서버 + 물리 SSD 4장 | SNMD 의도대로 동작 |
| 큰 SSD 1장을 파티션 4개로 분할 | **의미 없음** — 그 SSD가 죽으면 4개가 동시에 죽음. 용량만 절반 손해 |
| VM + 가상디스크 4개가 같은 물리 디스크 위 | 위와 동일 — 보호 없음 |
| VM + 하부 데이터스토어가 RAID/SAN/vSAN으로 이중화 | 디스크 보호는 하부가 담당 → **SNSD(가상디스크 1개) + 백업**이 실용적. 이레이저 코딩 이중 적용은 용량만 낭비 |

**VM으로 갈 때 인프라팀에 확인할 질문 한 가지**: "이 VM의 데이터스토어가 물리 디스크 장애에 대해 이중화되어 있나요?" — 사내 가상화 환경은 거의 예외 없이 "네"이며, 그 경우 SNSD로 구성합니다. "이중화 없음"이라면 백업 주기를 짧게 잡고 이중화된 데이터스토어로의 이전을 우선 요청합니다.

## 3. "1대 + 백업" 구조의 의미

단일 노드 구성은 두 겹의 보호를 서로 다른 장애에 대응시킵니다:

| 장애 | 결과 |
| --- | --- |
| 디스크 고장 | SNMD면 무중단(이레이저 코딩), VM-SNSD면 하부 스토리지가 흡수 |
| 서버/VM 전체 장애 | **중단** — 백업에서 복구. 마지막 백업 이후분은 유실(백업 주기 = 허용 유실 시간) |
| 삭제 실수·랜섬웨어 | 버저닝(1차) + 백업(2차)으로 복구 |

MNMD(4노드)와의 차이는 "서버 장애 시 무중단이냐, 복구 시간이 걸리냐"입니다. 첨부파일·문서·리포트처럼 잠시 못 읽어도 되는 데이터라면 1대 + 백업으로 시작하는 것이 현실적입니다.

## 4. 서버 스펙 — 공식 기준과 소규모 현실

MinIO 공식 하드웨어 체크리스트의 핵심은 **메모리를 저장 용량에 비례**해 잡는 것입니다:

| 호스트 총 스토리지 | 권장 메모리 |
| --- | --- |
| 1TB 이하 | 8GB |
| 10TB 이하 | 16GB |
| 100TB 이하 | 32GB |
| 1PB 이하 | 64GB |

그 외 공식 권장(베어메탈 8~16코어+, 25GbE~, NVMe)은 대규모·AI 클러스터 기준이라 사내 파일 저장소 규모에는 과합니다. MinIO는 CPU·RAM보다 **네트워크·디스크 I/O가 병목**입니다.

**사내 파일 저장소(수 TB 이하) 기준 권장:**

| 항목 | 권장 | 근거 |
| --- | --- | --- |
| CPU | 4~8코어 | I/O 중심. TLS·이레이저 코딩 해시 연산 몫이면 충분 |
| 메모리 | 16GB (여유 시 32GB) | 공식 용량표 ≤10TB 구간 |
| 디스크 | XFS 필수, SSD 권장 | HDD는 동시 사용자 적고 순차 위주일 때만 타협 |
| OS 디스크 | 데이터와 분리 | 공식 권장 |
| 네트워크 | 1GbE 시작 가능, 10GbE 여유 | 1GbE = 초당 약 125MB 상한 |

## 5. 용량 산정

- **SNMD(디스크 4, EC:2)**: 사용 가능 = 원시 × 1/2. 예: 1TB×4 → 사용 가능 약 2TB.
- **SNSD**: 사용 가능 = 원시 그대로.
- 산정 시 반영할 것: 현재 사용량 → **버저닝 오버헤드 +20~50%**(수명주기 규칙으로 통제) → 성장 여유 → **사용률 70%를 증설 준비선**으로.
- 예: 현재 400GB 사용이면 — SNMD는 1TB×4(시작 사용률 20%), VM-SNSD는 가상디스크 1TB(시작 40%, 가상디스크는 온라인 확장 가능하므로 과하게 잡지 않아도 됨).
- SNMD 디스크는 **반드시 같은 용량으로** — 풀 안에서 가장 작은 디스크 기준으로 전체가 취급됩니다.
