01 · Docker와의 대응

Docker 용어와 쿠버네티스 용어

Docker쿠버네티스차이

02 · 클러스터 구성

클러스터, 노드, 컨트롤 플레인

클러스터는 여러 서버(노드)를 하나의 실행 환경으로 묶은 단위. 컨트롤 플레인이 결정하고 각 노드가 실행

용어정의
노드 (Node)컨테이너가 실제로 실행되는 서버 1대
kube-apiserver모든 요청의 입구. kubectl, Rancher 모두 이곳에 요청
etcd클러스터 상태를 저장하는 DB. 과반 합의로 홀수 대 운영
scheduler새 Pod를 어느 노드에 둘지 결정
controller-manager선언한 상태와 실제 상태를 맞추는 반복 작업 수행
kubelet각 노드에서 Pod를 실제로 띄우고 상태 보고
containerd컨테이너 런타임. Docker 엔진 대신 사용
03 · 동작 방식

선언형 동작 방식과 매니페스트

"컨테이너를 띄워라"가 아니라 "이 상태여야 한다"를 저장. 컨트롤러가 실제 상태를 계속 그쪽으로 맞춤

용어정의
리소스 (Resource)API로 관리하는 대상 하나. Pod, Service, Deployment 등
매니페스트리소스의 원하는 상태를 적은 YAML 파일
spec / statusspec은 원하는 상태, status는 현재 상태
컨트롤러spec과 status의 차이를 감지해 메우는 반복 작업
kubectlapiserver에 요청을 보내는 명령줄 도구
Pod를 직접 지워도 다시 생기는 이유: Deployment의 spec(replicas 2)과 실제(1)가 달라 컨트롤러가 새 Pod 생성
apiVersion: apps/v1          # API 그룹과 버전
kind: Deployment             # 리소스 종류
metadata:
  name: was-order            # 이름
  namespace: webwas          # 소속 네임스페이스
  labels:
    app: was-order           # 분류용 라벨
spec:                        # 원하는 상태
  replicas: 2
  selector:
    matchLabels:
      app: was-order
  template:                  # 만들 Pod의 틀
    metadata:
      labels:
        app: was-order
    spec:
      containers:
        - name: was
          image: <NEXUS>:5000/was-order:1.0.58
04 · 워크로드

Pod

쿠버네티스가 배치하는 최소 단위. 컨테이너 1개 이상과 네트워크·저장공간을 함께 묶은 실행 단위

특징

  • IPPod마다 고유 IP. 다시 만들어지면 IP 변경
  • 일회성죽으면 고치지 않고 새 Pod로 교체. 이름도 바뀜
  • 공유같은 Pod의 컨테이너는 localhost와 볼륨을 공유
  • 직접 생성 안 함보통 Deployment가 대신 생성·관리
Pod IP가 계속 바뀌기 때문에 다른 앱은 Pod가 아니라 Service 이름으로 접속
관련 용어정의
컨테이너이미지로 실행한 프로세스. Pod 안에 위치
사이드카본 컨테이너를 돕는 같은 Pod의 보조 컨테이너. 로그 전송 등
init 컨테이너본 컨테이너보다 먼저 실행되고 끝나는 준비 작업
이미지컨테이너 실행 파일 묶음. 레지스트리(Nexus)에 보관
imagePullPolicy이미지를 언제 다시 받을지. 태그 고정 시 IfNotPresent
05 · 워크로드

Deployment와 ReplicaSet

Deployment는 앱의 버전과 개수를 관리하고, ReplicaSet은 특정 버전의 Pod 개수를 유지

용어정의
Deployment앱 하나의 원하는 상태(이미지, 개수, 교체 방식) 선언
ReplicaSet같은 Pod 틀로 정해진 개수를 유지. 버전마다 하나씩 생성
replicas유지할 Pod 개수
rollout새 버전으로 교체하는 진행 과정
RollingUpdate새 Pod를 추가하고 준비되면 기존 Pod를 줄이는 기본 교체 방식
revision교체 이력 번호. 이전 ReplicaSet이 0개로 남아 롤백 대상
06 · 워크로드

그 밖의 워크로드 종류

Pod를 어떤 규칙으로 띄우는지에 따라 리소스 종류가 나뉨

종류규칙예시
Deployment개수만 맞추면 되는 동일한 복제본web-portal, was-order
DaemonSet노드마다 1개씩Traefik(RKE2), MetalLB speaker, 로그 수집기
StatefulSet순서와 고정 이름(db-0, db-1), Pod별 디스크DB, Kafka 같은 상태 보존 서비스
Job끝날 때까지 1회 실행. 실패 시 재시도데이터 이관, Helm 설치 Job(helm-install-rke2-traefik)
CronJob정해진 일정마다 Job 생성야간 배치, 정리 작업
static Podapiserver가 아닌 노드 파일로 kubelet이 직접 실행RKE2의 etcd, kube-apiserver
Deployment의 Pod는 구별되지 않는 복제본. 특정 Pod 하나만 내리는 개념이 없고, 지우면 바로 새 Pod 생성
07 · 상태 확인

Probe: 살아 있는지, 받을 준비가 됐는지

kubelet이 컨테이너 상태를 주기적으로 검사하는 규칙. 종류마다 실패 시 동작이 다름

검사 방법

  • httpGet지정 경로가 200~399 응답이면 성공
  • tcpSocket포트가 열려 있으면 성공
  • exec명령의 종료 코드가 0이면 성공
tcpSocket은 앱 초기화 완료 여부를 모름. 가능하면 앱의 헬스 엔드포인트를 httpGet으로 검사
종류질문실패 시
startup기동이 끝났는가통과 전까지 나머지 검사 보류. 제한 시간 초과 시 재시작
readiness요청을 받아도 되는가Service 대상에서 제외. 재시작하지 않음
liveness멈추지 않고 살아 있는가컨테이너 재시작

예: WAS는 Spring 기동이 길어 startupProbe로 최대 3분(5초 × 36) 대기

07 · 상태 확인

자원: requests, limits, QoS

스케줄러는 실제 사용량이 아니라 requests 합계로 배치를 결정. limits는 넘을 수 없는 상한

용어정의
requests보장받을 최소량. 노드 합계가 차면 새 Pod는 Pending
limits상한. 메모리 초과 시 OOMKilled, CPU 초과 시 지연
m (밀리코어)CPU 단위. 250m = 0.25 코어
Mi, Gi메모리 단위. 1Mi = 1024 × 1024 바이트
OOMKilled메모리 limit을 넘어 커널이 강제 종료한 상태

QoS 등급

등급조건
Guaranteedrequests = limits
Burstablerequests < limits
BestEffort둘 다 없음. 자원 부족 시 가장 먼저 퇴출
JVM은 힙을 limit의 75%로 제한(MaxRAMPercentage=75)해 OOMKilled 여유 확보
08 · 네트워크

Service와 Endpoints

Service는 바뀌는 Pod들 앞에 고정된 이름과 IP를 두는 리소스. 라벨로 대상 Pod를 고름

용어정의
selector대상 Pod를 고르는 라벨 조건
Endpointsselector에 맞고 readiness를 통과한 Pod IP 목록
ClusterIP클러스터 안에서만 쓰는 가상 IP. 기본 타입
NodePort모든 노드의 같은 포트(30000~32767)로 노출
LoadBalancer외부 IP를 받아 노출. 온프레미스는 MetalLB가 IP 제공

Service 이름 해석

was-order                               # 같은 네임스페이스
was-order.webwas                        # 다른 네임스페이스
was-order.webwas.svc.cluster.local      # 전체 이름(FQDN)
  • CoreDNS가 Service 이름을 ClusterIP로 응답
  • nginx 변수 proxy_pass는 짧은 이름을 못 풀어 FQDN 필요
  • Service에는 Pod IP가 아닌 이름으로 접속

Ingress와 Ingress Controller

Ingress는 "이 도메인·경로는 이 Service로" 규칙. 규칙을 실제로 처리하는 프로그램이 Ingress Controller

용어정의
Ingress도메인·경로별 라우팅 규칙. 앱 차트에 포함
Ingress Controller규칙을 읽어 요청을 전달하는 프록시. RKE2 1.36은 Traefik
IngressClass어느 컨트롤러가 처리할지 지정. traefik (default)
TLS Secret인증서와 개인키를 담은 Secret. Traefik 기본 인증서로 등록
hostPort노드의 포트를 Pod 포트에 직접 연결. MGMT Traefik 방식

11 · 구분과 설정

Namespace, Label, Annotation

리소스를 나누고(Namespace), 고르고(Label), 부가 정보를 붙이는(Annotation) 방법

용어정의
Namespace클러스터 안의 논리 구획. 이름 중복 허용, 권한·쿼터 단위
Label리소스에 붙이는 키·값 표식. selector의 검색 대상
selector라벨 조건으로 리소스를 고르는 식
Annotation검색에 쓰지 않는 부가 정보. 도구 설정 전달용
Helm release는 네임스페이스 이동 불가. 앱 네임스페이스를 먼저 정하고 설치

예시

metadata:
  namespace: webwas
  labels:
    app.kubernetes.io/name: web-portal
    app.kubernetes.io/version: 1.0.41
  annotations:
    metallb.io/loadBalancerIPs: <DEV VIP>
  • kube-system: 클러스터 시스템 구성요소
  • cattle-system: Rancher와 에이전트
12 · 구분과 설정

ConfigMap, Secret, 환경변수

설정값을 이미지 밖에 두는 리소스. 같은 이미지를 환경마다 다른 값으로 실행

용어정의
ConfigMap일반 설정값 묶음. 환경변수나 파일로 주입
Secret비밀번호·키·인증서 묶음. base64 저장, 접근 권한 분리
env컨테이너 환경변수. 직접 값 또는 ConfigMap·Secret 참조
hostAliasesPod의 /etc/hosts에 이름·IP 추가
imagePullSecret비공개 레지스트리 인증 정보. RKE2는 registries.yaml로 대체 가능
  • base64는 암호화 아님Secret을 읽을 권한이 있으면 원문 확인 가능. 권한 관리가 핵심
  • Spring 연결txm.url → TXM_URL처럼 환경변수로 application.yml 값 대체
  • 변경 반영환경변수로 주입한 값은 Pod 재시작 후 반영
개인키를 Rancher Additional Manifest에 넣으면 클러스터 설정에 평문으로 남음. Secret은 kubectl create secret으로 생성
13 · 저장공간

Volume, PV, PVC, StorageClass

Pod는 일회성이라 컨테이너 안 파일은 교체 시 사라짐. 남겨야 할 데이터는 볼륨에 저장

용어정의
VolumePod에 붙이는 저장공간
emptyDirPod와 수명이 같은 임시 공간. Pod 삭제 시 함께 삭제
PVPersistentVolume. 실제 스토리지 조각
PVCPersistentVolumeClaim. Pod가 "이만큼 필요"라고 요청하는 신청서
StorageClassPVC 요청 시 PV를 자동으로 만드는 방식 정의
 
Pod ─ volumeMounts ─▶ PVC (10Gi 요청)
                          │  StorageClass가 자동 생성
                          ▼
                         PV ─▶ Longhorn / NFS
  • RKE2에는 기본 StorageClass 없음. Longhorn이나 NFS 별도 구성
  • 현재 WAS 로그(/app/logs)는 emptyDir. 장기 보관은 로그 수집으로 해결

15 · 도구

Helm 용어

Helm은 쿠버네티스용 패키지 관리자. 매니페스트 묶음을 버전 단위로 설치·업그레이드·롤백

용어정의
Chart템플릿과 기본값을 묶은 패키지 (.tgz)
values템플릿 빈칸에 넣을 값
Release차트를 클러스터에 설치한 실체 하나
revision설치·업그레이드·롤백마다 1씩 증가하는 이력
Repository차트와 index.yaml 보관소. Nexus helm hosted
version / appVersion차트 버전 / 앱 버전. 이번 구축에서는 동일 값
 
Chart + values ─▶ 렌더링된 YAML ─▶ Release
                                      revision 1, 2, 3 ...
  • 롤백도 새 revision. 3에서 1로 롤백하면 4가 생성
  • revision 기록은 네임스페이스의 Secret(sh.helm.release.v1.*)에 저장
  • Rancher Apps 화면은 Helm 명령의 화면판
16 · 도구

RKE2와 Rancher 용어

이번 구축에서 쓰는 배포판과 관리 도구에 등장하는 용어

용어정의
RKE2Rancher가 만든 온프레미스용 Kubernetes 배포판. systemd 서비스로 설치
server / agent 노드server는 컨트롤 플레인 포함, agent는 워크로드만 실행

자주 보는 Pod 상태와 첫 확인

상태값마다 원인 범위가 다름. 첫 확인은 대부분 describe의 Events와 logs

상태의미첫 확인
Pending배치할 노드 없음. 자원 부족, PVC 미연결kubectl describe pod Events
ContainerCreating이미지 다운로드·볼륨 연결 중몇 분 이상이면 Events
ImagePullBackOff이미지를 받지 못함. 태그 오타, 인증, 방화벽Events의 pull 오류 메시지
CrashLoopBackOff기동 직후 종료를 반복. 설정 누락, 외부 접속 실패kubectl logs --previous
OOMKilled메모리 limit 초과로 강제 종료describe의 Last State, limits 조정
Running · 0/1 Ready실행 중이지만 readiness 실패. 트래픽 제외 상태probe 설정과 앱 로그
Terminating종료 진행 중. 오래 남으면 finalizer나 노드 문제kubectl get pod -o yaml
