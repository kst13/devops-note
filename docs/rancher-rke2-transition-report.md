# 배포 방식 전환 보고: Jenkins 스크립트 배포 → Rancher + RKE2

- 작성일: 2026-10-23
- 대상: 사내 웹/WAS 애플리케이션 배포 체계
- 현황 (2026-10-25 갱신): 실서버 관리 클러스터 3대와 Rancher 설치 완료(10-19~20). 개발 클러스터 3대를 Rancher로 생성(10-21)하고 웹·WAS 앱 배포 확인(10-23)

## 1. 전환 요약

| 구분 | 기존 (Jenkins 스크립트) | 변경 (Rancher + RKE2) |
| --- | --- | --- |
| 빌드 산출물 | jar/war 파일을 서버로 복사 | Docker 이미지와 Helm 차트를 Nexus에 push |
| 배포 실행 | Jenkins가 서버에 SSH 접속 후 `docker stop && rm && run` | Rancher 화면에서 버전 선택 후 Install/Upgrade |
| 배포 주체 | Jenkins가 운영 서버에 직접 접근 | Jenkins는 빌드·push까지. 실행은 Rancher |
| 서버 배치 | 앱별 서버·포트를 사람이 지정 | 클러스터가 여유 있는 노드에 자동 배치 |
| 롤백 | 이전 파일을 찾아 스크립트 재실행 | Rollback 버튼으로 이전 버전 선택 |
| 장애 시 | 사람이 발견해 수동 재기동 | 헬스체크 실패 시 자동 재시작, 노드 장애 시 다른 노드로 이동 |

Jenkins 빌드 단계는 그대로 유지합니다. 마지막 "복사 + docker run" 단계만 "docker push + helm push"로 바뀝니다.

## 2. 기대 효과

### 2-1. 배포 중단 시간 제거

- 기존 방식은 컨테이너를 멈춘 뒤 새로 띄우는 동안 서비스가 끊깁니다. JVM 기동 시간만큼 매 배포마다 다운타임이 생깁니다.
- 새 방식은 RollingUpdate입니다. 새 Pod가 헬스체크를 통과한 뒤에 옛 Pod를 내리므로 사용자는 끊김을 느끼지 않습니다.
- 새 버전이 기동에 실패하면 옛 버전이 그대로 남습니다. 기존 방식은 실패 시 서비스가 내려간 상태로 멈춥니다.

### 2-2. 화면 선택만으로 끝나는 롤백

- 모든 릴리즈가 Nexus에 버전별로 보관됩니다. 이미지 태그, 차트 버전, Jenkins 빌드 번호가 하나의 번호로 일치합니다.
- Rancher 화면에서 Rollback → 이전 버전 선택으로 끝납니다. 스크립트 수정이나 옛 파일 탐색이 없습니다.
- 기존에는 "어느 서버에 어느 빌드가 있는지"를 사람의 기억과 Jenkins 로그에 의존했습니다.

### 2-3. 자동 복구

- 컨테이너가 죽으면 즉시 재시작됩니다. 서버 한 대가 내려가면 그 위의 앱이 다른 노드에 다시 뜹니다.
- 기존 방식은 같은 서버 안에서만 재시작되고, 서버가 죽으면 사람이 다른 서버에 수동 배포해야 했습니다.
- "프로세스는 떠 있는데 응답은 없는" 상태도 헬스체크로 자동 감지합니다.

### 2-4. 서버 자원 효율

- 기존에는 앱마다 서버와 포트를 지정해 서버 간 부하가 고르지 않았습니다. 포트 충돌을 피하려 앱당 서버를 따로 두기도 했습니다.
- 새 방식은 앱마다 CPU·메모리 요구량을 선언하고, 클러스터가 여유 있는 노드에 배치합니다. 노드 3대를 하나의 자원 풀로 씁니다.
- 노드 추가는 등록 명령 한 줄입니다. 앱 설정을 바꾸지 않아도 새 노드가 배치 대상이 됩니다.
- 복제 수를 숫자 하나로 늘리고 줄입니다. 기존에는 서버 추가와 L4 설정 변경이 필요했습니다.

### 2-5. 빌드와 배포의 분리, 보안 단순화

- Jenkins가 운영 서버에 SSH로 들어가는 구조가 없어집니다. Jenkins는 Nexus에 push만 하고 서버 접근 권한을 갖지 않습니다.
- 방화벽이 단순해집니다. 기존에는 Jenkins → 모든 앱 서버 22번이 필요했고 서버가 늘면 재신청했습니다. 새 방식은 Jenkins → Rancher 443 하나이며, stage·prod 클러스터가 늘어도 재신청이 없습니다.
- 운영 서버에 sudo로 들어가는 일은 설치 때로 한정됩니다. 일상 배포·로그·재시작은 Rancher 화면과 kubectl로 하고, 작업 이력이 Rancher에 남습니다.

### 2-6. 배포 규격의 표준화

- 포트, 환경변수, 자원, 헬스체크, 복제 수가 Helm 차트 파일로 소스 저장소에 함께 들어갑니다. 배포 방법이 특정 사람의 스크립트나 서버 상태에 묻히지 않습니다.
- 환경별 차이는 값 파일로만 다릅니다. 개발에서 검증한 차트를 stage·prod에 값만 바꿔 그대로 씁니다.
- 새 앱 추가는 차트 복사와 Jenkins Job 하나입니다. 서버 선정, 포트 배정, 스크립트 작성이 없습니다.

### 2-7. 운영 가시성과 권한 위임

- Rancher 화면 하나에서 전 클러스터의 앱 상태, 로그, 이벤트, 자원 사용량을 봅니다. 기존에는 서버마다 접속해 `docker ps`, `docker logs`를 실행했습니다.
- Project 단위 권한으로 개발팀에 자기 앱의 로그 조회·재시작·복제 수 조정만 열어 줄 수 있습니다. 서버 계정을 주지 않아도 됩니다.
- 기동 로그, 재시작 횟수, 배포 이력이 화면에 남아 장애 분석이 빨라집니다.

### 2-8. 서버마다 다른 환경 문제 제거

- 기존에는 jar가 같아도 서버의 JDK, 라이브러리, 설정 파일 차이로 "이 서버에서만 안 되는" 문제가 있었습니다.
- 이미지는 OS 라이브러리부터 앱까지 한 덩어리로 빌드되어 어느 노드에서나 같은 환경으로 실행됩니다. 개발에서 테스트한 이미지가 그대로 운영에 올라갑니다.

## 4. 현재 진행 상태와 다음 단계

| 단계 | 상태 |
| --- | --- |
| 로컬 실습: Jenkins → Nexus → Rancher → 클러스터 배포 | 완료 (web-portal 배포·버전 확인) |
| 실서버 OS 준비 (관리 3대, 개발 3대) | 완료 |
| 인프라 요청 (방화벽, L4, DNS, NetworkManager) | 완료. Docker Hub CDN·quay CDN 허용은 추가 신청 진행 |
| 관리 클러스터·Rancher 설치 | 완료 (RKE2 v1.36.4, Rancher 2.15.2, 3대 이중화) |
| 개발 클러스터 등록 | 완료 (RKE2 v1.36.5, MetalLB VIP, Traefik, 와일드카드 인증서) |
| 웹·WAS 앱 배포 | 완료 (Rancher Apps로 설치·업그레이드 확인) |

## 5. 한 줄 요약

Jenkins가 서버에 들어가 컨테이너를 교체하던 방식에서, Jenkins는 산출물을 저장소에 올리고 Rancher가 클러스터에 배포·복구·롤백을 책임지는 방식으로 바꿉니다. 배포 중단과 수동 복구가 없어지고, 서버를 공용 자원 풀로 쓰게 됩니다.
