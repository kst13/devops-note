02 · 최종 구성

최종 구성도

MGMT 앞에는 인프라팀 L4, DEV 앞에는 MetalLB VIP. 모든 노드 에이전트는 Rancher 443으로만 접속

  • MGMTL4가 443을 노드 3대로 분산. Traefik이 TLS를 처리하고 Rancher로 전달
  • DEVMetalLB가 VIP를 노드 한 대에 붙이고, Traefik이 도메인별로 앱에 분배
  • NexusDEV 노드는 5000에서 이미지를, MGMT의 Rancher는 8081에서 차트 목록을 받음
  • JenkinsNexus push까지만 수행. 클러스터 접근 없음
Rancher → 노드 방향 접속 경로 없음. 방화벽은 노드 → Rancher 443 단방향

05 · RKE2 설치

MGMT RKE2 설치: tar 반입

온라인 설치가 rpm.rancher.io 차단으로 실패. PC에서 받은 tar 묶음을 SSH로 옮겨 3대 설치

설치 순서

  1. 1PC에서 바이너리·이미지 묶음·체크섬·설치 스크립트 다운로드 후 scp
  2. 2체크섬 확인, 이미지 묶음을 agent/images/에 배치
  3. 3토큰을 root 전용 파일로 생성, config에는 token-file만 기재
  4. 4sudo env INSTALL_RKE2_METHOD=tar ... sh install.sh
  5. 5MGMT-1 Ready 확인 후 MGMT-2, 3 순서로 조인

설치 중 막힌 지점

  • SSH 끊김차단된 EPEL로 dnf 실패, || exit 1이 셸 종료
  • 환경변수 유실VAR=값 sudo sh 형태는 sudo 정책에 따라 변수 누락. sudo env로 변경
  • YAML 깨짐붙여 넣기 시 들여쓰기 추가로 Traefik 설정 ParseManifestFailed. cat -A로 확인
  • kubeconfig0640으로는 일반 계정 접근 불가. 0600 원본 + 계정별 복사본
L4 443만으로는 조인 불가. 9345 listener가 없어 MGMT-1 IP로 직접 조인
05 · RKE2 설치

노드 이름 사고와 재조인

MGMT-1 config를 복사하며 node-name, node-ip 누락. MGMT-2가 OS hostname으로 조인

증상kubectl get nodes에 mgmt-2 대신 OS hostname 표시
원인노드 이름이 etcd 멤버 이름과 kubelet 인증서에 기록. config 수정과 재시작으로 변경 불가
조건etcd 3개일 때만 한 대씩 처리. 2개에서 제거하면 과반 상실로 API 정지
보존이미지 묶음, config, 토큰 파일은 삭제하지 않음
config 복사 시 token: 줄을 주석으로 남기면 화면 공유 때 토큰 노출. 노출 시 rke2 token rotate
# MGMT-1: 잘못된 노드 삭제 (etcd 멤버도 제거)
kubectl delete node <잘못된 이름>

# 해당 노드: server 데이터와 노드 인증서만 삭제
sudo systemctl stop rke2-server
sudo /usr/local/bin/rke2-killall.sh
sudo rm -rf /var/lib/rancher/rke2/server \
            /etc/rancher/node

# config.yaml에 node-name, node-ip 추가 후
sudo systemctl start rke2-server

08 · DEV 외부 접속

MetalLB VIP, Traefik, 와일드카드 인증서

L4가 없는 DEV에 VIP 1개를 만들어 Traefik에만 할당. 모든 앱 도메인이 같은 VIP 사용

  • MetalLB L2노드 한 대가 ARP로 VIP에 응답, 장애 시 다른 노드가 인계. autoAssign: false로 Traefik 전용
  • TraefikRancher Edit Config → Additional Manifest에 HelmChartConfig 등록
  • 인증서kube-system TLS Secret을 TLSStore 기본 인증서로 지정. 두 번째 도메인은 certificates 목록 추가, SNI로 선택
RKE2 Traefik 차트의 Service 키는 service.spec.type. service.type은 무시되어 설치 Job 반복 실패, 그동안 Traefik 소멸
apiVersion: helm.cattle.io/v1
kind: HelmChartConfig
metadata:
  name: rke2-traefik
  namespace: kube-system
spec:
  valuesContent: |-
    service:
      annotations:
        metallb.io/loadBalancerIPs: <DEV VIP>
      spec:
        type: LoadBalancer
        externalTrafficPolicy: Local
    tlsStore:
      default:
        defaultCertificate:
          secretName: wildcard-tls

10 · 배포 표준

저장소 표준과 환경 분리

기존 stage·운영 배포에 영향이 없도록 쿠버네티스용 파일은 모두 deploy/k8s/ 아래에 신규 작성

<저장소>/
└── deploy/k8s/
    ├── Dockerfile              # 컨텍스트 = 저장소 루트
    ├── Dockerfile.dockerignore # 이 빌드에만 적용
    ├── Jenkinsfile
    ├── nginx/                  # (웹) 템플릿
    └── chart/
        ├── Chart.yaml
        ├── values.yaml         # profiles, overrides
        └── templates/
  • 루트 Dockerfile, nginx.conf, .dockerignore는 수정하지 않음
  • Jenkins가 values의 environment, builtFor를 채움. 다른 환경으로 설치하면 템플릿 fail로 차단
  • dev 차트 저장소명 helm-hosted는 기존 저장소를 그대로 사용한 결과
브랜치이미지 경로 (같은 docker-hosted)차트 저장소
develop:5000/dev/<그룹>/<앱>helm-hosted
stage:5000/stage/<그룹>/<앱>helm-stage
production:5000/prod/<그룹>/<앱>helm-prod
  • 이미지저장소 하나에서 경로(폴더)로 환경 구분
  • 차트helm hosted는 폴더 없이 index.yaml 하나. 환경별 저장소로 분리, DEV Rancher에는 helm-hosted만 등록
  • 분리 이유빌드 번호가 Job마다 별도라 dev 1.0.5와 stage 1.0.5가 다른 결과물. 같은 저장소면 덮어쓰기 금지로 업로드 실패

WAS 이미지와 차트

Spring Boot jar를 Dockerfile 안에서 빌드하고, docker run 옵션을 차트 values로 이전

JVM과 컨테이너 설정

  • MaxRAMPercentage=75힙을 메모리 limit의 75%로 제한, OOMKilled 여유 확보
  • ExitOnOutOfMemoryError힙 부족 시 즉시 종료, 쿠버네티스가 재기동
  • exec javajava가 PID 1로 SIGTERM 직접 수신, 교체 시 요청 마무리
  • USER 1000root 미사용, /app만 소유권 부여
기존 docker run차트
--add-host db:<IP>hostAliases (Pod /etc/hosts)
-e SPRING_PROFILES_ACTIVEprofiles.<env>.springProfile
application.yml 값 변경env, relaxed binding (a.b-c → A_BC)
-p 9060:9060Service, Ingress 없음
헬스체크tcpSocket, startupProbe 최대 3분
DB·Redis 등 클러스터 밖 호출의 출발지가 DEV 노드 3대로 변경. 첫 기동 CrashLoopBackOff는 방화벽부터 확인

11 · 배포 흐름

롤링 업데이트 진행 순서

Upgrade 시 Deployment가 새 ReplicaSet을 만들고, 새 Pod가 준비된 만큼만 기존 Pod를 줄이는 방식. 준비된 Pod 수가 replicas 아래로 내려가지 않음

  1. 1Rancher Upgrade로 Deployment의 이미지 태그 변경
  2. 2새 ReplicaSet 생성, maxSurge만큼 새 Pod 추가
  3. 3readiness probe 통과 시 Service Endpoints에 등록, Traefik이 트래픽 전달 시작
  4. 4maxUnavailable 범위 안에서 기존 Pod 종료

11 · 배포 흐름

끊김이 생기는 지점과 대응

교체 순서만으로는 무중단이 보장되지 않음. Pod 시작과 종료 두 지점에서 요청이 실패할 수 있음

Pod 종료 시 동시에 일어나는 일

Pod 삭제 결정
 ├─ (가) Endpoints에서 제거
 │      → Traefik 목록 갱신
 └─ (나) preStop → SIGTERM
        → 유예 30초 후 SIGKILL

(나)가 (가)보다 먼저 끝나면
내려간 Pod로 요청 전달 → 502
무중단 여부는 Upgrade 중 0.1초 간격 연속 요청으로 실패 응답 수를 세어 실측 예정
지점문제대응
시작WAS readiness가 tcpSocket 기준. 포트가 열려도 초기화 미완료 가능actuator readiness 같은 HTTP 헬스 체크로 전환 검토
종료 경합Endpoints 제거 전에 프로세스 종료preStop에 수 초 대기를 넣어 제거를 먼저 반영
진행 중 요청SIGTERM 즉시 종료 시 처리 중 요청 실패exec java로 SIGTERM 수신(적용). Spring graceful shutdown 확인 (Boot 3.4부터 기본)
유예 시간긴 요청이 30초 안에 미완료 시 강제 종료terminationGracePeriodSeconds를 preStop + 최장 요청보다 길게

Rancher Apps 배포 규칙

설정 변경은 모두 git과 Jenkins를 거쳐 새 차트 버전으로 반영. Rancher 화면은 버전 선택과 임시 덮어쓰기만 담당

변경 대상작업
소스, Dockerfile, nginx커밋 → Jenkins → Upgrade
백엔드 주소, 도메인, envprofiles 수정 커밋 → Jenkins → Upgrade
긴급 임시 변경Upgrade 화면의 overrides만, 이후 profiles 반영
Pod 수, 일시 정지overrides.replicas로 Upgrade (0 가능)

Scale 버튼 사용 금지

  • 워크로드 화면의 +/− 사용 시 spec.replicas 소유자가 Rancher로 기록
  • 다음 Helm Upgrade가 conflict with "agent" ... .spec.replicas로 실패
  • 복구: Deployment 삭제 후 같은 버전으로 Upgrade (앱 일시 중단)
앱은 반드시 앱 네임스페이스에 설치. Helm release는 네임스페이스 이동 불가
12 · 운영

로그와 노드 자원

컨테이너 로그는 Pod가 있는 노드의 파일로 저장. 수집 서버 구성 전까지는 kubectl·stern으로 조회

로그

  • 위치/var/log/pods/<ns>_<pod>_<uid>/<컨테이너>/0.log
  • 보관파일당 10Mi, 5개. Pod 삭제 시 함께 삭제
  • 조회Rancher kubeconfig로 PC에서 kubectl logs, stern, k9s
  • 수집 계획Rancher Logging(Fluent Bit) → 클러스터 밖 VM의 Loki + Grafana
Loki를 클러스터 밖에 두는 이유: DEV 노드 메모리 여유 부족, 클러스터 장애 시에도 로그 조회 가능

한 노드만 사용률이 높을 때

원인확인
VIP 보유 노드로 요청 집중MetalLB speaker 로그
etcd·controller 리더kubectl -n kube-system get lease
시스템 Pod 편중--field-selector spec.nodeName=

스케줄러는 실사용량이 아닌 requests 합계로 배치. 며칠 운영 후 kubectl top 기준으로 조정
