01 · 추진 배경

추진 배경

데이터가 서비스별 DB에 분산되어 있어 통합 조회 요구가 발생할 때마다 연계 개발이 반복됩니다. 동시에 과거 데이터는 운영 DB에 지속적으로 누적되고 있습니다.

  • 서비스별 데이터 분산. 회원·주문·채팅·결제가 각자의 DB를 가집니다. 한 고객의 전체 모습은 어느 DB에도 없습니다.
  • 반복되는 통합 조회 개발. 마이페이지, 고객센터, 경영 지표가 요구될 때마다 여러 DB를 잇는 API나 배치를 새로 만듭니다. 같은 조인을 팀마다 다시 구현합니다.
  • 과거 데이터 증가. 수년치 이력이 운영 DB에 남아 용량과 조회 성능을 압박합니다. 지우자니 감사·분석에 필요하고, 두자니 서비스가 느려집니다.
통합 조회는 매번 새 프로젝트가 아니라, 한 곳에 모인 데이터를 SQL로 조회하는 일이어야 합니다.
02 · 추진 목표

추진 목표

장기 이력 보관, 운영 DB 부하 경감, 서비스 간 통합 분석의 세 가지를 목표로 설정합니다.

과제현재 문제목표
장기 이력 보관수년치 거래·메시지가 운영 DB에 남아 있습니다. 삭제하면 감사·분석이 막히고, 두면 용량과 백업 시간이 늘어납니다.전체 이력을 Lakehouse에 저장합니다. 운영 DB는 서비스에 필요한 최근 범위만 유지합니다.
운영 DB 부담 완화통계·추출·감사 쿼리가 서비스 DB에서 실행돼 실서비스 응답에 영향을 줍니다. 대량 조회는 야간 배치로 미룹니다.분석·추출 쿼리는 Trino에서 실행합니다. 운영 DB는 업무 처리와 빠른 조회에 집중합니다.
서비스 간 분석DB마다 따로 뽑아 스프레드시트에서 결합합니다. 기준이 팀마다 달라 숫자가 맞지 않습니다.회원·주문·채팅·결제를 한 SQL에서 조인합니다. 지표 정의를 테이블 하나로 통일합니다.
범위에 넣지 않는 것: 실서비스 화면의 실시간 조회 대체, 업무 트랜잭션 처리. 이 둘은 운영 DB의 역할로 남깁니다(4장).
03 · 아키텍처 개요

Lakehouse 아키텍처 개요

객체 저장소 위에 테이블 관리 계층을 두고 SQL 엔진으로 조회하는 3계층 구조입니다. 각 계층은 독립된 제품으로 구성되어 개별 교체가 가능합니다.

Data Lake는 다양한 데이터를 파일로 쌓는 구조입니다. 파일만 쌓으면 다음 질문에 답하기 어렵습니다.

  • 어떤 파일들이 지금의 거래 테이블에 속하는가?
  • 기록하는 중에 조회해도 되는가?
  • 컬럼이 추가되면 기존 파일은 어떻게 읽는가?
  • 수정 전 데이터를 다시 볼 수 있는가?

Lakehouse는 이 질문에 답하는 테이블 포맷(Iceberg)을 파일 저장소 위에 두고, SQL 엔진(Trino)이 그 테이블을 읽게 한 구조입니다.

이번 구축의 목적: Kafka로 수집한 업무 데이터를 MinIO에 지속적으로 보관하고, Iceberg 테이블로 관리하여 Trino에서 통합 조회한다.
04 · 역할 분담

운영 DB와의 역할 분담

업무 처리와 저지연 조회는 운영 DB가, 장기 이력 보관과 분석은 Lakehouse가 담당합니다. 분담 기준은 데이터의 경과 기간이 아니라 조회 요구사항입니다.

데이터 범위서비스에 필요한 최근 범위전체 이력
응답 시간수 ms, 예측 가능수 초 ~ 수 분
반영 시점즉시분 단위 지연 다음 장

04 · 역할 분담 (서비스별)

서비스별 역할 분담

로그인·주문 확정·결제 승인과 같이 즉시성과 정확성이 요구되는 판단은 기존 시스템이 계속 담당합니다. Lakehouse의 반영 지연이 서비스 처리에 영향을 주지 않는 구조입니다.

서비스기존 DB · 서비스 저장소가 담당Lakehouse에서 활용
회원로그인, 현재 회원 정보, 권한, 동의 상태가입·탈퇴 추이, 고객군별 구매 분석
주문주문 생성, 현재 상태, 취소 가능 여부 판단장기 주문 이력, 상품별 판매·취소 분석
결제승인·취소·환불 처리, 중복 결제 방지결제 성공률, 주문과 결제의 불일치 점검
채팅메시지 전송·조회, 읽음 처리, 대화방 권한이용량, 응답 시간, 정책에 따른 장기 이력
파일업로드·다운로드·미리보기·삭제 (저장소만 MinIO로)파일 사용량과 접근 이력 분석 (필요 시)
왼쪽 열의 기능은 이번 구축으로 바뀌지 않습니다. 오른쪽 열은 지금은 여러 DB를 따로 뒤져야 답할 수 있는 질문들입니다.
시간이 지나며 바뀌는 값(회원 등급 등)은 해석을 정해야 합니다. "현재 VIP인 회원의 과거 구매"와 "구매 당시 VIP였던 회원의 구매"는 다른 분석입니다.
04 · 역할 분담 (반영 지연)

반영 지연의 원인과 규모

Lakehouse에 데이터가 늦게 보이는 것은 장애가 아니라 설계입니다. 이벤트를 배치로 묶어 파일로 만들고 테이블에 커밋하는 구조에서 지연은 커밋 주기와 같습니다.

구간소요원인
① 앱 → 운영 DB즉시트랜잭션 커밋. 화면은 여기를 읽으므로 사용자는 지연을 느끼지 않는다
② 앱 → Kafka수십 ms이벤트 발행. 브로커 저장까지 확인(acks=all)
③ Kafka → Iceberg 커밋0 ~ 커밋 주기
(평균 주기의 절반)		Writer가 이벤트를 모았다가 한 번에 Parquet 파일을 만들고 스냅샷을 커밋한다. 이벤트마다 커밋하면 수 KB짜리 파일이 폭발해 조회가 느려지고 메타데이터가 비대해진다. 지연의 대부분이 이 구간
④ 커밋 → 조회 화면0 ~ 갱신 주기대시보드·화면이 다시 조회하는 주기. 즉시 조회하면 0
환경커밋 주기체감 지연파일 생성
PoC (로컬)30초실측 15초 안팎, 최대 45초(화면 갱신 15초 포함)테이블당 2분에 4개
운영 제안1~5분목표 5분 이내 (15장 결정 항목)테이블당 시간당 12~60개 → 일 단위 병합
커밋 주기는 "반영 지연 ↔ 파일 수"의 절충입니다. 짧게 잡으면 빨리 보이지만 작은 파일이 쌓여 조회 성능이 떨어지고 병합 작업이 늘어납니다. 그래서 커밋 주기는 짧게 두고 일 단위 병합(compaction)으로 큰 파일로 합치는 것이 운영 원칙입니다(12장, 부록 E).
05 · 플랫폼 구성

전사 데이터 플랫폼에서의 위치

전사 데이터 플랫폼은 Serving·Lakehouse·Search 3계층으로 구성됩니다. 이 자료는 그중 Lakehouse 계층과 수집 경로만 다룹니다. Serving·Search 계층은 위치만 표시합니다.

계층배치 기준대표 용도
Serving짧고 예측 가능한 응답이 필요한 조회대화방 메시지, 마이페이지 거래 목록
Lakehouse 이번 범위대규모 이력 보관과 SQL 처리전체 거래 분석, 감사 조회, 데이터 추출
Search검색 조건과 관련도 기반 조회메시지 본문, 상품명 검색
  • 세 계층은 같은 Kafka 이벤트를 각자의 Consumer Group으로 읽습니다. 서로의 진행 상태에 영향을 주지 않습니다.
  • Lakehouse에는 처음부터 전체 이력을 쌓습니다. Serving·Search는 각자 필요한 범위만 유지합니다.
  • Serving(ScyllaDB)과 Search(OpenSearch)는 데이터량과 조회 패턴을 확인한 뒤 채택 여부를 정합니다.

06 · 구성 기술 (Parquet)

Parquet — 데이터 파일의 내부 구조

실제 이벤트 데이터가 담기는 파일 형식입니다. 행이 아니라 컬럼 단위로 저장하기 때문에 분석 쿼리가 필요한 컬럼만 읽을 수 있습니다.

행 단위 저장과의 차이

행 단위 (CSV·JSON·RDB 페이지)컬럼 단위 (Parquet)
저장 순서주문1 전체 → 주문2 전체 → …모든 주문의 amount → 모든 주문의 method → …
"금액 합계" 쿼리파일 전체를 읽고 amount 만 골라냄amount 컬럼 덩어리만 읽음. 컬럼 30개 중 2개만 쓰면 I/O 가 그만큼 줄어듦
압축이질적인 값이 섞여 압축률이 낮음같은 타입이 연속돼 압축률이 높음. JSON 대비 보통 3~5배 작음
파일 안 통계없음컬럼별 최소·최대값을 파일 헤더에 기록. 조건에 안 맞는 파일은 열지 않음
단건 조회·수정유리불리. 파일은 만들어지면 수정하지 않음 (append 전용)
Parquet 는 파일 하나 안의 구조를 정합니다. 여러 파일이 하나의 테이블을 이루게 하는 것은 Iceberg 의 일입니다(다음 장). Trino 의 Iceberg 커넥터는 ORC·Avro 도 읽지만 기본은 Parquet 입니다.
PoC 실측: 결제 이벤트 7건이 든 Parquet 파일이 4.6KB, 4건이 4.4KB 입니다. 파일마다 스키마·통계 헤더가 붙어 작은 파일은 헤더 비중이 큽니다. 작은 파일이 많아지면 병합해야 하는 이유입니다(부록 E).
06 · 구성 기술 (Parquet 조회)

Parquet 조회 방식 — 컬럼에서 행을 조립하는 원리

컬럼별 덩어리 안에서 값의 순서가 같습니다. amount 의 3번째 값과 method 의 3번째 값은 같은 행에서 온 것이므로, 컬럼을 따로 읽어도 위치로 행을 다시 조립할 수 있습니다.

조건 검색 WHERE method = 'POINT' 의 처리 순서

  1. 1파일 건너뛰기. 파일 footer 의 method 최소·최대값으로 POINT 가 있을 수 없는 파일은 열지 않습니다. Iceberg 매니페스트의 통계가 이 판단을 파일을 열기 전에 해 줍니다.
  2. 2행 그룹 건너뛰기. 파일 안은 행 그룹(수만~수십만 행) 단위로 나뉘고 그룹마다 통계가 따로 있습니다. 조건에 안 맞는 그룹은 읽지 않습니다.
  3. 3조건 컬럼만 읽어 위치를 찾습니다. 남은 그룹에서 method 덩어리만 읽어 POINT 인 위치(3번째, 17번째 …)를 얻습니다.
  4. 4그 위치의 값만 다른 컬럼에서 꺼내 행을 조립합니다. SELECT 에 없는 컬럼은 끝까지 읽지 않습니다.

잘 맞는 쿼리와 안 맞는 쿼리

쿼리Parquet이유
SELECT method, sum(amount) … GROUP BY method매우 유리컬럼 2개만 읽음. 30개 컬럼 테이블이면 I/O 가 1/15
WHERE occurred_at BETWEEN … 기간 집계유리파일·행 그룹 통계로 대부분 건너뜀. 파티션이 있으면 더 좁혀짐
WHERE order_id = 'order-50a5024f' 단건불리인덱스가 없어 통계로 좁힌 뒤에도 파일을 열어 훑음
UPDATE … WHERE …직접 불가파일은 수정 불가. Iceberg 가 새 파일을 쓰고 옛 파일을 스냅샷에서 제외하는 방식으로 처리
SELECT * 대량보통모든 컬럼을 읽어 조립. 압축 덕에 행 단위 파일보다 크게 나쁘진 않음
정렬과 파티션이 통계를 살립니다. 파일 안 행이 occurred_at 순이면 파일·행 그룹의 최소·최대 범위가 겹치지 않아 1·2단계에서 건너뛰는 양이 커집니다. day(occurred_at) 파티션은 같은 일을 디렉터리 수준에서 한 번 더 하는 것입니다.
이것이 4장 역할 분담의 근거입니다. 키로 한 건을 찾는 조회는 운영 DB 가, 컬럼 몇 개를 수백만 행에 걸쳐 집계하는 조회는 Lakehouse 가 맡는 이유는 저장 방식의 차이입니다. 실제 읽은 양은 EXPLAIN ANALYZE 의 Input: N rows 로 확인합니다.
06 · 구성 기술 (Iceberg 메타데이터)

Iceberg 메타데이터 — 커밋이 MinIO에 남기는 것

테이블을 장부라고 보면 Parquet 는 낱장, 매니페스트는 낱장 묶음의 표지, 스냅샷은 "지금 장부에 속한 묶음" 쪽지, metadata.json 은 맨 앞 목차입니다. 커밋할 때마다 낱장·표지·쪽지가 하나씩 늘고 목차가 새 세대로 바뀝니다.

PoC 의 payment_events 에 커밋 3번이 만든 것

테이블 생성      → 00000.metadata.json      목차만, 낱장 없음

1차 커밋 (7건)   → parquet ①                낱장
                 → m0.avro ①               표지: "낱장 ①, amount 1.2만~120만"
                 → snap ①                  쪽지: "묶음 ①"
                 → 00001.metadata.json      목차: 현재 = snap ①

2차 커밋 (4건)   → parquet ②, m0.avro ②
                 → snap ②                  쪽지: "묶음 ①, ②"  ← 이전 묶음도 다시 적음
                 → 00002.metadata.json      목차: 현재 = snap ②

3차 커밋 (2건)   → parquet ③, m0.avro ③
                 → snap ③                  쪽지: "묶음 ①, ②, ③"
                 → 00003.metadata.json      목차: 현재 = snap ③  ← Catalog 가 가리킴

결과: Parquet 3 · 매니페스트 3 · 스냅샷 쪽지 4(생성 포함) · 목차 4세대. 이전 목차와 쪽지를 지우지 않으므로 "2차 커밋 시점의 장부"를 그대로 다시 펼칠 수 있습니다(시점 조회).

파일비유실제로 담는 것
data/*.parquet장부의 낱장이벤트 본문. 한 번 쓰면 수정하지 않음
…-m0.avro
매니페스트		낱장 묶음의 표지데이터 파일 경로, 레코드 수, 컬럼별 최소·최대값·null 수. 조건에 안 맞는 낱장은 펼치지 않게 해 줌

0000N-….metadata.json맨 앞 목차스키마(버전별), 파티션 규칙, 스냅샷 목록, 현재 스냅샷 ID. 커밋마다 새 세대
Catalog사서"payment_events 의 현재 목차는 00003" — 테이블 이름 → 현재 metadata.json (다음 장)

이 구조가 주는 것

  • 원자적 커밋. 낱장·표지·쪽지를 올리는 동안은 아무도 못 봅니다. 새 목차가 "현재"로 지정되는 순간 한꺼번에 보입니다. DB 커밋과 뜻은 같지만 DB 는 행 몇 개를 요청마다, Iceberg 는 낱장 묶음을 30초~수 분마다 확정합니다.
  • 시점 조회. 이전 목차·쪽지가 남아 FOR VERSION AS OF 로 과거 장부를 그대로 읽습니다.
  • 낱장 건너뛰기. 표지의 컬럼 통계로 조건에 안 맞는 파일은 열지 않습니다. 디렉터리 목록 조회가 없어 객체 저장소에서 빠릅니다.
  • 스키마 변경. 컬럼 추가·이름 변경은 목차만 바뀌고 낱장은 그대로입니다.
표지·쪽지·목차도 커밋마다 쌓입니다. 스냅샷 만료·매니페스트 재작성·오래된 목차 정리가 정기 작업에 들어가는 이유입니다(부록 E).
06 · 구성 기술 (Catalog)

Iceberg Catalog — 장부의 현재 목차를 아는 사서

MinIO 에는 장부의 목차(metadata.json)가 세대별로 여러 권 남아 있습니다. "지금 유효한 목차가 어느 것인가"를 아는 사서가 필요하고, 그 사서가 Catalog 입니다. 사서는 목차의 위치만 알고, 장부 내용은 들고 있지 않습니다.

조회 경로 — 사서에게 묻고, 목차·쪽지·표지를 따라 낱장까지

어디에 묻나무엇을 얻나
①Catalog (사서)"commerce.payment_events 의 현재 목차는 어디?" → …/metadata/00003-….metadata.json
②MinIO · 목차 (metadata.json)컬럼 구성, 현재 쪽지(스냅샷) ID, 그 쪽지의 위치
③MinIO · 쪽지 (snap-….avro)지금 장부에 속한 묶음(매니페스트) 목록
④MinIO · 표지 (…-m0.avro)낱장 목록과 컬럼별 최소·최대값 → 조건에 안 맞는 낱장은 펼치지 않음
⑤MinIO · 낱장 (data/*.parquet)선별된 낱장만 펼쳐 필요한 컬럼 추출

왜 "현재 목차" 기록을 서가(MinIO)가 아니라 사서에게 맡기나

커밋은 사서의 기록을 "현재 목차 = 00003 → 00004"로 바꾸는 한 줄 수정입니다. Writer 와 병합 작업이 동시에 커밋하면 "아직 00003 이 맞나"를 확인하고 바꾸는 비교·교체가 원자적이어야 둘 중 하나가 덮어쓰이지 않습니다. 객체 저장소는 이를 표준으로 보장하지 않고, DB 트랜잭션이나 REST 서버는 보장합니다. 그래서 낱장·표지·목차는 MinIO 에 두고, "현재 목차" 한 줄만 Catalog 가 관리합니다.

사서가 사라지면 서가에 장부가 온전히 있어도 어느 목차가 현재인지 모릅니다. Catalog 와 MinIO 는 함께 백업합니다(12장). Writer 와 Trino 는 같은 사서에게 물어야 Writer 가 커밋한 장부를 Trino 가 찾습니다.

구현 선택

RESTHTTP 규약. 엔진 간 호환이 가장 넓음. 규약을 제공하는 서버(Polaris, Nessie 등)를 따로 둠. PoC: REST fixture + sqlite
JDBC (Postgres)관계형 DB 테이블 두 개에 포인터·네임스페이스 저장. 구성이 가장 단순. 운영 1단계 제안
Hive Metastore기존 Hadoop 생태계 호환용

이름이 비슷한 두 개념: lakehouse.commerce.payment_events 의 lakehouse 는 Trino Catalog(연결 설정 파일 이름)이고, 그 설정 안에서 지정하는 REST·JDBC 가 Iceberg Catalog입니다.

07 · 처리 흐름

데이터 적재 및 조회 흐름

주문 이벤트가 Kafka에 유입되어 Trino에서 조회되기까지의 처리 경로입니다. 파일 저장과 테이블 커밋은 별개의 단계로 구분됩니다.

{
  "eventId": "evt-1001",
  "eventType": "ORDER_CREATED",
  "transactionId": "order-2001",
  "customerId": "customer-3001",
  "amount": 35000,
  "occurredAt": "2026-09-13T10:00:00+09:00"

  1. 1수집. Writer가 Kafka에서 이벤트를 읽습니다. 읽은 위치(오프셋)를 추적합니다.
  2. 2변환. 필드와 타입을 테이블 컬럼에 맞춥니다.
  3. 3파일 생성. 일정량을 모아 Parquet 파일을 만듭니다.

08 · 활용 사례 ①

회원·주문 통합 분석

1순위 활용 사례이자 PoC 대상입니다. 회원 DB와 주문 DB에 나뉘어 있는 데이터를 customer_id로 연결해, 회원 유형별 주문 현황과 회원별 재주문을 봅니다.

답하려는 질문

  • 회원 유형별 주문 수·주문 금액. 개인·법인, 등급, 가입 채널별로 일·월 주문 수와 금액. 유형별 취소율.
  • 회원별 재주문 횟수. 첫 주문 이후 몇 번 더 주문했는가, 재주문 간격은 며칠인가, 재주문율이 유형별로 다른가.
  • 가입 후 첫 주문까지 기간. 가입 시각과 첫 ORDER_CREATED 시각의 차이. N일 안에 첫 주문에 이르는 비율.

테이블 3단계 (Iceberg 안의 논리 구분)

① 수집 이력member_events order_events가입·유형 변경·탈퇴, 주문 생성·취소를 사건 단위로 보존
② 정제 데이터members member_type_history orders현재 회원 상태, 유형 변경 이력(시작·종료 시각), 주문 단위 정리
③ 분석 테이블daily_orders_by_member_type member_reorder_summary유형별 일 주문 수·금액·취소율, 회원별 첫 주문일·재주문 횟수·마지막 주문일
회원 유형은 시점을 정해야 합니다. "지금 VIP인 회원의 지난달 주문"과 "지난달 주문 당시 VIP였던 주문"은 다른 숫자입니다. 유형 변경 이력을 남겨야 후자를 계산할 수 있고, 회원 DB의 현재 상태만으로는 전자밖에 안 됩니다.
결제 이벤트(payment_events)를 같은 방식으로 붙이면 결제 성공률, 취소·환불 현황, 주문·결제 불일치 후보까지 같은 테이블 구조에서 확장됩니다. 로컬 PoC 샘플이 이 확장 형태를 먼저 구현해 두었습니다.

10 · 활용 사례 ③

콜드 데이터 이관

운영 DB의 장기 미사용 데이터를 Lakehouse로 이관하고 DB에서 정리합니다. 삭제에 앞서 검증을 완료합니다.

  1. 1대상 선정. 기준을 명시합니다. 예: 마지막 변경 후 24개월 경과, 업무 종료 상태(배송 완료·환불 완료). 법정 보관 의무가 있는 항목은 제외합니다.
  2. 2복사. 초기 적재로 이미 Lakehouse에 있으면 건너뜁니다. 없으면 배치로 복사합니다.
  3. 3검증. 건수·금액 합계·샘플 레코드를 DB와 대조합니다. 불일치가 하나라도 있으면 4단계로 가지 않습니다.
  4. 4DB 정리. 아카이브 플래그 → 유예 기간 → 삭제 순서로 진행합니다. 되돌릴 수 있는 단계를 둡니다.
  5. 5과거 조회 경로. Query API가 조회 기간에 따라 DB 또는 Trino로 보냅니다. 응답 시간 차이를 화면에 반영합니다.
Serving 저장소(ScyllaDB 등)에서 TTL로 만료시키기 전에 Lakehouse 적재 완료를 확인하는 기준이 필요합니다. 만료가 적재보다 빠르면 데이터가 사라집니다.

11 · 파일 서비스 (4/4)

파일 이전 절차와 검증

무중단 병행 전환 6단계입니다. 1·2·4단계에 저장 검증과 삭제 복구를 보장하는 절차를 포함하며, 각 단계의 검증을 통과한 경우에만 다음 단계로 진행합니다.

단계하는 일검증 · 챙길 것
1MinIO 구축, files 버킷 생성, 앱에 전용 키 발급버킷을 만들자마자 버저닝을 켠다. 켜기 전 객체는 보호되지 않으므로 백필(3단계)보다 먼저. 이전 버전 90일 정리 수명주기 규칙을 함께 건다. Object Lock이 필요하면 버킷 생성 시에만 켤 수 있다
2앱 수정: 쓰기는 MinIO, 읽기는 "MinIO 먼저 → 없으면 기존 경로"(이중 조회)업로드 응답 ETag를 검증하고 저장한다. 보내기 전 계산한 해시와 응답 ETag를 비교해 불일치면 재시도. ETag와 versionId를 DB 파일 메타데이터에 함께 저장. 5MB 이상 멀티파트는 ETag가 MD5가 아니므로 SHA256 체크섬 또는 HEAD로 확인
3기존 파일 백필: mc mirror 로 운영 중 백그라운드 복사변경분만 다시 돌릴 수 있다. 1차 복사 후 전환 직전에 한 번 더 돌려 따라잡는다
4검증건수·용량 대조 + 전수 해시 대조. 원본 md5sum 목록과 MinIO ETag 목록을 diff. 원본 해시가 DB 메타데이터와도 다르면 기존 저장소에서 이미 깨진 파일이므로 목록을 남기고 담당자와 처리(재업로드·폐기)를 정한다
5이중 조회 제거(읽기도 MinIO만) → 관찰 기간4단계를 통과한 뒤에만. 관찰 기간 동안 mc undo·mc stat으로 복구·확인 절차를 실제로 한 번 수행해 본다
6기존 마운트 저장소 회수 → 인프라팀에 반납 보고관찰 기간이 끝난 뒤. "신규 저장 공간 요청"이 아니라 기존 사용분의 표준 저장소 이관 + 반납으로 보고한다

Uber — 업무 DB의 변경 데이터를 분석 플랫폼으로 전달

2019년 공개한 DBEvents 구조 기준입니다. 당시 기술은 Kafka·StorageTapper·Marmaray·Hudi·HDFS이며, 이 자료의 MinIO·Iceberg 구성과는 제품이 다릅니다. 가져올 것은 제품이 아니라 수집 원칙입니다.

풀려던 문제

수십 개 업무 DB의 테이블 전체를 반복해서 읽어 분석 저장소에 적재하고 있었습니다. 데이터가 커질수록 복사 시간이 늘고 업무 DB에 부하가 갔습니다. 주문이 1억 건이고 오늘 바뀐 주문이 10만 건이어도 매번 1억 건을 옮기는 구조였습니다(설명용 예시).

핵심 결정

초기 적재와 변경분 적재 분리기존 데이터는 한 번(Bootstrap), 이후는 변경 로그만 반영
초기 스냅샷은 복제본에서StorageTapper가 MySQL 복제본을 읽어 Primary 부하를 피하고 읽기 속도를 제한. 큰 테이블은 나눠 처리
변경은 binlog에서변경 내용을 Avro 메시지로 바꿔 Kafka로. 앱이 분석 저장소에 직접 쓰지 않고 DB에 반영된 변경을 수집 경로가 따라감
표준 메타데이터행 식별자, 증가하는 변경 버전, 삭제 여부를 모든 메시지에 부착. 버전 11 적용 뒤 버전 10이 늦게 와도 되돌아가지 않게
오류 격리변환 실패 데이터는 오류 테이블에 원본과 함께 보관. 원인을 고친 뒤 재투입
체크포인트마지막 성공 위치를 저장하고 성공했을 때만 갱신. 실패하면 이전 위치부터 재시작
체크포인트만으로 중복 방지가 완성되지 않습니다. 저장은 됐는데 체크포인트 저장 전에 죽을 수 있으므로, 재실행 시 같은 데이터를 안전하게 처리하는 규칙(eventId·버전)이 함께 필요합니다. 12장 이벤트 규약이 그 대응입니다.

이 자료에 적용할 점

  • 초기 적재(9장 구축 순서 7단계)와 변경분 수집(Outbox·CDC)을 처음부터 함께 설계합니다.
  • PoC 검증 항목에 "장애 후 어디서부터 다시 읽고, 어디까지 저장됐다고 판단하는가"를 넣습니다. Iceberg Sink는 커밋 오프셋을 스냅샷에 기록해 이 문제를 풉니다.
  • 콜드 데이터 이관과의 차이. Uber 구조는 DB 변경을 따라 반영하므로 DB 정리용 삭제도 분석 테이블에서 지웁니다. 장기 보관용 이력 테이블과 삭제 정책을 따로 두어야 합니다(10장).
13 · 기업 사례 (SK텔레콤)

SK텔레콤 — Trino와 Iceberg로 분석 조회 개선

Trino Summit 2022 발표 기준입니다. 저장 기반은 온프레미스 Hadoop/HDFS였고 MinIO 사례는 아닙니다. 가져올 것은 "테이블 포맷을 바꾸면 조회가 왜 빨라지는가"에 대한 실측 경험입니다.

풀려던 문제

Hive 기반 분석 환경에서 데이터와 사용자가 늘자 조회가 느려졌습니다. 조사 결과 병목은 데이터 읽기보다 메타데이터 접근과 파일 목록 조회에 있었습니다. Hive는 "어떤 파일이 테이블인가"를 디렉터리 목록으로 알아내기 때문에 파티션과 파일이 많을수록 쿼리 계획 단계가 길어집니다.

핵심 결정

조회 환경 분리배치 조회와 임시 분석 조회 환경을 나눠 서로 영향을 주지 않게
측정부터쿼리 계획, JMX, 시스템 지표, 로그를 수집해 어느 단계가 느린지 확인. 짐작으로 바꾸지 않음
Iceberg 도입파일 통계와 매니페스트로 읽을 파일을 미리 골라내 불필요한 파일 읽기와 디렉터리 목록 조회를 제거
파티션 절충파티션을 너무 잘게 나누면 매니페스트가 늘어 계획 시간이 다시 늘어남. 조회 패턴에 맞는 크기로
6장의 Parquet 조회 방식과 Iceberg 메타데이터가 바로 이 개선의 원리입니다. 표지(매니페스트)의 컬럼 통계로 낱장을 건너뛰고, 디렉터리 목록 대신 쪽지(매니페스트 목록)를 읽습니다.

이 자료에 적용할 점

  • "Iceberg를 쓰면 빨라진다"로 끝내지 않고, 대표 쿼리 3개로 계획 시간·읽은 파일 수·응답 시간을 측정합니다(9장 10단계, EXPLAIN ANALYZE).
  • 파티션은 실제 조회 조건으로 정합니다. 고객별 조회와 월별 전체 집계는 요구하는 배치가 다릅니다.
  • 수치를 인용할 때는 발표 자료 출처를 확인합니다. 이 장은 구조와 원리만 옮겼습니다.

Hive 테이블 포맷의 병목

Hive에서 테이블은 "이 디렉터리 아래 파일 전부"입니다. 어떤 파일이 테이블인지 어디에도 적혀 있지 않아, 조회할 때마다 디렉터리를 뒤집니다. 병목 다섯 가지가 모두 여기서 나옵니다.

예시 시나리오 (수치는 설명용) payment_events를 일 파티션, 30분 커밋(하루 파일 48개)으로 9개월 운영 → 파티션 270개 × 48 = 파일 12,960개. 질문: "지난 9개월 한도 초과(amount ≥ 1,000,000) 결제 실패는 몇 건인가" — 조건 컬럼 amount는 파티션 컬럼이 아닙니다.
①
파일 목록 조회가 파일 수에 비례
파티션 디렉터리마다 LIST. 객체 저장소는 LIST가 비싸고 1,000개씩 끊겨 옵니다.
예: 270개 디렉터리를 LIST해 파일 12,960개의 이름을 모읍니다. 쿼리를 시작하기도 전에 수십 초가 갑니다.
②
파티션마다 메타스토어 호출
파티션 경로를 파티션 수만큼 메타스토어 DB에 묻습니다.
예: 270번 질의. 시간 단위 파티션으로 바꾸면 6,480번이라 오히려 느려져서 잘게 나눌 수 없습니다.
③
파일을 열어야 조건 판단
파일별 통계가 없어 파티션 컬럼이 아닌 조건은 파일을 열어야 압니다.
예: amount ≥ 100만 조건인데 12,960개를 전부 엽니다. 한도 초과는 드물어 대부분 열고 버립니다.
④
원자적 커밋 없음
쓰기는 파일을 디렉터리에 넣으면 끝이라 중간 상태가 보입니다.
예: 30분 커밋이 파일 3개를 쓰는 중에 리포트를 돌리면 1개만 들어간 결과가 나옵니다. 실패해서 중간에 멈춘 파일도 다음 조회에 그대로 잡힙니다.
⑤
스키마·파티션이 물리 구조에 묶임
컬럼은 이름·위치로, 파티션은 디렉터리로 파일과 묶여 있습니다.
예: method를 payment_method로 바꾸면 옛 파일 9개월치가 null로 읽힙니다. 일 파티션을 월 파티션으로 바꾸려면 12,960개를 다시 씁니다.

13 · 기업 사례 (Iceberg의 해결)

Iceberg가 다섯 병목을 푸는 방식

Hive는 장부에 목차가 없어 매번 서가를 뒤졌습니다. Iceberg는 목차·쪽지·표지(6장)를 만들어 "무엇을 읽을지"를 파일을 열기 전에 정합니다.

같은 예시 적용 "지난 9개월 한도 초과(amount ≥ 1,000,000) 결제 실패 건수" — 파일 12,960개, 파티션 270개
  1. 1Catalog에 한 번 묻는다. "payment_events의 현재 목차는?" → 00512-….metadata.json. Hive는 파티션별 경로를 메타스토어에 270번 묻지만, Iceberg는 파티션 정보가 DB가 아니라 표지 파일에 있어 Catalog에는 목차 위치만 1회 묻습니다.
  2. 2목차에서 현재 쪽지를 연다. 쪽지에는 표지 270개(파티션당 1개)의 경로와 각 표지가 담당하는 파티션 값(dt)이 적혀 있습니다. 디렉터리 LIST 0회.
  3. 3표지 270개를 읽어 파일을 고른다. 표지마다 파일 48개의 amount 최소·최대값이 있습니다. 최대값이 100만 미만인 파일은 조건에 맞는 행이 있을 수 없으므로 열지 않습니다. 한도 초과는 드물어 12,960개 중 남는 파일은 수십 개입니다.
  4. 4남은 파일만 연다. 그 안에서도 amount 컬럼 덩어리를 먼저 읽어 조건에 맞는 행 위치를 찾고, event_type = 'PAYMENT_FAILED'인 행만 셉니다(6장 Parquet 조회 방식).
amount가 파티션 컬럼이 아니어도 파일 단위로, 열기 전에 걸러집니다. Hive는 폴더 이름으로만 거를 수 있어 파티션이 아닌 조건에는 속수무책이었습니다. 파티션 조건(dt)도 표지에 값이 있어 파일을 열지 않고 걸러집니다.
Hive 병목Iceberg
① 파일 목록 조회파일 목록을 표지(매니페스트)에 기록. 디렉터리 LIST를 하지 않음 — 예: LIST 270회 → 0회
② 파티션마다 메타스토어 호출파티션 값도 표지에. Catalog에는 "현재 목차 위치" 한 번만 묻는다 — 예: 270회 → 1회
③ 파일을 열어야 조건 판단표지의 컬럼 min·max로 열기 전에 건너뜀 — 예: 여는 파일 12,960개 → 수십 개
④ 원자적 커밋 없음새 목차를 쓰고 Catalog 포인터를 교체하는 순간 전체가 한 번에 보임 — 예: 파일 3개가 커밋 전엔 0개, 후엔 3개. 중간 상태 없음
⑤ 스키마·파티션이 물리 구조에 묶임컬럼은 ID로 대응해 이름 변경이 안전. 파티션 규칙은 목차에 있어 바꿔도 옛 파일은 옛 규칙으로 읽음 — 예: method→payment_method 변경 후에도 옛 파일 정상. 일→월 파티션 변경 시 재작성 없음
Iceberg도 표지가 너무 많아지면 ①과 비슷한 문제가 재발합니다. 파티션을 잘게 나누거나 작은 커밋이 쌓이면 계획 시간이 다시 늘어납니다. 부록 E의 병합·매니페스트 재작성이 그 대응입니다.

Netflix — Hive에서 Iceberg 전용 데이터 레이크로

AWS re:Invent 2023 NFX306 발표 기준입니다. Netflix는 Iceberg를 만들어 Apache에 기증한 곳이고, 이 발표는 자기 데이터 레이크를 Hive에서 Iceberg 전용으로 옮긴 과정입니다.

테이블은 언제 만들고, 구조는 누가 정하나

테이블 생성은 적재 전에 한 번 하는 별도 작업입니다. 커넥터가 자동으로 만들게 할 수도 있지만(auto-create), 그러면 첫 이벤트의 JSON이 테이블 구조를 결정합니다. 샘플은 DDL로 먼저 만들고 이벤트가 그 구조를 따르게 했습니다.

③ 커밋 반복30초마다 앞 장의 4단계. 목차 세대가 00001, 00002 … 로 늘어남

파일 업로드·다운로드 및 임시 URL 방식

파일 애플리케이션이 권한을 확인하고, 실제 바이트는 클라이언트와 MinIO가 직접 주고받습니다.

두 가지 전송 방식

방식흐름특징
앱 경유클라이언트 → 파일 앱 → MinIO앱이 바이트를 중계. 검사·변환 가능. 앱 서버 대역폭 소모
임시 URL 권장클라이언트 → 파일 앱(URL 발급) → 클라이언트 ↔ MinIO 직접앱은 권한만 확인. 대용량에 유리. URL에 만료 시간

임시 URL(presigned URL) 요점

  • 파일 앱이 자기 자격증명으로 서명한 URL을 발급합니다. 클라이언트는 자격증명 없이 그 URL로만 PUT/GET 합니다.
  • 만료 시간(예: 업로드 15분, 다운로드 5분)과 HTTP 메서드, 객체 키가 URL에 고정됩니다.
  • 업로드 완료는 클라이언트 신고가 아니라 앱이 MinIO에서 객체 존재·크기를 확인해 확정합니다.
  • 외부 노출 시 MinIO Endpoint 앞에 리버스 프록시·TLS를 둡니다.
  • 이 패턴은 AWS 공식 자료의 S3 직접 업로드 구조와 같습니다. 다만 AWS 전용 기능(Transfer Acceleration 등)과 MinIO가 지원하는 기능은 구현 시 구분합니다.

부록 G

예상 질문과 답변

Q. Trino로 사용자 화면의 과거 조회를 바로 처리할 수 있나요?

SQL로 조회는 됩니다. 사용자 화면이 요구하는 응답 시간과 동시 접속을 만족하는지는 별개입니다. 목표 부하로 검증하기 전에는 Serving 계층(DB)이 화면을 맡습니다.

Q. 실시간인가요?

아닙니다. Writer가 배치로 묶어 커밋하므로 분 단위 지연이 있습니다. 허용 지연을 정하고 "방금 쓴 데이터가 아직 없을 때"의 화면 동작을 함께 정합니다.

Q. 운영 DB를 대체하나요?

아닙니다. 업무 처리와 거래 상태의 기준은 운영 DB에 남습니다. Lakehouse는 이벤트로 갱신되는 조회용 복제본입니다.

Q. 기존 파일 서비스는 바뀌나요?

앱 로직은 그대로이고 저장소만 MinIO로 옮깁니다. 파일용 Bucket과 Lakehouse용 Bucket은 분리합니다.

Q. 개인정보 삭제 요청은 어떻게 처리하나요?

삭제 이벤트를 세 계층에 전파하고, Iceberg에서는 해당 행을 삭제한 뒤 스냅샷 만료로 과거 파일까지 정리합니다. 백업에 남은 데이터의 처리 기간도 정책에 넣습니다.

Q. 장애가 나면 데이터가 유실되나요?

Writer는 커밋한 오프셋을 기억하고 재시작 시 그 다음부터 읽습니다. Kafka 보관 기간 안이면 누락 없이 재적재됩니다. 그 밖은 초기 적재 절차로 복구합니다.

Q. Flink는 왜 지금 안 쓰나요?

첫 목표는 "Kafka 데이터를 저장하고 SQL로 확인"이라 Kafka Connect Iceberg Sink로 충분합니다. 스트림 조인, 이벤트 시간 집계가 필요해지면 그때 검토합니다.

Q. 이 구성은 Netflix 같은 회사의 공식 아키텍처인가요?

아닙니다. Netflix는 핵심 부품인 Iceberg 테이블 포맷을 만들어 Apache에 기증한 곳이고, 2023년 발표 기준으로 자기 데이터 레이크 전체를 Iceberg 전용으로 운영합니다. "Lakehouse"라는 용어는 2020년 Databricks가 정의해 퍼뜨린 업계 개념입니다. 이 자료의 Kafka·MinIO·Iceberg·Trino 조합은 그 개념을 오픈소스 부품으로 구현한 것이지 특정 회사의 구성을 옮긴 것이 아닙니다.

Q. 얼마나 걸리나요?

1~2단계(요구사항 확정, 수집·보관 PoC)가 첫 마일스톤입니다. 2단계 완료 기준을 통과한 뒤 3단계 일정을 잡습니다.
