# Kafka 도입 프로젝트 킥오프 (초안)

> 킥오프 미팅용 발표 초안. `[ ]` 표시는 발표 전에 실제 값·사례로 채울 부분.

## 1. 배경 — 기존 시스템의 한계

현행 시스템 간 연동 방식의 한계 (실제 사례로 교체):

- **[사례 1]** 서비스 간 직접 API 호출 — 수신 서비스가 죽으면 호출 측도 실패하거나 데이터가 유실됨. 연동 대상이 늘 때마다 호출 코드가 늘어남.
- **[사례 2]** DB 폴링 배치 — 실시간성이 떨어지고(배치 주기만큼 지연), 폴링 부하가 DB에 집중됨.
- **[사례 3]** 장애·재처리 — 전송에 실패한 데이터를 다시 보내는 표준 방법이 없어 수작업 복구.

공통 문제: **시스템 간 결합도가 높고, 유실·지연·재처리에 대한 표준 답이 없다.**

## 2. 요구사항 — 필요한 것

| 요구 | 의미 |
| --- | --- |
| 무손실 | 서버 1대 장애에도 접수된 데이터는 잃지 않는다 |
| 순서 보장 | 같은 대상(주문 등)의 이벤트는 발생 순서대로 처리된다 |
| 재처리 | 장애 복구·로직 수정 후 과거 데이터를 다시 처리할 수 있다 |
| 결합도 감소 | 발행하는 쪽은 구독하는 쪽이 몇 개인지 몰라도 된다. 구독 서비스 추가 시 기존 시스템 무변경 |
| 유연한 소비 속도 | 수신 서비스가 느리거나 잠시 죽어도 데이터가 쌓였다가 처리된다 |

## 3. 왜 Kafka인가 (대안 비교)

| | Kafka | RabbitMQ 등 전통 MQ | DB 폴링 |
| --- | --- | --- | --- |
| 메시지 보존 | 소비해도 보존(기간제) → **재처리 가능** | 소비하면 삭제 | 가능하나 DB 부하 |
| 순서 보장 | 파티션 단위 보장 | 큐 단위(경쟁 소비 시 깨짐) | 정렬 쿼리 필요 |
| 다중 구독 | 그룹별 독립 소비(N개 서비스가 같은 데이터) | 익스체인지 구성 필요 | 각자 폴링 |
| 처리량 확장 | 파티션 병렬로 수평 확장 | 상대적 제한 | DB가 병목 |
| 생태계 | CDC(Debezium)·스키마 관리·모니터링 표준 존재 | 제한적 | — |

업계 표준: 이벤트 파이프라인 용도로는 사실상 Kafka가 표준. 사내 [메시지 연동/이벤트 요구]에 부합.

## 4. 아키텍처 — 구축 완료 + 진행 예정

### 완료 ✅

- **3노드 KRaft 클러스터** (실서버 3대, Docker Compose) — RF3 + `min.insync.replicas=2`로 브로커 1대 장애에도 무손실
- **보안**: SASL/SCRAM 인증 + TLS 암호화 + ACL 인가(서비스별 계정, 자기 토픽만 접근)
- **Schema Registry 2대 이중화** — 메시지 형식의 중앙 관리·호환성 검사
- **개발자 사용 가이드 문서** (usage-guide 시리즈 7편)

### 진행 예정 🔄

- **Kafka Connect ×2** — DB 변경 캡처(Debezium) 등 커넥터 실행
- **모니터링**: Prometheus + Grafana + kafka_exporter — 클러스터 건강·컨슈머 lag 감시, 알람
- **관리 도구**: Kafka UI, Admin Portal

### 결정 필요: 서버 배치 방안 (A/B)

```text
[방안 B — 역할 분리 (플랫폼팀 추천)]
서버1 (데이터 플레인)      서버2 (데이터 플레인)      서버3 (관제)
Broker                  Broker                  Broker
Connect ①               Connect ②               Prometheus + Alertmanager
Schema Registry ①       Schema Registry ②       kafka_exporter, Grafana
                                                Kafka UI, Admin Portal
```

- 방안 A(제안 원안)와 B(역할 분리) 비교는 별도 문서(`kafka/concepts/15-deployment-layout-options.md`) 참고
- B 권장 이유: 서버3의 관제 컴포넌트는 전부 죽어도 데이터 흐름에 무영향, 사용자 접근 방화벽 단일화, 메모리 균등

## 5. 개발자 사용 방법

**원칙 3가지만 지키면 됩니다** (상세는 사용 가이드 문서):

1. 프로듀서: `acks=all` + 멱등 설정, 순서가 중요하면 **메시지 key** 지정
2. 컨슈머: **처리 완료 후 수동 커밋** + **멱등 처리**(같은 메시지 2번 와도 안전하게)
3. 토픽은 직접 만들지 않고 **요청** (명명 규칙 `<도메인>.<엔티티>.<이벤트>`)

- 샘플 코드·설정(`application.yml`) 제공: Java + Spring Boot 기준, 복사해서 시작 가능
- 가이드 문서: `kafka/usage-guide/` 시리즈 (개요 → 명명 → 토픽 요청 → 프로듀서 → 컨슈머 → 접속 설정 → 자주 하는 실수)
- 개발자에게 필요한 방화벽: 9094(브로커 3대), 8081(Schema Registry 2대)
