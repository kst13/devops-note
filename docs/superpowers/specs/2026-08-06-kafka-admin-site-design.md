# Kafka 관리자 사이트 설계

2026-08-06 브레인스토밍 결과. 3노드 KRaft 클러스터(SASL_SSL, `kafka/examples/compose-3node-kraft/`)를 대상으로 하는 관리자 사이트의 설계 문서.

## 목적과 사용자

- **운영자(ADMIN)**: 클러스터 모니터링, 장애 감지·알림 수신, 복구 조치 실행.
- **개발자(DEVELOPER)**: 토픽/컨슈머 그룹 조회, 토픽 생성 신청.

기성 도구(Kafbat UI 등)를 쓰지 않고 전부 직접 개발한다. 이유: 실제로 필요한 기능(알림, 인증서 만료 감시, 복구 조치, 브로커 재시작, 신청 워크플로우)이 기성 도구가 지원하지 않는 영역에 몰려 있음.

## 기술 스택

| 구성 요소 | 선택 |
|---|---|
| 백엔드(WAS) | Spring Boot (AdminClient/Consumer 직접 사용) |
| 프론트 | Vue SPA |
| 웹서버 | Nginx (정적 파일 서빙 + 리버스 프록시) |
| DB | H2 파일 모드로 시작, 필요 시 이전 |
| 배포 | 관리용 VM 1대(2core/4~8GB)에 docker-compose로 컨테이너 2개(web, was) |

## 아키텍처

```
관리용 VM
┌──────────────────────────────────────────────┐
│  web: Nginx 컨테이너                           │
│   - Vue 빌드 결과물(정적 파일) 서빙              │
│   - /api/* → WAS 리버스 프록시                  │
│   - 외부 노출 유일한 진입점 (80/443)             │
│              │                               │
│              ▼                               │
│  was: Spring Boot 컨테이너                     │
│   - REST API (/api/*)                        │      SASL_SSL :9094
│   - 지표 수집 스케줄러 + 알림 발송     ──────────│────▶ 브로커 3대
│   - H2 (파일 모드, 볼륨 마운트)                  │      SSH :22
│                                    ──────────│────▶ 브로커 호스트
└──────────────────────────────────────────────┘
```

- 관리자 사이트는 브로커 서버와 **분리된 VM**에 둔다. 브로커 장애 시 관리 도구가 함께 죽으면 안 되고, 브로커의 페이지 캐시를 잠식하면 안 되기 때문.
- 경로 규칙: `/api/*`는 WAS로 프록시, 나머지는 Vue `index.html` 폴백(`try_files`). 프론트/백 배포는 서로 독립.
- Kafka 접속: CLIENT 리스너(9094, SASL_SSL), 전용 admin SCRAM 계정 + truststore.
- 방화벽: WAS → 브로커 3대 전부 TCP 9094 (bootstrap 이후 각 브로커에 직접 접속하므로 1대만 열면 안 됨). 브로커 재시작 기능용 TCP 22.
- 외부 모니터링 스택(Prometheus 등) 없이 앱 내 스케줄러로 수집한다. 앱이 죽으면 수집도 죽는 약점은 규모 대비 단순함을 우선해 수용.

## 백엔드 모듈 구성

```
api ──────── REST 컨트롤러 (인증/권한 검사)
kafka ────── AdminClient/Consumer 래퍼. Kafka 접속의 유일한 통로
collector ── @Scheduled 지표 수집 (랙, URP, 디스크, 브로커 생존: 30초~1분 /
             인증서 만료일: 일 1회) → H2 이력 저장
alert ────── 임계치 평가 + 슬랙/메일 발송, 쿨다운으로 중복 억제
ops ──────── 위험 작업 실행기: 확인 절차 → 실행 → 감사 로그. SSH 연동 포함
workflow ─── 토픽 신청/승인 → 승인 시 kafka 모듈이 자동 생성
auth ─────── 로그인, 역할(ADMIN/DEVELOPER)
```

### kafka 모듈이 제공하는 작업

- 조회: 브로커·토픽·파티션·ISR·컨슈머 그룹·랙, 메시지 열람(파티션·오프셋 범위 지정).
- 조치: 오프셋 리셋, retention 등 설정 변경, 파티션 증가, preferred/unclean 리더 선출, 파티션 재할당(`alterPartitionReassignments`), 복제 스로틀.

### 안전장치 (설계의 중심 규칙)

- 위험 작업(오프셋 리셋, 재할당, unclean 선출, 브로커 재시작 등)은 **반드시 ops 모듈을 경유**한다. 컨트롤러가 kafka 모듈을 직접 호출해 조치하는 경로는 금지.
- ops는 ① 실행 전 영향 요약 표시 + 확인 절차, ② 감사 로그(누가·언제·무엇을·결과)를 강제한다.
- 자동 복구는 하지 않는다. 감지 → 알림 → 사람 확인 → 실행의 반자동 구조.

## 데이터 흐름

- **조회·조치**: 화면 → api → kafka/ops → 브로커. 실시간 동기 호출.
- **감시**: collector → H2 → alert → 슬랙/메일. 화면과 무관하게 백그라운드 동작.
- 화면의 추이 그래프는 H2 이력, "현재 상태" 카드는 실시간 조회.

## 예외 처리

- 브로커 일부/전체 무응답에도 사이트는 동작한다. AdminClient 타임아웃 5초 내외, 실패는 "브로커 접속 불가" 상태로 화면 표시.
- collector 수집 3회 연속 실패는 그 자체를 알림 대상으로 한다 (클러스터 전면 장애 신호).
- 조치 실행 결과는 성공/실패/타임아웃 모두 감사 로그에 남기고, 실패 시 원본 에러를 그대로 표시.

## 보안

- 로그인 필수. 단일 WAS 구성이므로 세션 방식(Spring Security 기본)을 사용. 역할 기반 권한: DEVELOPER는 조회 + 신청, ADMIN은 조치 실행까지.
- SSH 키, SCRAM 비밀번호, truststore 비밀번호는 환경변수 또는 마운트 파일로 주입. 코드/이미지에 포함 금지.
- Nginx만 외부 노출. WAS·H2는 내부 전용.
- SSH 기반 브로커 재시작은 Docker API 원격 노출(2375/2376) 대신 SSH 경유 `docker restart`를 사용.

## 구축 단계

| 단계 | 내용 | 완료 시 얻는 것 |
|---|---|---|
| 1 | 골격 + 조회: 로그인, 클러스터/토픽/그룹/랙 조회 | 기성 도구 조회 기능 대체 |
| 2 | collector + 알림, 인증서 만료 감시 | 기성 도구가 못 하는 감시 체계 |
| 3 | 조치: 오프셋 리셋, 설정 변경, 파티션 증가, 리더 선출, 재할당, 감사 로그 | 장애 대응 원클릭 |
| 4 | SSH 브로커 재시작, 토픽 신청 워크플로우, 메시지 열람 | 셀프서비스 + 인프라 조작 |

각 단계는 그 자체로 사용 가능한 상태로 마무리한다.

## 테스트 전략

- kafka 모듈: Testcontainers(단일 Kafka 컨테이너) 통합 테스트. 위험 조치(오프셋 리셋, 재할당)일수록 우선 작성.
- 나머지 모듈: kafka 모듈을 목으로 두고 단위 테스트.

## 범위 제외 (YAGNI)

- 메시지 본문 검색 (범위 지정 열람만 제공, 필요 시 추가)
- 자동 복구/self-healing (필요해지면 Cruise Control 도입 검토)
- Prometheus/Grafana 연동
- 멀티 클러스터 지원 (단일 클러스터 전제)

## 사이트로 해결할 수 없는 것 (기대치 관리)

- 랙 해소, 중복 소비, 핫 파티션, 리밸런스 설정 — 컨슈머 애플리케이션 코드/설정의 문제. 사이트는 감지·진단 정보 제공까지만 가능.
- 활성 컨슈머 그룹의 오프셋 리셋 — Kafka 프로토콜 제약. 그룹 정지 안내를 UI에 표시한다.
