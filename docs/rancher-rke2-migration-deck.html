01 · 기존 배포 방식

기존 배포 방식

Jenkins가 빌드 결과물을 서버별로 복사한 뒤, SSH로 접속해 컨테이너를 재시작하는 구조

  1. 1빌드GitLab 소스로 jar/war 생성
  2. 2전달대상 서버마다 scp로 결과물 복사
  3. 3재시작서버별 SSH 접속 후 docker stop → rm → run
  4. 4확인담당자가 서버에 접속해 docker ps, docker logs로 기동 확인
# 기존 배포 단계 예시 (앱별 스크립트 상이)
scp build/libs/app.jar deploy@${APP_SERVER}:/app/
ssh deploy@${APP_SERVER} \
  "docker stop app && docker rm app && \
   docker run -d --name app -p 8080:8080 ..."

03 · 선택 이유

Rancher + RKE2 선택 이유

Kubernetes는 여러 서버를 하나의 실행 환경으로 묶는 플랫폼. RKE2는 온프레미스용 Kubernetes 배포판, Rancher는 여러 클러스터를 통합 관리하는 도구

유지 항목

  • GitLab · Jenkins빌드 단계 유지, 마지막 배포 단계만 교체
  • Nexusdocker hosted, helm hosted 저장소만 추가. 별도 Harbor 불필요
기존 도구 유지로 학습 범위를 Dockerfile, Helm 차트, kubectl 기초로 한정
요구사항대응 방식
온프레미스 설치systemd 서비스로 설치. 보안 강화 기본 설정 제공
dev·stage·prod 통합 관리클러스터 목록, 사용자, 권한을 Rancher에서 일괄 관리
화면 기반 배포·롤백Apps 화면에서 차트 버전 선택 후 Install, Upgrade, Rollback
간단한 노드 추가Custom 등록. 노드에서 등록 명령 1회 실행, 에이전트가 RKE2 설치
개발팀 권한 위임Project 단위로 로그 조회, 재시작, 복제 수 조정만 허용. 서버 계정 미발급
04 · 목표 아키텍처

목표 아키텍처

빌드는 Jenkins, 보관은 Nexus, 배포·복구·롤백은 Rancher가 담당하는 역할 분리 구조

  • Jenkins이미지와 Helm 차트를 동일 버전으로 생성해 Nexus에 push. 배포는 수행하지 않음
  • Nexus이미지는 docker hosted(5000), 차트는 helm hosted(8081)에 버전별 보관
  • Rancher관리 클러스터 3대에서 운영. Nexus 차트 목록을 읽어 선택한 버전을 dev 클러스터에 설치
  • dev 클러스터노드 3대가 Nexus에서 이미지를 pull해 실행
Helm 차트: 포트, 환경변수, 자원, 헬스체크, 복제 수를 담은 배포 명세. 앱 소스 저장소에서 함께 관리
04 · 목표 아키텍처

관리 클러스터 분리

Rancher는 Kubernetes 위에서 동작하는 애플리케이션. Rancher를 설치한 관리 클러스터에는 다른 워크로드를 배치하지 않음

분리 이유내용
장애 범위앱 클러스터의 업그레이드·장애가 Rancher에 영향을 주지 않음. 역방향도 동일
권한Rancher는 전체 클러스터의 admin 권한 보유. 서비스 Pod와 같은 노드에 두면 침해 시 영향 범위가 전체 인프라로 확대
업그레이드Rancher 버전마다 지원 Kubernetes 버전이 다름. 분리하면 독립 일정으로 업그레이드
자원관리 대상이 늘면 Rancher 메모리 사용량도 증가. 서비스와의 자원 경합 방지

이중화 구성

  • control plane · etcdserver 노드 3대. etcd 과반 합의를 위해 홀수 구성
  • Rancher Podreplicas=3 + antiAffinity: required로 노드별 1개. replicas만으로는 분산 미보장
  • 진입점L4가 노드 3대로 443 분산. Rancher hostname은 L4를 가리킴
  • hostname전체 노드 에이전트의 접속 주소. 변경 시 전 노드 재등록이 필요하므로 초기에 확정
Rancher 중단 시에도 dev 클러스터의 앱은 정상 동작. 중단 범위는 Rancher 화면과 Rancher 경유 배포·인증
04 · 목표 아키텍처

접속 방향과 방화벽

노드 에이전트가 Rancher로 먼저 접속해 작업을 받아 가는 구조. Rancher의 노드 SSH 접속이 없어 방화벽 규칙이 단방향·단일 포트로 축소

노드 등록 순서

  1. 1Rancher 화면에서 Custom 클러스터 정의 (RKE2 버전, CNI, 노드 역할)
  2. 2각 노드에서 Rancher가 제공한 등록 명령 실행 (유일한 수동 단계)
  3. 3rancher-system-agent 설치 후 Rancher 443으로 접속·등록
  4. 4Rancher가 내려준 설치 계획에 따라 에이전트가 RKE2 설치·기동
Jenkins도 Rancher 443만 사용. stage·prod 클러스터를 추가해도 Jenkins 방화벽 재신청 불필요
05 · 릴리즈 단위

릴리즈 단위와 버전 규칙

앱 1개 = Jenkins Job 1개 = Helm 차트 1개. 이미지 태그, 차트 버전, 빌드 번호를 하나의 번호로 통일

  • 버전 형식1.0.<빌드번호>, latest 태그 미사용
  • 이미지 태그차트 appVersion을 기본값으로 사용. values에 태그 별도 기재 불필요
  • 앱별 배포web, WAS 각각 버전 선택. API 동시 변경 시 was → web 순서로 Upgrade
  • values 변경설정 변경도 릴리즈로 기록. 리비전 증가, Rollback 대상
실패한 빌드도 번호를 소비하므로 버전 번호 공백은 정상
web 저장소 push ─▶ web Job ─▶ Nexus
   web-portal:1.0.41 이미지 + web-portal-1.0.41.tgz 차트

was 저장소 push ─▶ was Job ─▶ Nexus
   was-order:1.0.58  이미지 + was-order-1.0.58.tgz  차트
                                  │
담당자: Rancher → Apps → was-order → 1.0.58 → Upgrade
        (web 영향 없음)
Deployment 태그 변경Apps (Helm 차트)
릴리즈 단위이미지이미지 + 설정 채택
버전 목록레지스트리에서 직접 확인드롭다운에 표시
롤백 범위이미지이미지 + values

Jenkins 파이프라인 변경

빌드 단계는 유지. 마지막 "복사 + docker run" 단계를 "docker push + helm push"로 교체

기존: 서버 접속 후 실행

   docker run -d --name app ..."
  • Jenkins에 서버 SSH 키 보관
  • 배포 대상 서버 목록을 스크립트에 고정
  • Job 성공 = 운영 반영 완료

변경: 저장소 push까지

VER = "1.0.${env.BUILD_NUMBER}"

docker build --build-arg APP_VERSION=$VER -t $IMAGE:$VER .

helm lint chart
helm package chart --version $VER --app-version $VER -d dist
curl -fsS -u "$U:$P" --upload-file \
  dist/web-portal-$VER.tgz $NEXUS_HELM
  • Jenkins는 Nexus 계정만 보유
  • 배포 대상은 Rancher에서 선택
  • Job 성공 = 배포 가능한 버전 1개 추가
Job 종료 메시지: "web-portal 1.0.N 준비 완료. Rancher → Apps에서 선택해 배포". 운영 반영은 Rancher에서만 실행

08 · 전체 경로 검증

Rancher 배포 절차

서버 접속 없이 Rancher 화면에서 앱과 버전을 선택해 배포

설치 · 업그레이드 · 롤백

  1. 1저장소 등록최초 1회. Apps → Repositories에 Nexus helm hosted 주소와 계정 등록
  2. 2InstallCharts에서 앱, 버전, 네임스페이스 선택. web은 was와 같은 네임스페이스에 설치
  3. 3Upgrade새 빌드 후 Repositories Refresh, Installed Apps에서 새 버전 선택. 이전 values 자동 입력
  4. 4Rollback이전 리비전 선택. 이미지와 values 동시 복원

롤링 업데이트 동작

  • 새 Pod가 헬스체크를 통과한 뒤 기존 Pod 종료. 배포 중 서비스 유지
  • 존재하지 않는 태그 지정 시 새 Pod는 ImagePullBackOff, 기존 Pod는 서비스 지속

10 · 트러블슈팅

nginx 기동 실패: WAS 주소 조회

web Pod 재시작 반복. nginx가 기동 시점에 WAS 주소를 조회하는 설정이 원인

증상CrashLoopBackOff, 로그 host not found in upstream "was-order"
원인고정 주소 proxy_pass는 기동 시 DNS 조회 필요. WAS Service가 없으면 기동 실패
확인공식 nginx 이미지와 ConfigMap으로 테스트 Pod 구성. /healthz 200, /api/hello 502, 기동 정상
해결주소를 변수로 바꾸고 resolver 지정. 요청 시점에 이름 해석
운영 원칙: WAS 장애가 web 기동 실패로 번지지 않도록 web은 WAS 없이 기동, /api만 502 응답
# default.conf.template (기동 시 envsubst로 치환)
resolver ${DNS_SERVER} valid=10s ipv6=off;

# 변수 proxy_pass는 search 도메인 미적용 → FQDN 사용
set $was_upstream http://${WAS_HOST}:8080;

location /api/ {
    proxy_pass $was_upstream;
    proxy_connect_timeout 2s;
}
  • 05-dns.envsh: /etc/resolv.conf의 첫 nameserver를 DNS_SERVER로 export
  • WAS_HOST: 차트 values로 주입. 기본값 was-order.<ns>.svc.cluster.local
