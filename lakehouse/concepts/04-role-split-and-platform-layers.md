# 운영 DB와의 역할 분담과 플랫폼 계층

> 업무 처리와 빠른 조회는 DB가, 장기 이력과 분석은 Lakehouse가 맡습니다. 나누는 기준은 데이터의 나이가 아니라 **조회 요구사항**입니다.

## 1. DB와 Lakehouse

| 항목 | 운영 DB | Lakehouse |
| --- | --- | --- |
| 담당 | 업무 처리(트랜잭션), 화면 조회 | 장기 이력, 분석·집계·추출 |
| 데이터 범위 | 서비스에 필요한 최근 범위 | 전체 이력 |
| 응답 시간 | 수 ms, 예측 가능 | 수 초 ~ 수 분 |
| 반영 시점 | 즉시 | 분 단위 지연 |
| 데이터 지위 | **거래 상태의 기준(원본)** | 이벤트로 갱신되는 **조회용 복제본** |
| 동시 사용자 | 전체 사용자 | 분석가·배치·내부 도구 |

```text
업무 처리 · 화면 조회                    장기 이력 · 분석
┌──────────────────────┐   변경 이벤트   ┌──────────────────────┐
│ 운영 DB              │ ─────────────▶ │ Lakehouse            │
│ 거래 상태의 기준       │ (Outbox·CDC    │ 조회용 복제본          │
│ 최근 범위만 유지       │  → Kafka)      │ 전체 기간 보관         │
└──────────────────────┘                └──────────────────────┘
        ▲                                        ▲
  사용자 화면 · 업무 판단                  분석가 · 감사 · 데이터 추출
  즉시 반영, ms 응답                       분 단위 지연 허용
```

결제 성공 여부나 취소 가능 여부 같은 **업무 판단은 운영 DB를 기준**으로 합니다. 복제본은 반영 지연이 있어 판단 근거로 쓰면 틀릴 수 있습니다. 같은 데이터가 두 곳에 있어도 됩니다. 어느 쪽을 보느냐는 조회 요구사항이 정합니다.

### 반영 지연의 원인과 규모

Lakehouse에 데이터가 늦게 보이는 것은 장애가 아니라 설계입니다. 지연은 Writer의 **커밋 주기**와 같습니다.

```text
결제 (t=0)
  ├─ ① 운영 DB 커밋            즉시        ← 화면은 여기를 읽는다
  ├─ ② Kafka 발행              수십 ms
  ├─ ③ Writer 배치 대기 → 커밋  0 ~ 커밋 주기 ← 지연의 대부분
  └─ ④ 조회 화면 갱신           0 ~ 갱신 주기
```

| 구간 | 소요 | 원인 |
| --- | --- | --- |
| ① 앱 → 운영 DB | 즉시 | 트랜잭션 커밋. 사용자는 지연을 느끼지 않는다 |
| ② 앱 → Kafka | 수십 ms | 브로커 저장까지 확인(`acks=all`) |
| ③ Kafka → Iceberg 커밋 | 0 ~ 커밋 주기 (평균 절반) | Writer가 이벤트를 **모았다가** 한 번에 Parquet 파일을 만들고 스냅샷을 커밋한다. 이벤트마다 커밋하면 수 KB짜리 파일이 폭발해 조회가 느려지고 메타데이터가 비대해진다 |
| ④ 커밋 → 조회 화면 | 0 ~ 갱신 주기 | 대시보드가 다시 조회하는 주기. 즉시 조회하면 0 |

| 환경 | 커밋 주기 | 체감 지연 | 파일 생성 |
| --- | --- | --- | --- |
| 로컬 PoC | 30초 | 실측 15초 안팎, 화면 갱신 15초를 더하면 최대 45초 | 테이블당 2분에 4개 |
| 운영 제안 | 1~5분 | 목표 5분 이내 | 테이블당 시간당 12~60개 → 일 단위 병합 |

커밋 주기는 "반영 지연 ↔ 파일 수"의 절충입니다. 짧게 잡으면 빨리 보이지만 작은 파일이 쌓여 조회 성능이 떨어지고 병합 작업이 늘어납니다. 그래서 커밋 주기는 짧게 두고 **일 단위 병합(compaction)** 으로 큰 파일로 합치는 것이 운영 원칙입니다([06 운영 원칙](06-consistency-and-operations.md) 5장). 결제 직후 운영 DB에는 있고 Lakehouse에는 없는 순간이 반드시 있으므로, 업무 판단은 운영 DB가 합니다. [주문·결제 샘플](../examples/order-payment-sample/README.md)의 조회 화면 ④가 이 지연을 실측해 보여 줍니다.

## 2. 경과 기간 기준 분담의 문제점

데이터의 나이로만 나누면 다음 상황이 생깁니다.

- 5년 전 메시지도 사용자가 대화방을 스크롤할 때 즉시 보여야 합니다.
- 최근 거래 데이터도 여러 서비스와 연결해서 분석해야 합니다.
- 오래된 거래도 고객센터에서 빈번하게 조회할 수 있습니다.

그래서 계층을 **조회 요구사항**으로 정의합니다.

| 계층 | 배치 기준 | 대표 용도 |
| --- | --- | --- |
| Serving | 짧고 예측 가능한 응답 시간이 필요한 조회 | 대화방 메시지, 마이페이지 거래 목록 |
| Lakehouse | 대규모 이력 보관과 SQL 처리 | 전체 거래 분석, 감사 조회, 데이터 추출 |
| Search | 검색 조건과 관련도 기반 조회 | 메시지 본문, 상품명 검색 |

Lakehouse에는 처음부터 전체 이력을 쌓습니다. Serving과 Search에는 각각 필요한 범위만 유지합니다. Trino를 과거 메시지 API에 연결하는 것은 가능하지만, SQL 조회 가능 여부와 사용자 화면의 응답 시간 만족 여부는 별개입니다. 목표 동시 접속과 데이터 규모로 검증하기 전에는 Serving 저장소가 화면을 맡습니다.

## 3. 전사 데이터 플랫폼 구성도

```text
업무 서비스 / 업무 DB (회원·주문·채팅·결제)
         │
    이벤트 발행 (Outbox) / CDC
         │
       Kafka
         │
         ├─ Serving Consumer ──── ScyllaDB 등 (최근 범위, ms 조회)
         │
         ├─ Iceberg Writer ────── Iceberg 테이블   ◀── 이번 구축 범위
         │                          ├─ 파일: MinIO
         │                          └─ 테이블 관리: Catalog
         │
         └─ Search Consumer ───── OpenSearch (본문 색인)

Query API
    ├─ ScyllaDB
    ├─ OpenSearch
    └─ Trino ── Catalog 확인 + MinIO 파일 읽기
```

- 세 계층은 **같은 Kafka 이벤트**를 각자의 Consumer Group으로 읽습니다. 서로의 진행 상태에 영향을 주지 않습니다. 단, Consumer Group 분리는 처리 진행을 분리할 뿐 공유 Kafka의 용량이나 장애까지 격리하지는 않습니다.
- 세 저장소는 서로 다른 시점에 갱신됩니다. 화면에서 허용할 지연과 "방금 쓴 메시지가 아직 검색되지 않는 경우"의 동작을 정해야 합니다.
- Serving(ScyllaDB)과 Search(OpenSearch)는 데이터량과 조회 패턴을 확인한 뒤 채택 여부를 정합니다. 이번 구축 범위는 Lakehouse와 그 수집 경로입니다.

## 4. 서비스별 역할 분담

| 서비스 | 기존 DB · 서비스 저장소가 담당 | Lakehouse에서 활용 |
| --- | --- | --- |
| 회원 | 로그인, 현재 회원 정보, 권한, 동의 상태 | 가입·탈퇴 추이, 고객군별 구매 분석 |
| 주문 | 주문 생성, 현재 상태, 취소 가능 여부 판단 | 장기 주문 이력, 상품별 판매·취소 분석 |
| 결제 | 승인·취소·환불 처리, 중복 결제 방지 | 결제 성공률, 주문과 결제의 불일치 점검 |
| 채팅 | 메시지 전송·조회, 읽음 처리, 대화방 권한 | 이용량, 응답 시간, 정책에 따른 장기 이력 |
| 파일 | 업로드·다운로드·미리보기·삭제 (저장소만 MinIO로) | 파일 사용량과 접근 이력 분석 (필요 시) |

왼쪽 열의 기능은 이번 구축으로 바뀌지 않습니다. 오른쪽 열은 지금은 여러 DB를 따로 뒤져야 답할 수 있는 질문들입니다.

## 5. 활용 사례

### 회원·주문 통합 분석 (첫 번째, PoC 대상)

회원 DB와 주문 DB에 나뉘어 있는 데이터를 `customer_id`로 연결합니다.

- **회원 유형별 주문 수·주문 금액.** 개인·법인, 등급, 가입 채널별로 일·월 주문 수와 금액, 유형별 취소율.
- **회원별 재주문 횟수.** 첫 주문 이후 몇 번 더 주문했는가, 재주문 간격은 며칠인가, 재주문율이 유형별로 다른가.
- **가입 후 첫 주문까지 기간.** 가입 시각과 첫 `ORDER_CREATED` 시각의 차이. N일 안에 첫 주문에 이르는 비율.

| 단계 | 테이블 | 목적 |
| --- | --- | --- |
| ① 수집 이력 | `member_events`, `order_events` | 가입·유형 변경·탈퇴, 주문 생성·취소를 사건 단위로 보존 |
| ② 정제 데이터 | `members`, `member_type_history`, `orders` | 현재 회원 상태, 유형 변경 이력(시작·종료 시각), 주문 단위 정리 |
| ③ 분석 테이블 | `daily_orders_by_member_type`, `member_reorder_summary` | 유형별 일 주문 수·금액·취소율, 회원별 첫 주문일·재주문 횟수·마지막 주문일 |

**회원 유형은 시점을 정해야 합니다.** "지금 VIP인 회원의 지난달 주문"과 "지난달 주문 당시 VIP였던 주문"은 다른 숫자입니다. 유형 변경 이력(`member_type_history`)을 남겨야 후자를 계산할 수 있고, 회원 DB의 현재 상태만으로는 전자밖에 안 됩니다. 주문마다 그 시점의 유형을 붙이려면 주문 시각이 유형 이력의 시작·종료 구간에 들어가는 행을 조인합니다.

결제 이벤트(`payment_events`)를 같은 방식으로 붙이면 결제 성공률, 취소·환불 현황, 주문·결제 불일치 후보까지 같은 구조에서 확장됩니다. [주문·결제 샘플](../examples/order-payment-sample/README.md)이 이 확장 형태를 먼저 구현해 두었습니다. 한 주문에 결제 시도와 환불이 여러 건 붙으므로, 단순 조인 후 합산하지 않고 주문·결제 시도·환불을 각각의 단위로 두고 집계 규칙을 정합니다.

### 회원·채팅 데이터 분석 (두 번째)

①의 회원·주문 연결에 채팅 이벤트를 하나 더 붙입니다.

```text
가입 ──▶ 첫 주문 ──▶ 채팅 문의 ──▶ 재주문        (시간 →)
                      └─ 문의 여부별 재주문율 비교
                      └─ 문의→첫 응답 시간
```

| 분석 질문 | 필요한 데이터 |
| --- | --- |
| 상담 받은 고객이 재주문을 더 하는가? | ①의 재주문 집계 + 상담 시작 이벤트 |
| 상담 채팅의 응답 시간은? | 상담 시작 · 첫 응답 시각 |
| 어느 시간대에 상담이 몰리는가? | 대화방·메시지 발송 시각 |

채팅은 본문이 아니라 **메타데이터**(대화방 ID·메시지 ID·발송 시각, 발송·수신·실패 이벤트, 상담 시작·첫 응답 시각, 첨부파일 ID·크기·종류)부터 수집합니다. 본문의 장기 보관·검색·요약은 접근 권한과 삭제 정책을 정한 뒤 확장합니다. 회원 식별자는 시스템마다 다를 수 있으므로 `customer_id` 매핑 테이블을 먼저 만듭니다. 회원 등급처럼 시간이 지나며 바뀌는 값은 해석을 정합니다. "현재 VIP인 회원의 과거 구매"와 "구매 당시 VIP였던 회원의 구매"는 다른 분석입니다.

## 6. 기존 파일 서비스와의 관계

파일 업로드·다운로드 애플리케이션은 그대로 두고 저장소만 MinIO로 옮깁니다. 파일용 `files` Bucket과 Lakehouse용 `lakehouse` Bucket은 분리하고, 계정도 분리합니다. 파일 서비스는 Iceberg나 Trino를 거치지 않습니다.

| 데이터·기능 | 우선 배치 |
| --- | --- |
| 주문·결제 현재 상태, 이벤트 처리 상태 | 기존 DB |
| 이벤트 장기 이력 · 통합 분석 | Kafka → Writer → MinIO(lakehouse), Trino 조회 |
| PDF·이미지·첨부파일 원본 | 파일 애플리케이션 → MinIO(files) |
| 파일 소유자 · 공유 권한 · 업무 정보 | 기존 DB |
| 파일 사용 이력 · 문서 추출 정보 분석 | 필요 시 Lakehouse로 전달 |

같은 MinIO 클러스터를 쓰면 용량과 IO를 나눠 씁니다. 대량 분석 쿼리가 파일 다운로드를 느리게 하지 않는지 확인합니다. 파일 이전 절차는 [MinIO: 04 기존 파일 애플리케이션 이전](../../minio/concepts/04-file-app-migration.md) 참고.
