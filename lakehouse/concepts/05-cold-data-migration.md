# 콜드 데이터 이관

> 운영 DB의 오래된 데이터를 Lakehouse로 옮기고 DB에서 정리합니다. 순서는 **복사 → 검증 → 삭제**이고, 삭제보다 검증이 먼저입니다.

## 1. 콜드 데이터의 정의

콜드 데이터는 "오래된 데이터"가 아닙니다. 다음 세 조건을 **모두** 만족하는 데이터입니다.

- 조회 빈도가 낮다.
- 변경이 드물다.
- 조회 지연을 어느 정도 허용할 수 있다.

3년 전 거래라도 고객이 마이페이지에서 빠르게 조회해야 한다면 콜드가 아닙니다. 이 경우 화면에 필요한 **요약은 DB에 남기고 상세 이력만** 옮깁니다.

## 2. 이관 기준 예시

아래 기간은 정책을 설명하기 위한 예시입니다.

| 데이터 | 이관 기준 | 확인할 점 |
| --- | --- | --- |
| 이벤트 이력 | 발생 후 6개월 경과 | 재처리·중복 확인에 아직 필요한지 |
| 완료된 거래 | 완료 후 1년 경과 | 취소·환불·정정 가능성이 남았는지 |
| Audit Log | 발생 후 3개월 경과 | 조회 성능·보관·접근 정책 |
| 사용자 활동 로그 | 발생 후 1개월 경과 | 서비스 화면이 직접 쓰는지 |
| 메시지 | 오래되고 조회 빈도가 낮음 | 과거 메시지도 즉시 표시해야 하는지 |

수정 가능한 데이터는 "생성일이 오래됐다"는 조건만으로 이관 대상을 정하면 안 됩니다. 상태·최종 변경 시각·버전을 포함해 확정합니다.

## 3. 절차

```text
운영 DB (주문)                          Lakehouse (order_events)
[ 콜드 (24개월↑) | 핫 ]                 [ 전체 이력 ]
       │ ① 선정  ② 복사 ──────────────────▶ │
       │                                    ▼
       │                            ③ 검증: 건수 · 금액 합계 · 샘플 대조
       │ ◀───── 모두 일치할 때만 ─────────────┘
       ▼
④ DB 정리: 플래그 → 유예 → 삭제
                                     ⑤ 과거 조회 경로 (Query API)
                                        최근 24개월 → DB (ms)
                                        그 이전 → Trino (초 단위, 화면에 표시)
```

1. **대상 선정.** 기준을 명시합니다. 예: 마지막 변경 후 24개월 경과, 업무 종료 상태(배송 완료·환불 완료). 법정 보관 의무가 있는 항목은 제외합니다.
2. **복사.** 초기 적재로 이미 Lakehouse에 있으면 건너뜁니다. 없으면 배치로 복사합니다.
3. **검증.** 건수·금액 합계·샘플 레코드를 DB와 대조합니다. 불일치가 하나라도 있으면 4단계로 가지 않습니다.
4. **DB 정리.** 아카이브 플래그 → 유예 기간 → 삭제 순서로 진행합니다. 되돌릴 수 있는 단계를 둡니다.
5. **과거 조회 경로.** Query API가 조회 기간에 따라 DB 또는 Trino로 보냅니다. 응답 시간 차이를 화면에 반영합니다.

⑤ 조회 경로가 준비되기 전에는 DB에서 지우지 않습니다. Serving 저장소(ScyllaDB 등)에서 TTL로 만료시키기 전에 Lakehouse 적재 완료를 확인하는 기준도 필요합니다. 만료가 적재보다 빠르면 데이터가 사라집니다.

## 4. 이관 방식 — 처음에는 Kafka 없이도 가능

이미 DB에 쌓인 콜드 데이터를 옮기는 작업이라면 Kafka가 반드시 필요하지는 않습니다.

```text
운영 DB (확정된 과거 이력) ──▶ 정기 배치 (기간별로 나누어 읽기) ──▶ Iceberg 지원 Writer
                                                                 ├─▶ MinIO (파일)
                                                                 └─▶ Catalog (테이블 커밋)
```

| 방식 | 적합한 상황 |
| --- | --- |
| 정기 배치 | 변경이 끝난 과거 데이터를 매일·매주 이관. **가장 단순, 첫 시작으로 적합** |
| 초기 적재 + CDC | 과거 데이터도 수정되며 변경분을 계속 반영해야 함 |
| Kafka 병행 적재 | 신규 이벤트를 발생 시점부터 Lakehouse에도 보관 |

현재 목적이 DB에 누적된 콜드 데이터 정리라면, 변경이 끝난 이벤트 이력부터 배치로 검증하는 방식이 단순합니다. 이후 신규 이벤트를 Kafka로 계속 적재하는 구조로 확장합니다.

## 5. 삭제 전 확인 목록

| 검증 | 확인 내용 |
| --- | --- |
| 이관 범위 | 어떤 기간·ID까지 옮겼는지 기록 |
| 데이터 일치 | 건수뿐 아니라 ID 누락·중복, 금액 합계 |
| 변경 충돌 | 복사 이후 원본이 수정되지 않았는지 (상태·최종 변경 시각·버전) |
| 조회 가능 | Trino에서 실제 필요한 조건으로 조회 |
| 복구 가능 | 백업과 복구 절차 확인 |
| 서비스 영향 | 기존 API가 삭제된 데이터를 DB에서 계속 찾지 않는지 |

DB에서 행을 지워도 디스크 사용량이 즉시 줄지 않을 수 있습니다. 공간 회수 방법은 DB 종류와 저장 구조별로 따로 확인합니다.

## 6. 삭제 정책을 구분해야 하는 이유

CDC로 변경을 수집하는 구조에서는 다음 일이 생깁니다.

```text
DB에서 오래된 주문 삭제 ──▶ CDC가 DELETE 수집 ──▶ 분석 테이블에서도 삭제
```

DB 용량을 줄이려고 삭제했는데 Lakehouse에서도 사라지는 문제입니다. 반대로 원본의 모든 삭제를 무시하는 것도 틀립니다. 개인정보 삭제 요청은 모든 저장소에 전파돼야 합니다.

| 목적 | 필요한 처리 |
| --- | --- |
| 업무 DB의 최신 상태 복제 | 변경·삭제를 분석 테이블에도 반영 |
| 장기 이력 보관 | 별도 이력 테이블에 보존 |
| DB 보관 기간 종료에 따른 정리 | 아카이브에서 유지할지 명시 (기본: 유지) |
| 실제 업무상 삭제·개인정보 삭제 | 필요한 저장소까지 삭제 전파, 과거 스냅샷·백업 처리 기간 명시 |

"보관 기간 종료에 따른 DB 정리"와 "실제 삭제 요청"을 이벤트 종류(`eventType`)로 구분합니다. 전자는 아카이브에서 유지하고, 후자는 세 계층 모두에 전파합니다.

## 7. 조회 경로

```text
사용자·관리자 ──▶ 조회 API ──┬─ 최근 데이터 ──▶ 운영 DB
                            └─ 과거 데이터 ──▶ Trino ──▶ Lakehouse
```

최근·과거를 한 화면에서 이어 조회하면 경계 구간의 누락·중복, 정렬, 페이지 처리를 설계해야 합니다. 초기에는 과거 이력 조회나 대량 다운로드를 **별도 기능**으로 제공하면 구현과 성능 검증이 쉽습니다. 고객 마이페이지의 과거 주문이나 채팅 스크롤에 적용하려면 별도 성능 검증이 필요합니다.
