# 단계별 구축과 PoC 계획

> 제품 도입 순서가 아니라 **활용 사례 하나의 완성**을 기준으로 단계를 나눕니다. 주문·결제부터 시작하고, 2단계 완료 기준을 통과하지 못하면 3단계로 가지 않습니다.

## 1. 단계

| 단계 | 권장 범위 | 완료 기준 |
| --- | --- | --- |
| 1. 요구사항 확정 | 활용 사례 한 가지(주문·결제 통합 분석), 조회 패턴, 응답 시간, 반영 지연, 보관 정책 | 측정 가능한 목표 확정 |
| 2. 수집·보관 검증 (PoC) | 원본 → Kafka → Writer → Iceberg·MinIO·Catalog → Trino | 누락·중복·재시작·재처리 검증 통과 |
| 3. 활용 사례 ① 구현 | 수집 이력·정제·분석 테이블, 결제 성공률·불일치 후보, 필요 시 Query API | 목표 부하에서 응답 시간 충족 |
| 4. 콜드 데이터·운영 보강 | 콜드 데이터 이관, 삭제 전파, 복구, 모니터링, 유지보수 자동화 | 장애·복구 시나리오 통과 |
| 5. 도메인 확장 | 회원·채팅 연결, 공통 규약으로 새 시스템 추가, Search 계층 검토 | 기존 기능 영향 없이 데이터 추가 |

1~2단계가 PoC 범위입니다. 메시지는 순차 조회, 읽기 직후 일관성, 본문 검색, 삭제와 첨부파일까지 고려할 범위가 넓으므로 통합 거래내역 한 종류로 먼저 검증합니다.

## 2. PoC에서 확인할 것

- 테스트 이벤트 N건이 Iceberg 테이블에 건수·금액 일치로 반영되는가
- Writer 강제 종료 후 재시작 시 누락·중복이 없는가
- 이벤트 발생 → Trino 조회까지 지연이 목표 안인가
- 스냅샷 시점 조회와 되감기 재처리가 되는가
- 병합·스냅샷 만료 작업이 조회를 방해하지 않는가

로컬에서는 [로컬 PoC](../examples/local-poc/README.md)가 1단계(MinIO + Catalog + Trino)와 2단계(Kafka Connect Iceberg Sink)를 나눠 검증합니다.

## 3. PoC에서 미루는 것

- Flink 도입. 스트림 조인·이벤트 시간 집계가 필요해질 때 검토합니다.
- ScyllaDB·OpenSearch 채택. 데이터량과 조회 패턴 확인 후 결정합니다.
- 메시지 본문 보관. 개인정보 정책과 함께 별도 검토합니다.

## 4. 첫 구축 결과물과 성공 기준

대상은 주문·결제·환불 + 최소한의 회원 식별 정보입니다.

| 결과물 | 성공 기준 |
| --- | --- |
| 일별 주문·결제·환불 현황 | 같은 기준 시점의 원본 집계와 일치 |
| 주문·결제 불일치 후보 | 반영 지연과 실제 오류를 구분 |
| 과거 거래 조회·다운로드 | 업무에서 요구하는 시간 안에 완료 (예: 1년치 조인 집계 p95 30초) |
| 장애 후 재처리 | 누락과 잘못된 중복 집계 없이 복구 |
| 콜드 데이터 이관 | 검증한 범위만 DB에서 정리 |
| 반영 지연 | 이벤트 발생 → Trino 조회 5분 이내 (예시, 1단계에서 확정) |

## 5. 검증할 효과

- **통합 조회 개발 감소.** 새 지표 요구가 API 개발이 아니라 SQL 작성으로 끝나는가.
- **운영 DB 부담 완화.** 분석·추출 쿼리를 Trino로 옮긴 뒤 DB 부하와 야간 배치 시간이 줄어드는가.
- **이력 보관 비용.** 콜드 데이터를 옮긴 뒤 DB 용량·백업 시간이 줄고, 객체 저장소 비용이 그보다 낮은가.
- **지표 일관성.** 결제 성공률 같은 숫자를 팀마다 다르게 내지 않게 되는가.

비교 기준은 "같은 이력을 운영 DB에 두었을 때의 스토리지·백업·성능 비용"입니다.

## 6. 결정이 필요한 항목

| 항목 | 제안 | 결정자 |
| --- | --- | --- |
| 초기 대상 | 주문·결제 이벤트 한 종류(이벤트 이력 테이블) | 데이터 플랫폼 · 커머스 |
| 담당 조직 | 플랫폼(Kafka·MinIO·Trino·Catalog), 도메인팀(이벤트 발행·테이블 의미) | 조직장 |
| 성능 목표 | 대표 쿼리 3개와 p95 응답 시간 | 분석 소비 부서 |
| 반영 지연 | 허용 지연(예: 5분)과 "방금 쓴 데이터가 아직 없을 때"의 화면 동작 | 서비스 기획 |
| 보관 기준 | 데이터 종류별 보관 기간·삭제 기준. "5~10년"은 검토 항목으로 | 법무 · 보안 · 도메인 |
| 수집 방식 | Outbox 우선, 레거시는 CDC | 도메인 개발 |
| Writer · Catalog | Kafka Connect Iceberg Sink · REST Catalog (구현체 선정) | 플랫폼 |

가장 먼저 정리할 네 가지: ① 과거 데이터의 서비스 조회 성능 가정, ② Catalog·Writer 선정, ③ 초기 수집의 정합성 방식, ④ 원본과 조회 모델의 책임 구분.

## 7. 비용 산정 항목과 용량 계획

| 항목 | 포함 내용 |
| --- | --- |
| 저장 (MinIO) | 디스크 용량 × Erasure Coding 계수(예: EC 4+2 → ×1.5), 스냅샷 보관 여유, 파일 Bucket 분 |
| Kafka 보관 | 보관 기간(예: 7일) × 일 유입량. 재처리 창을 얼마나 둘지가 곧 디스크 |
| 연산 노드 | Trino Coordinator 1 + Worker N, Kafka Connect Worker, Catalog 서비스 |
| 네트워크 | MinIO ↔ Trino 읽기 트래픽. 같은 랙·AZ 안에 두면 최소 |
| 운영 | 유지보수 작업 스케줄러, 모니터링, 백업 저장소, 담당 인력 |

```text
연간 용량 = 일 이벤트 수 × 평균 이벤트 크기(JSON)
          × Parquet 압축률 (보통 1/3 ~ 1/5)
          × 365 × EC 계수 (예: 1.5) × 스냅샷 여유 (예: 1.2)
```

예시(가정치, 1단계에서 실측으로 교체): 일 500만 건 × 1KB ≈ 5GB/일 → Parquet 후 ≈ 1.2GB/일 → 연간 논리 ≈ 440GB → 물리 ≈ 800GB/년 → 10년 ≈ 8TB. 회원·채팅 추가 시 별도 산정. 서버 배치는 [Kafka: 생태계 서버 배치 방안](../../kafka/concepts/15-deployment-layout-options.md)과 [MinIO: 02 배포 형태와 서버 스펙](../../minio/concepts/02-deployment-topology.md) 참고.
