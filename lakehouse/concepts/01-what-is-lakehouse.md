# Lakehouse란 무엇인가

> 파일 저장소 위에 테이블 관리 기능을 얹고, SQL 엔진으로 조회하는 구조입니다. 세 층이 각각 다른 제품이고, 각각 따로 교체할 수 있습니다.

## 1. 왜 검토하는가

우리 서비스는 회원·주문·채팅·결제가 각자의 DB를 가집니다. 여기서 세 가지 문제가 반복됩니다.

- **서비스별 데이터 분산.** 한 고객의 전체 모습은 어느 DB에도 없습니다.
- **반복되는 통합 조회 개발.** 마이페이지, 고객센터, 경영 지표가 요구될 때마다 여러 DB를 잇는 API나 배치를 새로 만듭니다. 같은 조인을 팀마다 다시 구현합니다.
- **과거 데이터 증가.** 수년치 이력이 운영 DB에 남아 용량과 조회 성능을 압박합니다. 지우자니 감사·분석에 필요하고, 두자니 서비스가 느려집니다.

통합 조회는 매번 새 프로젝트가 아니라, 한 곳에 모인 데이터를 SQL로 조회하는 일이어야 합니다. 그 "한 곳"이 Lakehouse입니다.

## 2. Data Lake와 무엇이 다른가

Data Lake는 다양한 데이터를 **파일로** 쌓는 구조입니다. 파일만 쌓으면 다음 질문에 답하기 어렵습니다.

- 어떤 파일들이 지금의 거래 테이블에 속하는가?
- 기록하는 중에 조회해도 되는가?
- 컬럼이 추가되면 기존 파일은 어떻게 읽는가?
- 수정 전 데이터를 다시 볼 수 있는가?

Lakehouse는 이 질문에 답하는 **테이블 포맷**(Iceberg)을 파일 저장소 위에 두고, SQL 엔진(Trino)이 그 테이블을 읽게 한 구조입니다.

## 3. 세 층 구조

```text
┌──────────────────────────────────────────────┐
│ SQL 엔진 · Trino                              │  조회
│ SQL을 받아 테이블을 찾고, 파일을 읽어 조인·집계    │
└──────────────────────┬───────────────────────┘
                       │ 어떤 파일을 읽어야 하나?
┌──────────────────────▼───────────────────────┐
│ 테이블 관리 · Iceberg + Catalog                │  관리
│ 스키마, 스냅샷, 파일 목록. 어떤 파일이 테이블인지  │
└──────────────────────┬───────────────────────┘
                       │ 파일은 어디에 있나?
┌──────────────────────▼───────────────────────┐
│ 객체 저장소 · MinIO                            │  저장
│ Parquet 데이터 파일과 Iceberg 메타데이터 파일      │
└──────────────────────────────────────────────┘
```

| 층 | 제품 | 하는 일 | 바꿀 수 있는가 |
| --- | --- | --- | --- |
| 저장 | MinIO | 파일을 그대로 보관하고 반환 | S3 등 다른 객체 저장소로 교체 가능 |
| 관리 | Iceberg + Catalog | 파일 목록·스키마·스냅샷 관리 | 테이블 포맷은 데이터 자산이라 가장 바꾸기 어려움 |
| 조회 | Trino | SQL 실행, 조인·집계 | Spark 등 다른 엔진을 같은 테이블에 붙일 수 있음 |

Iceberg는 별도 서버가 아닙니다. Writer와 Trino가 같은 포맷 규칙을 따르고 같은 Catalog를 바라보는 방식입니다.

## 4. 이번 구축의 목적

> Kafka로 수집한 업무 데이터를 MinIO에 지속적으로 보관하고, Iceberg 테이블로 관리하여 Trino에서 통합 조회한다.

세 가지 과제로 나눕니다.

| 과제 | 현재 문제 | 목표 |
| --- | --- | --- |
| 장기 이력 보관 | 수년치 거래·메시지가 운영 DB에 남아 있음 | 전체 이력을 Lakehouse에 저장. 운영 DB는 최근 범위만 유지 |
| 운영 DB 부담 완화 | 통계·추출 쿼리가 서비스 DB에서 실행됨 | 분석·추출 쿼리는 Trino에서 실행 |
| 서비스 간 분석 | DB마다 따로 뽑아 스프레드시트에서 결합 | 회원·주문·채팅·결제를 한 SQL에서 조인 |

범위에 넣지 않는 것도 명확히 합니다. 실서비스 화면의 실시간 조회 대체, 업무 트랜잭션 처리는 운영 DB의 역할로 남깁니다. 자세한 분담은 [04 운영 DB와의 역할 분담](04-role-split-and-platform-layers.md)에서 다룹니다.
