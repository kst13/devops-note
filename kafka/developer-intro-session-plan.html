개발자를 위한 Kafka 소개

Kafka를 처음 접하는 개발자에게 동작 원리를 이해시키고, 실무에서 바로 쓸 수 있는 사용 원칙까지 전달하는 45–60분 발표 구성입니다. 예시는 "주문 이벤트" 하나로 통일해 처음부터 끝까지 같은 시나리오로 끌고 갑니다.

1

왜 Kafka인가

5분

목표 — 개념에 들어가기 전에 "왜 배워야 하는지"부터 답한다. 여기서 청중을 잡으면 뒤가 쉽다.

① 동기 HTTP 직접 호출의 한계

  • 강결합 — 이벤트를 만든 쪽이 모든 소비자의 주소·스펙·인증을 알아야 하고, 소비자가 늘 때마다 발행자 코드를 수정
  • 장애 전파 — 부가 기능(알림)의 장애가 타임아웃 대기·스레드 고갈을 타고 핵심 기능(주문)까지 무너뜨림
  • 트래픽 스파이크 — 주문이 10배로 뛰면 그 10배가 뒷단 서비스에 그대로 꽂힘

② Kafka가 푸는 문제

  • 비동기 전달 — 발행자는 토픽에 기록하고 끝. 소비자가 늘어나도 발행자 코드는 그대로 (강결합 해소)
  • 버퍼링 — 스파이크는 Kafka에 쌓이고, 각 서비스는 자기 처리 속도대로 꺼내 감 (스파이크 흡수)
  • 독립 소비 — 소비자가 30분 죽어 있어도 발행자는 영향 없고, 복구되면 멈춘 지점부터 이어서 처리 (장애 격리)

③ 전통 MQ(큐)와의 결정적 차이

RabbitMQ 같은 큐는 소비자가 ack하면 메시지를 삭제한다 — 메시지의 소유권이 소비자에게 넘어가는 모델. Kafka는 메시지를 보존 기간 동안 그대로 두고, 컨슈머 그룹별로 "어디까지 읽었는지"(오프셋)만 이동한다. 다중 구독과 리플레이가 모두 여기서 나온다.

핵심 메시지 Kafka는 "빠른 메시지 큐"가 아니라, 여러 소비자가 각자의 속도로 읽어 가는 분산 로그다.

발표 팁사내에서 실제로 겪었던(또는 겪을 법한) 장애 전파 사례로 시작하면 몰입도가 크게 올라갑니다. 이후 모든 그림·데모를 "주문 이벤트" 예시 하나로 통일하세요.

2

핵심 개념 — 토픽, 파티션, 컨슈머 그룹

15분

목표 — 그림 네 장으로 Kafka의 구조를 머리에 심는다. 가장 시간을 많이 쓰는 섹션. (저장소 문서: concepts/01~03)

① 토픽 · 파티션 · 오프셋

  • 토픽 = 이벤트가 흐르는 논리 채널. 파티션 = 토픽을 나눈 물리 단위이자 순서 보장과 병렬 처리의 단위
  • 오프셋 = 파티션 안에서의 위치 번호. 메시지는 지워지지 않고 컨슈머가 "어디까지 읽었는지"만 이동

② 메시지 키가 파티션을 정한다

  • 키의 해시로 파티션이 정해진다 — 같은 키(같은 주문 ID)는 항상 같은 파티션 → 그 키의 이벤트 순서가 보장됨

③ 컨슈머 그룹

  • 파티션을 나눠 갖는 소비자 묶음 — 그룹 = 하나의 애플리케이션, 컨슈머 = 그 앱의 인스턴스. 그룹이 다르면 서로 독립적으로 전체를 읽음

④ 복제 — 브로커가 죽어도 되는 이유

  • 파티션마다 리더 1 + 팔로워 N. 브로커가 죽으면 팔로워가 리더로 승격 — 데이터가 안 사라지고, 클라이언트는 알아서 재연결
핵심 메시지 파티션은 순서 보장의 단위이자 병렬 처리의 단위다. 이 한 문장이 Kafka 설계의 절반이다.

발표 팁컨슈머 그룹(그림 6)이 개발자들이 가장 헷갈려하는 지점입니다. "그룹 = 하나의 애플리케이션, 컨슈머 = 그 앱의 인스턴스"라는 비유가 잘 통합니다.

3

개발자가 반드시 알아야 할 동작 특성

10분

목표 — 실무에서 사고가 나는 지점을 미리 알려준다. 온보딩 목적이라면 이 섹션이 실질적으로 가장 중요.

① 순서 보장은 파티션 안에서만

  • 전역 순서는 없다 — 순서가 필요한 단위(주문 ID 등)를 메시지 키로 잡아 같은 파티션에 모은다

② 중복 수신은 전제 조건 — 멱등 컨슈머

  • 기본 전달 보장은 at-least-once — 재시도·리밸런싱 과정에서 같은 메시지가 두 번 올 수 있다 → 이벤트 ID 중복 체크, UPSERT 등으로 멱등하게 작성

③ 컨슈머 랙(lag)

  • 최신 메시지와 읽은 위치의 차이 — 처리 속도가 발행 속도를 못 따라가면 쌓인다 → 모니터링 대상

④ 리밸런싱

  • 컨슈머가 들어오거나 나가면(배포·스케일 조정·장애) 파티션을 다시 분배 — 그 동안 소비가 잠시 멈추고 중복 가능성이 생긴다
핵심 메시지 중복 수신은 버그가 아니라 전제 조건이다. 컨슈머는 반드시 멱등하게 만들어라.

발표 팁"exactly-once 아니냐"는 질문이 거의 항상 나옵니다. "트랜잭션 기능으로 가능하지만 제약이 많아, 실무 기본기는 멱등 컨슈머"라고 정리해 두세요.

4

우리 환경에서 쓰는 법 — 사용 원칙

10분

목표 — 개념을 우리 인프라의 구체적인 규칙으로 연결한다. (저장소 문서: concepts/12-usage-principles.md 기반)

  • 접속 템플릿 — 부트스트랩 서버 주소, 보안 설정(SASL/TLS)이 포함된 복사용 설정 스니펫 제공
  • 토픽 규칙 — 네이밍 컨벤션, 파티션 수·보존 기간 기본값, 생성 신청 절차
  • 프로듀서 권장 설정과 이유 — acks=all(리더+팔로워 확인 후 성공 처리 → 무손실), retries/멱등 프로듀서(재시도해도 중복 발행 방지)
  • 컨슈머 권장 설정 — 수동 커밋 여부, 그룹 ID 규칙(앱 이름 기반), 재처리 전략
  • 안티패턴 — 요청-응답(RPC) 대체로 쓰지 말 것, 대용량 파일 전달 금지, 무한 보존을 DB처럼 쓰지 말 것
핵심 메시지 설정을 외우지 말고 템플릿을 복사하라 — 사용 원칙 문서가 항상 최신 기준이다.

발표 팁운영(클러스터 설계, KRaft, 인증서)은 "운영은 이렇게 되어 있고, 여러분은 접속 템플릿만 쓰면 됩니다" 슬라이드 한 장으로 끝내세요. 개발자 세션에서 운영 내용이 길어지면 집중이 끊깁니다.

라이브 데모 (선택)

8분

목표 — 그림 6(컨슈머 그룹)을 눈으로 확인시킨다. 개념이 한 번에 이해되는 순간. (저장소 예제: examples/compose-3node-kraft-plaintext)

# ① 클러스터 기동 후, 파티션 3개짜리 토픽 생성
docker compose exec kafka /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 \
  --create --topic order-events --partitions 3 --replication-factor 3

# ② 터미널 2개에 같은 그룹으로 컨슈머 실행 → 파티션이 나뉘는 것 확인
docker compose exec kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 \
  --topic order-events --group order-app

# ③ 프로듀서로 키를 바꿔가며 발행 → 같은 키는 같은 컨슈머로만 가는 것 확인
docker compose exec kafka /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 \
  --topic order-events \
  --property parse.key=true --property key.separator=:

# ④ --from-beginning 으로 새 그룹 실행 → 리플레이(재소비) 시연

발표 팁라이브 데모는 반드시 사전 리허설 + 실패 대비 녹화본을 준비하세요. 시간이 부족하면 ②(파티션 분배)만 보여줘도 효과의 80%는 나옵니다.

예상 질문과 답변 요지

Q. 메시지가 유실될 수 있나요?
프로듀서가 acks=all + 재시도로 보내고 복제 팩터가 3이면 브로커 장애에도 유실되지 않는다 — 우리 권장 설정이 이미 그렇게 되어 있다(섹션 4로 연결).
Q. Redis pub/sub이나 RabbitMQ와 뭐가 다른가요?
구독 중이 아니면 놓치는 pub/sub, 소비하면 사라지는 큐와 달리 Kafka는 보존되는 로그 — 여러 소비자가 독립적으로 읽고, 과거 시점부터 재소비할 수 있다.
Q. 순서가 꼬이면 어떡하죠?
순서는 파티션 안에서만 보장되므로 순서가 필요한 단위(주문 ID 등)를 메시지 키로 잡는 것이 답 — 키 설계가 곧 순서 설계다(그림 5로 연결).
Q. 그냥 REST 호출하면 안 되나요? 언제 Kafka를 써야 하죠?
즉시 응답이 필요한 조회·명령은 REST가 맞다. 결과를 기다릴 필요가 없는 사실의 전파(주문 생성됨, 결제 완료됨)가 Kafka의 자리다 — Kafka는 요청-응답 대체재가 아니다.
