# 토픽 요청하기 (직접 만들지 마세요)

> 토픽은 아무나 만들 수 없습니다 — 서비스 계정에는 토픽 생성 권한이 없고, 브로커의 자동 생성(`auto.create.topics.enable`)도 꺼져 있습니다. 오타 토픽·무관리 토픽을 막고, 모든 토픽이 표준 설정(RF3 + `min.insync.replicas=2`)으로 만들어지게 하기 위한 정책입니다.

## 1. 요청 양식

새 토픽이 필요하면 아래 정보를 담아 요청하세요.

| 항목 | 예 | 정하는 기준 |
| --- | --- | --- |
| 토픽명 | `commerce.order.created` | [01 토픽 명명 규칙](01-topic-naming.md) 준수 |
| 파티션 수 | 6 | 아래 2장 — 동시에 몇 개 컨슈머가 병렬 처리할지 |
| 보관 기간 | 7일 | 아래 3장 — 재처리·장애 복구에 필요한 기간 |
| 용도 | 주문 생성 이벤트 발행 | 한 줄로. 카탈로그·감사에 사용 |
| 요청 방법 | 팀 프로세스에 맞게 지정 | 예: `ows-infra` 리포에 토픽 정의 PR / 티켓 |

→ 관리자가 표준 설정(RF3, `min.insync.replicas=2`)으로 생성하고, 요청한 서비스 계정에 read/write 권한(ACL)을 부여합니다.

## 2. 파티션 수 정하기

파티션 수는 그 토픽의 **최대 병렬 처리 수**입니다. 같은 컨슈머 그룹 안에서 한 파티션은 한 컨슈머만 읽으므로, 파티션이 6개면 컨슈머를 7개 띄워도 1개는 유휴 상태가 됩니다.

- 출발점: **목표 처리량 ÷ 컨슈머 1대의 처리량**. 예: 초당 3,000건을 처리해야 하고 컨슈머 1대가 초당 500건을 처리하면 최소 6파티션.
- 트래픽 성장을 감안해 **여유 있게** 잡으세요. 파티션은 나중에 **늘릴 수는 있어도 줄일 수 없고**, 늘리는 순간 `hash(key) % N`의 N이 바뀌어 **같은 key가 다른 파티션으로 가기 시작합니다**(기존 순서 보장이 그 시점에 끊깁니다).
- 반대로 무한정 크게 잡지도 마세요. 파티션마다 브로커의 파일 핸들·복제 트래픽·리더십 관리 비용이 붙습니다. 일반 서비스 토픽은 3~12 사이에서 시작하는 것이 무난합니다.
- **전역 순서**(모든 메시지의 순서)가 필요한 특수한 경우는 파티션 1개로 요청합니다. 병렬성을 포기하는 대신 순서를 얻습니다. 복제는 그대로(RF3)라 가용성은 잃지 않습니다.

## 3. 보관 기간 정하기

Kafka는 컨슈머가 읽어도 메시지를 지우지 않고, **보관 기간이 지나야** 지웁니다. 보관 기간은 곧 **"컨슈머가 장애에서 복구하거나 데이터를 재처리할 수 있는 시간 창"** 입니다.

- 기본 감각: 주말 낀 장애 복구를 고려하면 **7일**이 무난한 출발점입니다.
- 재처리(백필) 요구가 있으면 그 기간만큼 늘립니다. 예: "최근 30일 이벤트로 통계를 다시 만들 수 있어야 한다" → 30일.
- 저장 비용은 대략 `유입량 × 복제 수(3) × 보관 기간`으로 늘어납니다. 압축([03 프로듀서](03-producer.md))을 켜면 보통 3~5배 줄어듭니다.

## 4. 요청 전 체크리스트

- [ ] 토픽명이 `<도메인>.<엔티티>.<이벤트>` 3단계 규칙에 맞는가
- [ ] 비슷한 토픽이 이미 있지 않은가 (같은 이벤트를 두 곳에서 발행하면 컨슈머가 갈라집니다)
- [ ] 순서가 필요한 이벤트들을 한 토픽으로 묶었는가 ([01 토픽 명명 규칙](01-topic-naming.md) 3장)
- [ ] 파티션 수를 늘릴 일이 머지않아 생기지는 않는가 (key 순서가 흐트러지므로 처음에 여유 있게)
