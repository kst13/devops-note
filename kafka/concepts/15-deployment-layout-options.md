# Kafka 생태계 서버 배치 방안 (검토 중)

> 실서버 3대에 Kafka 브로커와 주변 생태계(Connect, Schema Registry, 모니터링, 관리 UI)를 어떻게 나눠 올릴지에 대한 **검토 문서**입니다. 아직 방안이 확정되지 않았으며, 두 방안을 비교해 기록합니다. 모니터링 스택 자체의 목적·구축 방법은 [14-monitoring-prometheus-grafana](14-monitoring-prometheus-grafana.md) 참고.

## 배치 대상 컴포넌트

| 컴포넌트 | 역할 | 대략 상주 메모리 | HA 방법 |
| --- | --- | --- | --- |
| Kafka Broker ×3 | 메시지 저장·전달 (KRaft, 서버당 1개) | 힙 + OS 페이지 캐시(여유 메모리 전부) | RF3 + `min.insync.replicas=2` |
| Kafka Connect ×2 | Debezium 등 커넥터 실행 | 1~1.5GB | 분산 모드 워커 2개 페일오버 |
| Schema Registry ×2 | 스키마 저장·호환성 검사 | 0.5~1GB | 무상태(상태는 `_schemas` 토픽) — 2개면 리더 선출로 HA |
| Prometheus | 메트릭 수집·알람 평가 | 0.5~1GB | 단일 (이 규모에서 허용) |
| Alertmanager | 알람 라우팅·발송 | ~50MB | 단일 |
| kafka_exporter | 컨슈머 그룹 lag 수집 | ~50MB | 단일 |
| Grafana | 대시보드 (뷰어) | ~300MB | 단일 — 죽어도 수집·알람은 지속 |
| Kafka UI | 운영자용 클러스터 조회·관리 | ~500MB | 단일 |
| Admin Portal | 자체 관리 포털 | 0.5~1GB | 단일 (성격에 따라 재검토) |

## 어느 방안이든 공통 필수 사항

- **kafka_exporter 포함** — JMX만으로는 컨슈머 lag이 나오지 않습니다. lag은 모니터링 우선순위 1번입니다.
- **Schema Registry는 2개** — 1개면 그 서버 장애 시 새 스키마 등록·신규 앱의 스키마 조회가 실패하는 단일 장애점입니다. 무상태라 인스턴스 추가만으로 HA가 됩니다.
- **모든 컨테이너에 `mem_limit`** — Kafka는 남는 메모리를 OS 페이지 캐시로 쓰므로, 동거 프로세스가 메모리를 먹으면 OOM 전에 브로커 읽기 성능이 먼저 떨어집니다.
- **알람 규칙은 Grafana가 아니라 Prometheus 쪽에** — Grafana가 죽어도 알람이 계속 오게 합니다.
- **Watchdog 알람** — 브로커 서버에 모니터링을 얹는 이상, 그 서버 장애 = 알람 정지라는 운명 공유는 3대 안에서 구조적으로 해소되지 않습니다. 항상 발화하는 Watchdog 알람을 두고, 그것이 끊기면 외부(별도 헬스체크 또는 일일 점검)에서 감지합니다.
- **UI 접근 통제** — Kafka UI는 토픽 삭제까지 가능한 도구입니다. 내부망 + 관리자 한정으로 접근을 제한합니다.

## 방안 A — 제안받은 구성 (보완 반영판)

외부에서 권장안으로 제안받은 배치에 공통 필수 사항(kafka_exporter 추가, SR 2호기)을 반영한 형태입니다.

```text
서버1                       서버2                       서버3
──────────────────         ──────────────────         ──────────────────
Kafka Broker               Kafka Broker               Kafka Broker
Kafka Connect ①            Kafka Connect ②            Kafka UI
Schema Registry ①          Prometheus                 Grafana
Admin Portal               kafka_exporter (추가)       Alertmanager
                                                      Schema Registry ② (추가)
```

- 장점: 제안 원안과의 차이가 적어 도입 협의가 수월. 부하가 세 대에 흩어져 있음.
- 단점: 사람이 보는 도구(Admin Portal, Kafka UI, Grafana)가 세 서버에 흩어져 사용자 접근 방화벽을 서버마다 열어야 함. 서버1에 JVM이 3개(브로커 + Connect + SR + Portal) 몰려 추가 부담 약 2.5~3GB로 가장 무거움. 어느 서버가 죽어도 데이터 경로 컴포넌트가 하나씩 걸림(단, SR·Connect는 이중화로 서비스 영향은 없음).

## 방안 B — 역할 분리 구성 (데이터 플레인 / 관제)

"데이터 경로에 필요한 것"과 "사람이 보는 것"을 서버 단위로 분리한 배치입니다.

```text
서버1 (데이터 플레인)         서버2 (데이터 플레인)         서버3 (관제 서버)
──────────────────         ──────────────────         ──────────────────
Kafka Broker               Kafka Broker               Kafka Broker
Kafka Connect ①            Kafka Connect ②            Prometheus + Alertmanager
Schema Registry ①          Schema Registry ②          kafka_exporter
                                                      Grafana
                                                      Kafka UI
                                                      Admin Portal
```

- 장점: **서버3의 브로커 외 컴포넌트는 전부 죽어도 데이터 경로에 무영향** — 장애 시나리오가 단순해짐(아래 표). 사용자 접근은 서버3만 열면 되어 방화벽 단순. 브로커 외 추가 부담이 서버1 ≈ 2GB, 서버2 ≈ 2GB, 서버3 ≈ 2.5GB로 균등.
- 단점: 서버3에 단일 인스턴스들이 몰려, 서버3 장애 시 모니터링과 관리 도구를 한꺼번에 잃음(Watchdog으로 보완). 제안 원안과 차이가 커서 재협의 필요.

| 죽는 서버 | 일어나는 일 | 서비스 영향 |
| --- | --- | --- |
| 서버1 | 브로커 페일오버, Connect ②가 커넥터 인계, SR ②가 계속 서빙 | 없음 |
| 서버2 | 위와 대칭 | 없음 |
| 서버3 | 브로커 페일오버. 모니터링·UI만 상실 | 데이터 경로 무영향, 관측만 상실 |

## 비교 요약

| 기준 | 방안 A | 방안 B |
| --- | --- | --- |
| 데이터 경로 생존성 | 이중화로 확보 (컴포넌트가 흩어져 시나리오 복잡) | 이중화 + 서버 단위 격리 (시나리오 단순) |
| 메모리 균형 | 서버1 편중 (~3GB) | 균등 (~2GB씩) |
| 사용자 접근 방화벽 | 서버 3대 모두 개방 필요 | 서버3만 개방 |
| 관측 상실 범위 (해당 서버 장애 시) | 수집(2번)과 화면(3번)이 나뉘어 부분 상실 | 서버3 장애 시 일괄 상실 (Watchdog 보완) |
| 도입 협의 비용 | 낮음 (제안 원안 유지) | 재협의 필요 |

## 결정 전에 확인할 것

- [ ] **Admin Portal의 성격** — 관리자 전용이면 어느 방안이든 무방. 개발자들이 상시 쓰는 서비스(토픽 요청 창구 등)가 되면 가용성이 필요하므로, 방안 B에서도 서버1/2로 옮기는 변형을 검토.
- [ ] **Kafka UI와 Admin Portal의 역할 중복** — 겹치면 하나로 정리(운영 부담·보안 표면 축소).
- [ ] **각 서버의 실제 가용 메모리**(`free -h`) — 위 어림값(브로커 외 2~3GB)이 페이지 캐시를 침식하지 않는지 확인. 여유가 없으면 모니터링 스택의 별도 소형 VM 분리를 재검토.
- [ ] 알람 수신 채널(메신저/호출) 및 Watchdog 외부 감지 방법.
