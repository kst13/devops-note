# 실서버 클러스터 토폴로지

로컬 k3d의 노드 컨테이너들이 실서버에서는 머신 몇 대, 어떤 역할로 배치되는지 다룹니다. server가 3대인 이유(etcd 쿼럼), API 고정 접점, Control Plane 보호 같은 온프레미스 구축의 설계 결정과, 도입 전 검증 단계에서 무엇을 확인해야 하는지를 정리합니다.

## 머신 = 노드 = 역할 하나

가장 먼저 잡아야 할 감각은 단순합니다. **머신(물리 서버 또는 VM) 1대 = 노드 1개 = 역할 1개**. server와 agent는 한 머신 안에 같이 있는 것이 아니라 각각 별도의 머신입니다. 각 머신에서 실제로 돌아가는 것은 k3s(또는 RKE2) 프로세스 하나이며, server 머신에서는 `k3s server`로, agent 머신에서는 `k3s agent`로 실행한다는 차이만 있습니다.

로컬 [k3d 구성](06-k3d-architecture-and-request-path.md)은 이 머신들을 컨테이너로 흉내 낸 것이므로, 실서버로 가면 컨테이너 하나하나가 진짜 머신 1대로 바뀝니다. "server 3대 + agent 3대" 구성이라면 머신이 총 6대 필요하다는 뜻입니다.

## 규모별 구성

| 구성 | 머신 수 | 형태 | 용도 |
| --- | --- | --- | --- |
| 최소 | 1~3대 | server 1 + agent 0~2 | 학습, 개발 환경. server 장애 시 클러스터 제어 정지 |
| 소규모 절충 | 3대 | server 3대가 워커 겸임 | HA는 확보하되 머신을 아끼는 구성. 워크로드가 가벼울 때만 |
| 표준 운영 | 3 + N대 | server 3 + agent N | 온프레미스 프로덕션의 기본형 |

```text
                 ┌─ 로드밸런서 or VIP ─┐
                 │   (API 고정 접점)    │
        ┌────────┼─────────┬───────────┘
   server-1   server-2   server-3     ← Control Plane 3대 (각각 etcd 포함)
        │        │          │
   ─────┴────────┴──────────┴─────
   agent-1   agent-2   agent-3 ...    ← 워커: 워크로드 규모만큼
```

agent 수는 워크로드가 결정합니다. 시작은 2~3대로 하고 부족하면 추가하면 됩니다. agent 추가는 [설치 스크립트에 토큰을 넘겨 조인](05-k3s-cluster-installation.md)하는 것이 전부라, 클러스터 확장은 쿠버네티스 운영에서 가장 쉬운 작업에 속합니다.

## server가 3대인 이유: etcd 쿼럼

클러스터의 모든 상태는 etcd에 저장되고, etcd는 데이터 일관성을 다수결(쿼럼)로 지킵니다. 과반이 살아 있어야 클러스터가 동작합니다.

| server 수 | 과반 | 허용 장애 | 평가 |
| --- | --- | --- | --- |
| 1대 | 1 | 0대 | 학습·개발 전용 |
| 2대 | 2 | 0대 | 1대보다 오히려 위험 — 어느 한 대만 죽어도 과반 미달로 정지 |
| 3대 | 2 | 1대 | 실무 표준 |
| 5대 | 3 | 2대 | 대규모에서만 |

짝수는 의미가 없고(허용 장애 수가 홀수-1과 같음), 실무 대부분은 3대입니다. server 1대 구성에서 그 머신이 죽으면 이미 떠 있는 앱은 계속 돌지만 새 배포·자동 복구·kubectl 제어가 전부 멈춥니다. "운영"이라 부르려면 3대가 출발점입니다.

로컬 k3d 실습도 노드가 3개(server 1 + agent 2)라 숫자가 우연히 같지만, 그쪽은 HA가 아닙니다. HA의 3은 **server(Control Plane) 3대**를 뜻합니다.

## API 고정 접점

server가 3대가 되면 새 문제가 생깁니다. agent들과 운영자 kubectl이 바라볼 "Control Plane 주소"가 하나여야 하는데 server가 3대라는 것. 그래서 server들 앞에 고정 접점을 둡니다.

- 사내 L4 로드밸런서가 있으면 그것으로 6443 포트를 server 3대에 분산
- 없으면 kube-vip 같은 도구로 가상 IP(VIP)를 server들이 나눠 갖게 구성

kubeconfig의 `server:` 주소에는 이 고정 접점(예: `https://k8s-api.example.internal:6443`)을 적습니다. 로컬 k3d에서 serverlb 컨테이너가 하던 역할을 실서버에서는 LB/VIP가 하는 것으로, [요청 경로](06-k3d-architecture-and-request-path.md)의 구조 자체는 동일합니다. 온프레미스 구축에서 처음 마주치는 설계 결정이 보통 이것입니다.

## Control Plane 보호

표준 구성에서 server에는 워크로드를 올리지 않습니다. taint를 걸어 Control Plane 역할만 하게 하고 앱은 전부 agent에 배치합니다. Control Plane이 앱 부하로 흔들리면 클러스터 전체가 흔들리기 때문입니다.

```bash
kubectl taint nodes server-1 node-role.kubernetes.io/control-plane=:NoSchedule
```

소규모 절충 구성(3대 겸임)은 이 taint를 걸지 않는 선택이며, HA와 머신 수를 맞바꾸는 대신 Control Plane 안정성을 일부 양보하는 것임을 알고 선택해야 합니다.

## 도입 단계와 검증 체크리스트

쿠버네티스를 처음 도입하는 조직이 실패하는 지점은 대부분 배포판 선택이 아닙니다. 설치는 어느 배포판이든 하루 이틀이면 되고, 그다음에 오는 장애 복구·업그레이드·스토리지·모니터링에서 막힙니다. 검증은 "클러스터가 뜨는가"가 아니라 "우리가 이것을 운영할 수 있는가"를 확인하는 과정이어야 합니다.

권장 단계는 다음과 같습니다.

1. **개념 학습 (로컬, 2~4주)** — k3d에서 이 시리즈의 [워크로드 실습](03-pod-deployment-service.md)과 [설정·볼륨](04-config-and-volume.md)을 익힙니다.
2. **운영 검증 PoC (실서버, 1~2개월)** — VM 5대(server 3 + agent 2)로 표준 토폴로지를 구성하고 아래 체크리스트를 돌립니다. VM이 3대뿐이면 절충 구성으로 검증합니다. 사양은 검증용 기준 server 대당 4 vCPU / 8GB, agent는 올릴 워크로드에 따라 그 이상.
3. **파일럿** — 실제 서비스 후보 하나를 올려 배포 → 장애 → 복구 사이클을 겪은 뒤 도입을 판단합니다.

PoC에서 확인할 항목:

| 항목 | 검증 내용 |
| --- | --- |
| HA·장애 복구 | server 1대를 강제 종료해도 API와 워크로드가 유지되는가. etcd 스냅샷 백업·복원을 실제로 수행 |
| 노드 장애 | agent를 `kubectl drain`으로 비웠을 때 Pod가 다른 노드로 옮겨 가는가 |
| 업그레이드 | 마이너 버전 하나를 실제로 올려 보고 절차와 소요 시간을 기록 |
| 스토리지 | 사내 스토리지(NFS, SAN, Ceph 등)와 CSI 연동. 온프레미스 최대 난관이므로 반드시 PoC 범위에 포함 |
| 네트워크·인그레스 | 사내망 기준으로 외부 → 서비스 경로 구성. LB가 없으면 MetalLB 등 대안 검증 |
| 모니터링·로깅 | Prometheus + Grafana를 올려 "장애 시 무엇을 보게 되는가"까지 |
| 실워크로드 | 데모 앱이 아닌 실제 후보 서비스로 배포 → 롤백 → 스케일 |

마지막으로 배포판 관점 하나. 이 시리즈의 실서버 기준은 k3s이지만, 운영 배포판으로 [RKE2를 선택](02-ways-to-run-kubernetes.md)하더라도 이 문서의 토폴로지는 그대로 적용됩니다. k3s와 RKE2는 같은 회사 작품이라 설치·조인·설정 방식이 거의 같고, PoC를 운영과 같은 배포판으로 하면 검증 결과가 곧 도입 근거가 됩니다. 그리고 도입 판단에는 기술 검증만큼 "전담 인원을 확보할 수 있는가"가 중요합니다. 쿠버네티스는 설치해 두면 굴러가는 물건이 아니라 인증서 만료, 버전 업그레이드, 노드 장애가 주기적으로 오는 운영 대상입니다.
