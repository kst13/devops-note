# 외부 트래픽 진입점

클러스터 안의 라우팅(Ingress → Service → Pod)은 준비됐는데, 정작 사용자를 서버 3대 중 어느 IP로 보낼 것인가 — 온프레미스에서 web/WAS를 운영할 때 가장 먼저 부딪히는 문제를 다룹니다. 클라우드라면 LoadBalancer 타입 Service가 실제 로드밸런서를 만들어 이 문제를 대신 풀어 주지만, 온프레미스에서는 직접 설계해야 합니다.

## 문제 정의: 첫 홉이 비어 있다

[Ingress 라우팅 예제](../examples/ingress-routing/README.md)까지 마치면 클러스터 내부 경로는 완성입니다. 남은 것은 그 앞입니다.

```text
사용자 → ???              → Traefik(Ingress) → Service → Pod
         └ 여기가 문제      └───────── 여기부터는 이미 해결 ─────────┘
```

`???`에 들어갈 답은 두 가지를 정해야 합니다. DNS가 가리킬 IP는 무엇인가, 그리고 그 IP를 가진 노드가 죽으면 어떻게 되는가.

## k3s ServiceLB의 실체를 먼저 이해하기

k3s에서 Traefik의 Service는 LoadBalancer 타입이고, 내장 ServiceLB가 이를 구현합니다. 그런데 ServiceLB는 진짜 로드밸런서가 아닙니다. 모든 노드의 80/443 포트를 열어 그 노드로 들어온 트래픽을 Traefik으로 넘겨줄 뿐입니다. `kubectl get svc -n kube-system traefik`의 EXTERNAL-IP에 노드 IP들이 그대로 나열되는 이유입니다.

의미는 이렇습니다. **3대 중 어느 노드 IP로 접속해도 Ingress 라우팅은 동작합니다.** 그래서 진입점 문제는 "어떻게 분산하나"가 아니라 "사용자에게 어떤 주소를 주고, 그 주소의 가용성을 어떻게 지키나"로 좁혀집니다.

## 선택지 비교

| 방식 | 동작 | 장점 | 한계 |
| --- | --- | --- | --- |
| DNS 라운드로빈 | 도메인에 노드 IP 3개를 모두 등록 | 추가 구성 요소 없음 | 노드 장애 시 DNS 캐시(TTL)가 만료될 때까지 해당 IP로 간 사용자는 실패 |
| VIP (keepalived) | 가상 IP 1개를 노드들이 나눠 가짐. 보유 노드가 죽으면 다른 노드가 수 초 안에 이어받음 | IP가 하나라 DNS·방화벽 관리 단순, 빠른 failover | 능동-대기라 트래픽 분산은 안 됨 (한 노드로 들어와 클러스터가 내부 분산) |
| MetalLB | LoadBalancer 타입을 온프레미스에서 실제로 구현 (L2 모드는 VIP와 유사, BGP 모드는 진짜 분산) | 쿠버네티스 네이티브 — Service 선언만으로 IP 할당 | ServiceLB와 역할이 겹쳐 k3s에서는 `--disable servicelb` 필요, BGP는 네트워크 장비 협조 필요 |
| 외부 L4 장비 | 사내 로드밸런서가 노드 3대로 분산 | 분산·헬스체크·운영 모두 검증된 방식 | 장비가 있어야 함 |

## 추천 경로

판단 기준은 단순합니다. **사내에 L4 로드밸런서가 있으면 그것이 정답입니다.** 노드 3대의 80/443을 백엔드로 등록하고 헬스체크를 걸면 끝이며, 분산과 failover를 모두 얻습니다.

없다면 **keepalived VIP로 시작**하는 것을 추천합니다. 구성이 단순하고(각 노드에 keepalived 데몬 + 설정 파일), 사용자에게는 IP 하나만 알리면 되고, 노드 장애 시 수 초 안에 VIP가 이동합니다. 능동-대기라서 진입 트래픽이 한 노드로 몰리지만, 그 노드는 첫 홉일 뿐이고 실제 부하는 Ingress와 Service가 클러스터 전체 Pod로 분산하므로 web/WAS 규모에서는 대부분 문제가 되지 않습니다. 진입 노드의 대역폭이 병목이 되는 규모라면 그때 MetalLB(BGP)나 장비 도입을 검토합니다.

DNS 라운드로빈은 "장애 시 일부 사용자 실패"를 감수할 수 있는 내부 도구 수준에서만 씁니다.

## API 진입점과 혼동하지 않기

[실서버 클러스터 토폴로지](07-production-cluster-topology.md)에서 다룬 6443 API 고정 접점은 kubectl과 agent가 쓰는 관리용 진입점이고, 이 문서의 80/443은 사용자 트래픽 진입점입니다. 별개의 문제이지만 해법(VIP 또는 LB)이 같으므로, keepalived를 구성한다면 VIP 두 개(API용, 서비스용)를 한 번에 잡는 것이 관례입니다.

## 확인 방법

VIP든 LB든, 구성 후에는 반드시 장애 시나리오로 검증합니다.

```bash
# 평상시: VIP(예: 10.0.0.100)로 접속 확인
curl -H "Host: a.example.test" http://10.0.0.100/

# VIP를 보유한 노드를 강제 종료한 뒤 수 초 내 같은 명령이 다시 성공하는지 확인
```

이 검증이 [토폴로지 문서의 PoC 체크리스트](07-production-cluster-topology.md)에서 말하는 "네트워크·인그레스" 항목의 실체입니다. 다음 문서 [web/WAS 워크로드 설계](10-web-was-workload-design.md)에서는 이 진입점 뒤에서 실제로 트래픽을 받는 워크로드를 설계합니다.
