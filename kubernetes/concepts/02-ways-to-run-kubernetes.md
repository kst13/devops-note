# 쿠버네티스를 경험하는 방법들

같은 쿠버네티스라도 어떻게 실행하느냐에 따라 배우는 것이 다릅니다. 로컬 도구는 워크로드(YAML, kubectl)를 가르쳐 주지만 클러스터 운영은 가르쳐 주지 않고, 실서버 배포판은 설치·노드 관리·운영을, 관리형 서비스는 클라우드와의 결합을 가르쳐 줍니다. 이 문서는 그 선택지 전체를 비교하고, 이 시리즈가 k3d와 k3s를 기준으로 삼은 이유를 설명합니다.

## 로컬 실습 도구

| 도구 | 구조 | 특징 | 언제 고르나 |
| --- | --- | --- | --- |
| k3d | k3s를 Docker 컨테이너 안에서 실행 | 생성 수 초, 가벼움, 실서버 k3s와 같은 스택 | 이후 k3s로 서버를 운영할 계획일 때 (이 시리즈의 선택) |
| kind | 표준 업스트림 쿠버네티스를 Docker 컨테이너 안에서 실행 | 쿠버네티스 프로젝트 CI가 쓰는 사실상 표준 로컬 도구 | 업스트림과 100% 동일한 동작 검증, CI에서 일회용 클러스터 |
| minikube | VM 또는 컨테이너로 단일 클러스터 실행 | 애드온이 풍부, 역사가 김 | 튜토리얼 호환성이 필요할 때 |
| Docker Desktop / Rancher Desktop | 데스크톱 앱에 쿠버네티스 내장 | 설정 없이 체크박스 하나로 활성화 | 가장 낮은 진입 장벽으로 맛볼 때 |

kind는 로컬·CI 영역에서 전문가들이 가장 많이 쓰는 표준 도구입니다. 그럼에도 이 시리즈가 k3d를 기준으로 삼는 이유는 실서버 기준이 k3s이기 때문입니다. k3d는 k3s 그 자체를 Docker 안에서 돌리는 것이라 Traefik, ServiceLB, local-path 스토리지까지 실서버와 동일하게 경험되고, 로컬에서 배운 것과 서버에서 만나는 것 사이의 간극이 구조적으로 가장 작습니다. kubectl과 YAML 실습은 어느 도구에서든 동일하게 동작하므로, kind를 쓰고 있어도 [워크로드 실습](03-pod-deployment-service.md)을 그대로 따라올 수 있습니다.

## 브라우저 실습

설치 없이 브라우저에서 바로 실습하는 방법도 있습니다. Killercoda 같은 플레이그라운드는 계정만 만들면 터미널이 열린 클러스터를 제공합니다. 세션이 끝나면 사라지므로 학습용 일회 실습에만 적합하지만, 회사 노트북에 Docker를 깔 수 없는 상황 등에서 유용합니다.

## 실서버 직접 구축

서버에 직접 설치할 때의 선택지는 "부품"과 "조립"으로 구분하면 명확해집니다.

| 배포판 | 부품 | 조립 | 주 용도 |
| --- | --- | --- | --- |
| kubeadm | 표준 업스트림 그대로 | 직접 조립 — CNI·Ingress·스토리지 선택, etcd HA 설계, 인증서·업그레이드 관리 전부 수동 | 내부 구조 학습, CKA 자격증 기준 |
| RKE2 | 표준 업스트림 그대로 (etcd, ingress-nginx) | 완성품 — 한 줄 설치, 토큰 조인, CIS 보안 강화가 기본값 | 온프레미스 프로덕션 |
| k3s | 경량화 (sqlite 기본, 레거시 제거) | 완성품 — 한 줄 설치, 토큰 조인, Traefik 등 내장 | 엣지, 소규모 운영, 개발 환경, 학습 |

kubeadm은 모든 것을 직접 선택하고 조립하므로 쿠버네티스 내부 구조를 배우기에 가장 좋지만, 프로덕션에서 순수 kubeadm을 직접 유지하는 팀은 줄고 있습니다(쓰더라도 Kubespray 같은 자동화 도구를 통해 씁니다). RKE2는 kubeadm의 표준성을 유지하면서 설치·운영을 k3s 수준으로 단순화한 것으로, 온프레미스 신규 구축에서 기세가 강합니다. k3s와 RKE2는 같은 회사(SUSE/Rancher) 작품이라 설치·운영 방식이 거의 같아, k3s에서 쌓은 경험이 RKE2로 그대로 이어집니다. 대기업 상용 영역에는 Red Hat의 OpenShift가 별도로 존재합니다.

## 관리형 서비스

클라우드를 쓸 수 있다면 프로덕션의 다수는 EKS(AWS), GKE(Google), AKS(Azure) 같은 관리형입니다. 핵심은 Control Plane 운영이 통째로 사라진다는 것입니다. etcd 백업, API 서버 HA, 버전 업그레이드를 클라우드가 책임지고, 사용자는 워커 노드와 워크로드만 관리합니다.

관리형의 진짜 차별점은 클라우드 서비스와의 결합입니다. EKS를 예로 들면 Ingress를 만들면 실제 ALB가 자동 생성되고, IRSA/Pod Identity로 "이 Pod만 이 S3 버킷에 접근" 같은 IAM 권한을 Pod 단위로 부여하며, PersistentVolume이 실제 EBS 볼륨이 됩니다. 반면 비용이 들고, 클라우드별 결합이 깊어질수록 이식성은 줄어듭니다.

AWS 안에서는 쿠버네티스가 유일한 답이 아니라는 점도 알아둘 만합니다. ECS라는 AWS 자체 오케스트레이터가 있고, Helm·오퍼레이터 같은 쿠버네티스 생태계가 필요 없는 소규모 팀에는 ECS가 더 단순한 선택일 수 있습니다.

## 환경별 구성 전략

로컬부터 운영까지 어떤 조합으로 갈지도 설계 대상입니다. 원칙은 하나입니다. 아래(로컬·개발)는 싸고 가볍게 달라도 되지만, 스테이지는 운영의 축소판이어야 합니다.

| 환경 | 추천 | 이유 |
| --- | --- | --- |
| 로컬 | k3d 또는 kind | 빠른 생성·삭제, 비용 없음 |
| 개발 | k3s | 서버 한두 대로 충분, 낮은 리소스 |
| 스테이지 | 운영과 같은 배포판 (노드 수만 축소) | 운영 직전 마지막 검증 환경이므로 |
| 운영 | RKE2 (온프레미스) 또는 EKS 등 관리형 | 표준 구성, 보안, 지원 |

스테이지와 운영의 배포판이 다르면 Ingress 컨트롤러(Traefik vs ingress-nginx), LoadBalancer 구현, 스토리지 클래스 같은 "가장자리"의 차이가 스테이지에서 걸러지지 않고 운영에서 처음 터집니다. 워크로드 YAML은 어디서나 같지만 가장자리는 환경마다 다르기 때문입니다. 운영 규모가 크지 않다면 개발부터 운영까지 전부 k3s로 통일하는 것도 정당한 선택입니다. k3s도 프로덕션 인증 배포판입니다.

가장자리 차이에 대비하는 이식성 습관도 중요합니다. 예를 들어 Ingress에는 `ingressClassName`을 항상 명시합니다. 배포판의 기본값에 암묵적으로 기대면 환경을 옮길 때 의도가 깨집니다.

## 이 시리즈의 선택

이 시리즈는 로컬 k3d, 실서버 k3s를 기준으로 합니다. 목표가 "다양한 실행 방법을 이해하되, 배운 것을 실서버 설치·운영까지 같은 스택으로 이어가는 것"이기 때문입니다. 다음 문서인 [Pod, Deployment, Service](03-pod-deployment-service.md)에서 k3d로 실습을 시작하고, [k3s 클러스터 설치](05-k3s-cluster-installation.md)에서 같은 스택을 실서버에 올립니다.
