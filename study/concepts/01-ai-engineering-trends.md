# AI 엔지니어링 트렌드의 계보

## 학습 목표

- 프롬프트 엔지니어링부터 그래프 엔지니어링까지 각 용어가 무엇을 설계 대상으로 삼는지 구분합니다.
- 새 용어가 왜 생기는지, 어떤 문제가 먼저 오고 이름이 나중에 붙는지 이해합니다.
- 그래프 엔지니어링이 보편화된 뒤 생길 문제와 그 다음 단계를 예측합니다.

## 설계 단위가 커져 온 흐름

2026년 기준으로 AI 에이전트 개발 담론은 "모델을 더 똑똑하게"에서 "모델 바깥의 구조를 어떻게 짜느냐"로 옮겨왔습니다. 각 단계는 앞 단계를 대체하지 않고 감쌉니다.

| 순서 | 용어 | 설계 대상 | 등장 시기 |
| --- | --- | --- | --- |
| 1 | 프롬프트 엔지니어링 | 모델 호출 한 번을 어떻게 지시할까 | 2023 |
| 2 | 컨텍스트 엔지니어링 | 모델에 어떤 정보를 보여줄까 | 2025 |
| 3 | 하네스 엔지니어링 | 에이전트 하나의 실행 환경. 도구, 권한, 검증, 복구 | 2026 초 |
| 4 | 루프 엔지니어링 | 에이전트 하나가 사람 개입 없이 목표까지 반복하는 제어 구조 | 2026년 6월 |
| 5 | 그래프 엔지니어링 | 에이전트 여러 개의 조직. 노드, 전이, 승인 지점 | 2026년 7월 |

### 하네스 엔지니어링

하네스는 모델을 감싸는 실행 환경입니다. 에이전트가 어떤 도구를 쓰고, 무엇을 참고하고, 어디서 검증하고, 실패하면 어떻게 복구할지를 사람이 구성합니다. "에이전트 = 모델 + 하네스"라는 공식이 자주 인용됩니다. 모델 성능이 비슷해지면서 경쟁력이 모델 선택보다 하네스 품질로 옮겨갔습니다. LangChain이 모델을 바꾸지 않고 하네스만 손봐 벤치마크 순위를 30위에서 5위로 올린 사례가 대표적입니다.

### 루프 엔지니어링

"개발자가 에이전트에게 직접 프롬프트를 치지 말고, 에이전트에게 프롬프트를 주는 시스템을 설계하라"는 주장에서 나왔습니다. OpenClaw를 만든 Peter Steinberger가 용어를 만들었고, Claude Code를 이끄는 Boris Cherny도 자기 역할이 외부 실행 루프를 작성하는 쪽으로 옮겨갔다고 언급했습니다. `/loop` 같은 반복 실행 명령, 워크플로 스크립트, 서브에이전트 오케스트레이션이 실물입니다.

### 그래프 엔지니어링

여러 에이전트를 노드와 엣지로 엮은 조직을 설계합니다. 어떤 노드가 있는지, 어떤 전이가 허용되는지, 실행 중에 작업 그래프가 어떻게 바뀌는지가 대상입니다. 지식 그래프나 데이터 구조와는 다른 뜻입니다. 기술 자체는 새롭지 않습니다. LangGraph가 2024년 1월부터 노드와 엣지와 공유 상태 모델을 제공했고, AutoGen과 Google ADK도 같은 일을 했습니다. 2026년 7월에 생긴 것은 이름입니다.

### OpenClaw

Clawdbot에서 Moltbot을 거쳐 OpenClaw가 된 오픈소스 로컬 에이전트 런타임입니다. 사용자 컴퓨터에서 직접 작업을 실행하고, 메모리와 파일을 로컬에 두고 필요한 토큰만 모델에 보냅니다. 72시간 만에 GitHub 스타 6만을 넘겼습니다. 만든 사람이 루프 엔지니어링 용어를 만들고 OpenAI에 합류했기 때문에, "클로 → 루프 → 그래프"가 한 커뮤니티에서 이어진 흐름으로 읽힙니다.

## 그래프 엔지니어링은 비용 때문에 나왔나

절반만 맞습니다. 직접적인 계기는 비용보다 예측 불가능성입니다. 에이전트 하나가 루프를 돌게 두면 어디까지 갈지 통제가 안 됩니다. 그래서 "누가, 무엇을, 어떤 순서로, 어디서 사람 승인을 받는지"를 명시하자는 것이 출발점입니다. 구조가 생기면 노드마다 싼 모델을 배치하고 불필요한 반복을 잘라낼 수 있습니다. 비용 절감은 따라오는 효과입니다.

## 그래프가 보편화되면 생길 문제

소프트웨어 역사와 같은 길을 갈 가능성이 큽니다. 모놀리스에서 서비스 분리, 마이크로서비스 남발, 아무도 전체를 모르는 상태로 이어진 흐름입니다. 노드가 수십 개를 넘고 여러 팀이 각자 그래프를 만들기 시작하면 다음 문제가 예상됩니다.

- 조율 비용이 실행 비용을 넘어섭니다. 에이전트끼리 주고받는 메시지와 중간 요약이 실제 작업보다 토큰을 더 씁니다.
- 누구도 전체 그래프를 보지 못합니다. 노드 하나는 잘 동작하는데 시스템 결과가 틀리는 창발적 오류가 늘어납니다.
- 모델 업데이트가 그래프를 깨뜨립니다. 노드마다 특정 모델에 맞춘 프롬프트가 모델 교체 한 번에 연쇄로 어긋납니다.
- 정적 그래프는 경직되고 동적 그래프는 예측이 안 됩니다. 실행 중 스스로 바뀌는 그래프는 그래프를 만든 이유였던 통제력을 다시 잃습니다.
- 책임 경계가 흐려집니다. 그래프가 팀과 회사 경계를 넘으면 사고 났을 때 누구 소관인지 정리가 안 됩니다.

## 다음 단계 예측

두 방향으로 갈라질 것으로 봅니다. 둘은 선택지가 아니라 순서입니다.

### 1. 평가 엔지니어링 또는 AgentOps

노드 단위가 아니라 그래프 전체를 CI처럼 지속 평가하는 계층입니다. 노드별 비용을 회계처럼 추적하고, 모델이 바뀔 때 회귀를 자동으로 잡습니다. 관측 데이터로 하네스를 자동 진화시키는 연구가 이미 나오고 있어 가장 먼저 이름이 붙을 가능성이 큽니다.

### 2. 목표 엔지니어링

그래프를 사람이 그리는 것을 포기하는 단계입니다. 사람은 목표와 제약과 예산만 명시하고, 그래프는 에이전트가 생성하고 진화시킵니다. 사람의 일은 "무엇을 금지하고 어디까지 허용하느냐"로 좁혀집니다.

### 왜 1이 먼저인가

자율성이 올라간 층에는 항상 측정이 먼저 있었습니다.

- 컴파일러가 코드 생성을 맡은 것은 테스트로 결과를 검증할 수 있게 된 뒤입니다.
- 오토스케일링이 서버 배치를 맡은 것은 모니터링 지표가 먼저 있었기 때문입니다.
- 지금 에이전트가 스킬을 스스로 고르는 것도, 그 선택이 틀렸을 때 잡아내는 검증 루프가 하네스 안에 있기 때문입니다.

그래프 설계를 에이전트에게 넘기려면 "이 그래프가 저 그래프보다 낫다"를 판단할 신호가 있어야 합니다. 그 신호가 평가 계층입니다.

### "알아서 한다"는 것도 한 층 위의 하네스 안에서다

에이전트가 스킬을 알아서 고르지만, 스킬 목록과 권한 규칙과 훅은 사람이 정했습니다. 자율성이 올라간 것이 아니라 사람이 정의하는 층이 한 칸 위로 올라간 것입니다. 그래프도 같습니다. 에이전트가 그래프를 그리게 되면 사람은 "어떤 노드 종류가 허용되는가, 예산은 얼마인가, 어디서는 반드시 멈추는가"를 정의하는 메타 그래프를 짜게 됩니다.

## 목표 엔지니어링의 대가: 사람이 그래프를 판단하지 않게 된다

이것이 가장 불편한 부분입니다. 사람은 그래프 구조가 맞는지 직접 판단하지 않게 됩니다. 대신 판단 대상이 바뀝니다.

| 지금 | 그때 |
| --- | --- |
| 이 그래프의 구조가 맞는가 | 결과가 기준을 통과했는가 |
| 이 노드가 저 노드로 넘기는 것이 맞는가 | 실행이 금지선을 넘지 않았는가 |
| | 예산 안에서 끝났는가 |

이미 그렇게 하는 영역이 있습니다. 컴파일러가 만든 기계어를 사람이 검토하지 않고 테스트로 동작만 봅니다. 오토스케일러가 서버를 몇 대 띄웠는지 판단하지 않고 SLO와 비용 한도만 봅니다.

### 실제로 잃는 것

- 왜 그렇게 됐는지 모릅니다. 그래프를 사람이 안 그렸으니 결과가 나빴을 때 어느 구조가 문제였는지 아무도 설명하지 못합니다.
- 제약은 항상 불완전합니다. 사람이 적은 금지 조건은 사람이 상상한 실패만 막습니다. 에이전트는 제약을 다 지키면서 의도는 벗어나는 그래프를 찾아냅니다. 지표를 맞추려다 목적을 놓치는 굿하트 문제가 그래프 층에서 재현됩니다.
- 사고 났을 때 되돌릴 사람이 없습니다. 그래프를 이해하는 사람이 없으면 고치는 것도 에이전트에게 맡겨야 합니다.

### 예상되는 타협

전부 넘기는 것이 아니라 영역별로 갈라질 것입니다.

- 결과로 판단해도 되는 낮은 위험 영역은 사람이 그래프를 보지 않습니다.
- 의료, 금융, 인프라처럼 결과가 나온 뒤에는 늦는 영역은 사람이 계속 그래프를 검토하고 규제가 이를 강제합니다.
- 중간 지대를 위해 "생성된 그래프를 사람이 읽을 수 있게 설명하라"는 요구가 생깁니다. 생성된 코드를 리뷰하듯 생성된 그래프를 샘플링해 리뷰하는 관행이 나올 것입니다.

## 정리

지금까지 설계 단위는 호출, 환경, 반복, 조직으로 커져 왔습니다. 다음 단계는 단위가 더 커지는 것이 아니라 사람이 직접 설계하는 층이 한 칸 위로 올라가는 변화입니다. 그래프를 짜는 것이 아니라 그래프를 짜는 시스템의 목표와 한계를 짭니다. 용어는 늘 실제 고통이 먼저 온 다음에 붙습니다.
