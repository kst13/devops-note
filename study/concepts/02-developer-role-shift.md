# 개발자 역할의 변화와 준비

## 학습 목표

- 에이전트 시대에 개발자의 어떤 일이 사라지고 어떤 일이 남는지 구분합니다.
- 남는 일을 잘하기 위해 준비할 다섯 가지를 익히는 구체적인 방법을 정합니다.
- 각 항목이 익혀졌는지 스스로 확인하는 기준을 갖습니다.

## 개발자라는 직업은 없어지는가

"코드를 손으로 짜는 직업"은 상당 부분 없어집니다. 그러나 "시스템이 제대로 동작하는 것에 책임지는 사람"은 없어지지 않습니다. 이름이 남을지는 모르지만 역할은 남습니다.

실제 작업 세션을 보면 구분이 분명합니다.

| 에이전트가 한 일 | 사람이 한 일 |
| --- | --- |
| 코드를 읽고 원인을 추적 | 어느 브랜치가 진짜 의도인지 결정 |
| 수정, 빌드, 푸시 | stage를 되돌릴지, 강제 푸시를 할지 결정 |
| 시뮬레이션으로 검증 | 에이전트가 머지 방향을 잘못 이해했을 때 잡아냄 |

에이전트가 한 일은 더 빨라지고 싸집니다. 사람이 한 일은 자동화되지 않습니다. 그것은 코딩이 아니라 판단이고, 판단은 "이 시스템이 왜 이렇게 생겼고 무엇이 깨지면 안 되는가"를 아는 사람만 할 수 있습니다.

### 솔직한 전망

숫자는 줄어듭니다. 주니어 진입 자리, 화면을 찍어내는 일, 정해진 API를 붙이는 일은 이미 사라지는 중입니다. 자동화는 늘 새 일자리를 만들었다는 위로가 이번에도 통할지는 확실하지 않습니다. 이번에는 자동화 대상이 사고 자체라서 앞선 사례와 다릅니다.

### 남는 일

- 무엇을 만들어야 하는지 정의하는 일. 요구사항은 여전히 사람에게서 나옵니다.
- 결과가 맞는지 판단하는 일. 자율성이 올라갈수록 검증하는 사람의 가치는 오릅니다.
- 경계를 긋는 일. 무엇을 금지하고 어디서 멈출지 정하는 것은 책임질 수 있는 존재만 합니다.
- 사고가 났을 때 수습하는 일. 도메인과 시스템을 이해하는 사람이 없으면 복구가 안 됩니다.

문제를 푸는 것은 명령어를 아는 것이 아니라 감각입니다. 예를 들어 "호스트명이 바뀌었을 때 옛 프로세스가 옛 경로에 계속 쓰고 있을 수 있다"는 감각은 코드를 많이 짜 본 사람에게서 나옵니다. 앞으로 코드를 직접 안 짜는 세대가 그 감각을 어떻게 얻느냐는 아직 아무도 답을 모릅니다.

결론은 "개발자는 없어진다"보다 "개발자의 정의가 코드를 쓰는 사람에서 시스템을 책임지는 사람으로 바뀐다"에 가깝습니다. 전환에서 살아남는 것은 도구를 잘 쓰는 사람이 아니라 도구가 틀렸을 때 알아채는 사람입니다.

## 준비할 다섯 가지

남는 일을 거꾸로 뒤집으면 준비 목록이 됩니다.

### 1. 검증하는 힘

가장 중요합니다. 에이전트가 "완료했습니다"라고 할 때 그것이 진짜인지 확인하는 능력입니다. 머지 후 빌드가 깨졌을 때 코드 문제인지 로컬 환경 문제인지 가르는 데 필요한 것은 코딩 실력이 아니라 "패키지 버전이 lockfile과 다를 수 있다"는 의심입니다.

익히는 방법은 다음과 같습니다.

- 에이전트가 작업을 끝내면 결과를 읽기 전에 먼저 적습니다. "이게 맞다면 무엇이 관찰되어야 하는가?" 그 다음 결과가 그 관찰을 보여주는지 확인합니다. 보여주지 않으면 요구합니다.
- 지시에 검증 방법을 포함합니다. "고쳐줘"가 아니라 "고치고, 고쳐졌다는 것을 보여줘"입니다.
- 매주 하나씩 에이전트 결과를 믿지 않고 직접 재현합니다. 열 번에 한 번은 틀린 것을 잡게 되고, 그 한 번이 감각을 만듭니다.
- 테스트 코드를 직접 쓰지 않아도 됩니다. 대신 "이 기능의 테스트 케이스 목록"을 먼저 글로 적고 구현은 에이전트에게 시킵니다. 케이스를 떠올리는 것이 검증 능력입니다.

익혀졌다는 신호: 에이전트가 "완료"라고 했는데 찜찜해서 확인해 보니 실제로 빠진 것이 있는 경험이 한 달에 몇 번 생깁니다.

### 2. 코드 아래 층

프레임워크 사용법은 에이전트가 더 잘 압니다. HTTP, 프로세스, 파일시스템, 네트워크, DB 트랜잭션, 쿠키와 도메인 같은 기반 원리는 문제가 났을 때 원인을 가르는 기준이 됩니다. 이 항목만 따로 시간이 필요합니다.

- 문제가 생겼을 때 그 밑 원리를 한 층만 팝니다. 쿠키가 두 도메인 사이에 공유 안 되는 문제를 봤으면, 그 김에 쿠키 Domain 속성과 등록 가능 도메인을 30분 읽습니다. 주 1회면 충분합니다.
- 에이전트에게 설명을 시키되 "왜"를 세 번 묻습니다. 세 번째 답에서 보통 기반 원리가 나옵니다.
- 6개월에 하나 정도는 밑바닥 프로젝트를 합니다. HTTP 서버를 소켓으로 직접 짜 보기, 간단한 리버스 프록시 만들어 보기 같은 것입니다. 에이전트와 같이 해도 되지만 코드는 한 줄씩 읽으며 갑니다.

구체적인 목록은 [03 공부 목록: 코드 아래 층](03-study-roadmap-core.md)과 [04 공부 목록: 더 넓은 기반](04-study-roadmap-extended.md)에 있습니다.

익혀졌다는 신호: 에러 메시지를 봤을 때 검색하기 전에 "이건 아마 이 층의 문제겠다"는 가설이 먼저 떠오릅니다.

### 3. 도메인

서비스에서 어떤 사용자가 어떤 경로로 들어오고, 무엇이 깨지면 실제로 누가 곤란해지는지 아는 것은 에이전트가 대신하지 못합니다. "모바일 웹 사용자에게 안내 페이지를 보여줄 것인가"는 기술 결정이 아니라 사업 결정입니다. 이런 판단의 비중이 계속 커집니다.

- 기획서와 정책 문서를 개발 전에 읽습니다. 결정의 배경 회의록이나 기록을 찾고, 없으면 결정한 사람에게 직접 묻습니다.
- 사용자가 실제로 쓰는 것을 봅니다. CS 문의, 앱 리뷰, 로그의 실제 요청 패턴입니다.
- 기능 하나를 맡을 때마다 "이게 실패하면 누가 어떤 곤란을 겪나"를 한 문장으로 적습니다. 안 써지면 도메인 이해가 부족한 것입니다.
- 다른 직군의 언어를 익힙니다. 기획, 운영, 영업이 쓰는 용어와 그들이 중요하게 보는 숫자입니다.

익혀졌다는 신호: 기획자가 오기 전에 "이 기능은 이런 문제가 있을 텐데요"를 먼저 말하게 됩니다.

### 4. 에이전트에게 일 시키기

특정 도구 사용법은 반년마다 바뀝니다. 변하지 않는 것은 위임의 원리입니다.

- 지시를 쓸 때 세 가지를 구분해 적습니다. 목표(무엇이 되어야 하는가), 제약(무엇을 하면 안 되는가), 검증(어떻게 확인할 것인가). 예를 들어 "stage는 건드리지 말고, guide-page에 stage를 머지하고, 빌드가 통과하는 것을 보여줘"가 이 구조입니다.
- 작업을 "한 번에 확인 가능한 크기"로 쪼갭니다. 기준은 결과를 5분 안에 읽고 판단할 수 있는가입니다.
- 에이전트가 틀렸을 때 왜 틀렸는지 분류합니다. 지시가 모호했나, 컨텍스트가 부족했나, 모델이 잘못 판단했나. 앞의 둘은 내가 고칠 수 있고, 그 비율이 보통 절반이 넘습니다.
- 반복되는 지시는 파일로 남깁니다. CLAUDE.md, 스킬, 훅입니다. 이것이 하네스 엔지니어링의 실물입니다.

익혀졌다는 신호: 지시 한 번에 원하는 결과가 나오는 비율이 올라가고, 다시 시키는 횟수가 줄어듭니다.

### 5. 글로 남기기

가장 쉽고 가장 안 하는 것입니다. 에이전트는 코드는 읽지만 결정 이유는 기록에만 남습니다.

- 커밋 메시지에 "무엇을"이 아니라 "왜"를 씁니다. 무엇을 바꿨는지는 diff에 있고, 왜인지는 메시지에만 남습니다.
- 결정할 때마다 세 줄을 기록합니다. 무엇을 결정했나, 어떤 대안이 있었나, 왜 이것을 골랐나.
- 문제를 해결하면 원인을 한 문단으로 남깁니다. 이 한 문단이 다음에 같은 증상을 보는 사람의 하루를 아낍니다.
- 쓰기 부담을 줄이려면 에이전트에게 초안을 시킵니다. 세션 끝에 "오늘 결정과 이유를 정리해 줘"라고 하고 틀린 부분만 고칩니다.

익혀졌다는 신호: 몇 달 전 내가 쓴 기록을 읽고 "이거 안 써 뒀으면 큰일 났겠다"는 순간이 옵니다.

## 시작 순서

한꺼번에 시작하면 흐지부지됩니다.

| 순서 | 항목 | 비용 |
| --- | --- | --- |
| 오늘부터 | 1 검증, 5 기록 | 거의 없음 |
| 일하면서 | 4 위임 | 자연히 늘어남 |
| 의식만 하면 | 3 도메인 | 낮음 |
| 주 1회 시간 확보 | 2 기반 원리 | 따로 시간 필요 |

다섯 가지의 공통점은 전부 "코드를 더 잘 쓰는 법"이 아니라 "코드가 맞는지, 필요한지, 왜 그런지를 아는 법"이라는 점입니다.

## 하지 않아도 되는 것

- 새 프레임워크를 따라다니며 문법을 외우는 것
- 알고리즘 문제 풀이에 시간을 쏟는 것. 면접용이 아니면 수익이 낮아졌습니다.
- 에이전트보다 빨리 코드를 치려고 하는 것. 그 경쟁은 이미 끝났습니다.
